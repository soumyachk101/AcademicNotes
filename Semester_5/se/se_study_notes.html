Unit 1 — Software Process Models & Project Management

What is Software Engineering?

Software Engineering is the application of engineering principles to the design, development, testing, and maintenance of software. The goal is to produce reliable, cost-effective software on time. Three core forces act on every software project: customer requirements, time/budget constraints, and technical quality.

Software Process Model Comparison

flowchart BT W[Waterfall - Sequential, fixed reqs] --> I[Iterative - Refinement cycles] I --> INC[Incremental - Functional slices] INC --> S[Spiral - Risk-driven loops] S --> A[Agile - Customer-collaborative] A --> CBD[Component-Based - Reusable parts] CBD --> FM[Formal Methods - Math-based] FM --> XP[eXtreme Programming] XP --> SCR[Scrum]

The Generic Process Model (Pressman)

Five framework activities that every project uses, regardless of model choice:

  1. Communication — Understand stakeholder needs.
  2. Planning — Scope, resources, schedule, risks.
  3. Modeling — Analysis & design (UML models).
  4. Construction — Coding & testing.
  5. Deployment — Delivery to users, feedback.

Umbrella activities run across all five: project tracking, risk management, QA, configuration management, and reviews.

Waterfall Model

Linear sequential phases: Feasibility → Requirements → Design → Coding → Testing → Deployment → Maintenance. Each phase is completed and baselined before the next begins. Best when requirements are well understood and stable; unsuitable when requirements change frequently.

Iterative vs Incremental Model

Iterative: The entire system is repeatedly refined through cycles — each cycle produces a more complete version. Incremental: The system is built piece by piece — each increment delivers a new, usable set of features.

In practice, Iterative-Incremental combines both: each iteration delivers an increment.

Spiral Model — Risk-Driven Development

flowchart TD D[Determine Objectives] --> RA[Identify & Resolve Risks] RA --> ED[Develop & Test] ED --> PE[Plan Next Cycle] PE --> D

Agile Manifesto Values

Individuals & interactions over processes & tools
Working software over comprehensive documentation
Customer collaboration over contract negotiation
Responding to change over following a plan

12 Agile Principles: early delivery, welcome changing requirements, daily business-developer collaboration, face-to-face conversation, working software as primary measure, sustainable pace, technical excellence, simplicity, self-organising teams, regular reflection.

Agile vs Plan-Driven

Plan-driven (waterfall) assumes predictable processes and change is costly. Agile embraces change as a source of value. Hybrid approaches (Agile-Waterfall, ScrumBan) are increasingly common.

Scrum Framework

Roles: Product Owner (prioritises backlog), Scrum Master (facilitator, impediment remover), Development Team (self-organising, 3–9 members).

Events: Sprint (1–4 weeks), Sprint Planning, Daily Standup (15 min), Sprint Review, Sprint Retrospective, Backlog Refinement.

Artefacts: Product Backlog, Sprint Backlog, Product Increment, Burn-down Chart.

Scrum Sprint Flow

RUP Phases

Inception: Scope, feasibility, use-case model outline.
Elaboration: Refine requirements, establish architecture baseline.
Construction: Iterative implementation, continuous testing.
Transition: Beta releases, user training, deployment.

Software Project Management

Project Planning: Scope → WBS → Gantt/PERT → resource allocation.
Cost Estimation: COCOMO, Function Points, Expert Judgment.
Metrics: LOC, FP, Cyclomatic Complexity, Defect Density.
Scheduling: PERT, Gantt charts, CPM (Critical Path Method).
Tracking: Earned Value Management (EVM), burn-down charts.

COCOMO — Basic Formula

\[ E = a \times (KLOC)^b \]

\[ T_{dev} = c \times (E)^d \]

\[ SS = \frac{E}{T_{dev}} \]

Where: E = Effort (person-months), Tdev = Duration (months), SS = Avg staffing, KLOC = size.

ModeabcdProject Size
Organic2.41.052.50.38Small, familiar (2–50 KLOC)
Semi-Detached3.01.122.50.35Medium, mixed (50–300 KLOC)

Example: Organic project, 20 KLOC: \(E = 2.4 \times 20^{1.05} \approx 55.7\) PM, \(T_{dev} = 2.5 \times 55.7^{0.38} \approx 11.95\) months, \(SS = 55.7/11.95 \approx 5\) engineers.

Key Takeaway for Unit 1

Choose the process model based on project characteristics: use Waterfall for stable requirements, Spiral for high-risk projects, Agile for changing requirements, and CBD when reusable components are available.

Unit 2 — Requirement Analysis & Specification

Requirements Engineering Process

flowchart LR E[Elicitation] --> A[Analysis] A --> N[Negotiation] N --> V[Validation] V --> S[Specification] S --> M[Management] M -.->|Change| E

Elicitation Techniques

  • Interviews — Structured, open-ended, closed questions.
  • Workshops / JAD — Facilitated group sessions.
  • Surveys / Questionnaires — Broad stakeholder coverage.
  • Observation (Ethnography) — Watch real work practice.
  • Prototyping — Build a throwaway or evolutionary prototype.
  • Brainstorming — Free-form idea generation.
  • Use-Case Driven — Identify actors, scenarios, goals.

Elicitation Pitfalls

Customers may not know what they want until they see it. Hidden requirements come from tacit knowledge. Always prototype and validate early. Watch for ambiguity, incompleteness, inconsistency, and wishful thinking in requirements.

Unit 3 — Software Design & Testing

Software Design Concepts

  • Abstraction: Expose only essential features; hide complexity.
  • Refinement: Top-down decomposition of a problem into smaller, more manageable pieces.
  • Modularity: Decompose into cohesive, loosely-coupled modules.
  • Software Architecture: High-level organisation and component interaction.
  • Control Hierarchy: Calling structure of the modules.
  • Structural Partitioning: Horizontal (layers) and vertical (tasks) partitioning.
  • Information Hiding: Each module hides its implementation details behind an interface.

Software Testing Levels

flowchart BT U[Unit Testing] --> I[Integration Testing] I --> S[System Testing] S --> A[Acceptance Testing] A -.->|Feedback| U

Unit: Individual functions/classes in isolation.
Integration: Interface correctness between combined modules.
System: Full system compliance with SRS on production-like environment.
Acceptance: User-driven alpha (in-house) and beta (customer-site) testing.

JUnit 5 Unit Test Example

import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

class CalculatorTest {

    @Test
    void testAddition() {
        assertEquals(5, Calculator.add(2, 3));
        assertEquals(-1, Calculator.add(-2, 1));
    }

    @Test
    void testDivisionByZero() {
        ArithmeticException ex = assertThrows(
            ArithmeticException.class,
            () -> Calculator.divide(10, 0)
        );
        assertEquals("/ by zero", ex.getMessage());
    }

    @Test
    void testEdgeCases() {
        assertEquals(0, Calculator.add(0, 0));
        assertEquals(Integer.MAX_VALUE, Calculator.add(0, Integer.MAX_VALUE));
    }
}

Good unit tests cover: happy path, edge cases, and error paths. Use parameterised tests for multiple inputs.

Observer Pattern in Java

import java.util.*;

interface Observer {
    void update(String message);
}

class Subject {
    private final List<Observer> observers = new ArrayList<>();

    void subscribe(Observer o) { observers.add(o); }
    void unsubscribe(Observer o) { observers.remove(o); }

    void notifyObservers(String msg) {
        for (Observer o : observers) o.update(msg);
    }
}

class EmailNotifier implements Observer {
    private String email;
    EmailNotifier(String email) { this.email = email; }
    public void update(String msg) {
        System.out.println("Email to " + email + ": " + msg);
    }
}

class SMSNotifier implements Observer {
    private String phone;
    SMSNotifier(String phone) { this.phone = phone; }
    public void update(String msg) {
        System.out.println("SMS to " + phone + ": " + msg);
    }
}

Architectural Styles

  • Layered (N-Tier): Presentation → Business Logic → Data Access → Database.
  • Client-Server: Thin/fat clients communicate with a central server.
  • Pipe-and-Filter: Data flows through a chain of filters (compilers, Unix pipelines).
  • Repository (Shared Data): Central data store + independent agents (blackboard for AI).
  • Event-Driven: Components react to events posted on a bus (Kafka, RabbitMQ).
  • Microservices: Independently deployable services communicating via APIs; each owns its data store.

User Interface Design Principles

Shneiderman's Golden Rules:

  1. Place the user in control (undo, shortcuts, flexible interaction).
  2. Reduce the user's memory load (recognise over recall).
  3. Make the interface consistent (uniform terminology, actions, layout).

Nielsen's 10 Usability Heuristics: Visibility, Real-world mapping, User control, Consistency, Error prevention, Recognition over recall, Flexibility, Minimalist design, Helpful error messages, Help system.

UI Design Checklist

Consistent navigation? Error messages helpful? Feedback on every action? Accessible (keyboard, screen reader)? Responsive across devices? Adequate contrast ratio? Labels descriptive? Login/signup clear? Search prominent? Loading states visible?

Unit 4 — Software Quality & Maintenance

Software Quality Assurance (SQA)

SQA is a planned, systematic set of activities ensuring that processes and products conform to standards and requirements. Activities: Audits, Formal Technical Reviews (FTRs), Testing, Configuration Audits, Process & Product Quality Reviews.

Formal Technical Reviews (FTRs)

  • Walkthroughs: Author-led, open-ended, primarily to find defects and improve understanding.
  • Inspections: Formal process (7 steps), 5 roles: Moderator, Recorder, Reader, Author, Reviewer — most effective for defect removal.
  • Code Reviews: Peer-level review focusing on code quality, standards, efficiency.

Software Quality Concepts

McCall's Quality Model:

Product Operation: Correctness, Reliability, Efficiency, Integrity, Usability.

Product Revision: Maintainability, Flexibility, Testability.

Product Transition: Portability, Reusability, Interoperability.

Software Configuration Management (SCM)

SCM ensures the integrity of software artefacts throughout their lifecycle. Key activities:

  1. Configuration Identification — Name and catalogue CI.
  2. Version Control — Branch, merge, tag.
  3. Baseline Management — Formal freeze points.
  4. Change Control — CCB approves modifications.
  5. Configuration Audit — Verify conformance.
  6. Release Management — Package, distribute.

Software Reliability

Reliability is the probability of failure-free operation for a specified time.

\[ MTBF = MTTF + MTTR \]

\[ \text{Availability} = \frac{MTTF}{MTBF} \]

\[ \text{Failure Rate} \lambda = \frac{1}{MTTF} \]

\[ R(t) = e^{-\lambda t} \]

Software Maintenance

  • Corrective: Fix bugs.
  • Adaptive: Adapt to new environment.
  • Perfective: New features, performance improvements.
  • Preventive: Refactor to prevent future degradation.

ISO 9000 & SEI CMM

ISO 9000 is an international quality-management standard. ISO 9001:2015 focuses on process approach, risk-based thinking, Plan-Do-Check-Act (PDCA) cycle.

SEI CMM is a maturity framework specifically for software. Organisations are assessed against Key Process Areas (KPAs) and receive a maturity level from 1 to 5.

Formula Sheet

COCOMO — Basic

\[ E = a \times (KLOC)^b \qquad T_{dev} = c \times E^d \qquad SS = \frac{E}{T_{dev}} \]

COCOMO-II Maintenance

\[ AT = \frac{\text{Added} + \text{Modified}}{\text{Original Size}} \]

\[ AD = AT \times AAF \qquad E_{maintenance} = 2.4 \times (AD)^{1.05} \]

Software Reliability

\[ MTBF = MTTF + MTTR \]

\[ \text{Availability} = \frac{MTTF}{MTBF} \]

\[ \lambda = \frac{1}{MTTF} \qquad R(t) = e^{-\lambda t} \]

Function Points

\[ UFP = \sum (Count_i \times Weight_i) \]

\[ VAF = 0.65 + (0.01 \times \Sigma F_i) \]

\[ FP = UFP \times VAF \]

Cyclomatic Complexity

\[ CC = E - N + 2P \]

E = edges, N = nodes, P = connected components. This equals the number of linearly-independent paths, giving the minimum test cases needed for path coverage.

Halstead Complexity Measures

\[ N = \eta_1 + \eta_2 \qquad n = n_1 + n_2 \]

\[ V = N \times \log_2 n \qquad D = \frac{n_1}{2} \times \frac{n_2}{n_1} \]

\[ E = V \times D \qquad T = \frac{E}{S} \]

Earned Value Management (EVM)

\[ PV = \text{Planned Value (BCWS)} \]

\[ EV = \text{Earned Value (BCWP)} \]

\[ AC = \text{Actual Cost (ACWP)} \]

\[ SV = EV - PV \qquad CV = EV - AC \]

\[ SPI = \frac{EV}{PV} \qquad CPI = \frac{EV}{AC} \]

\[ EAC = \frac{BAC}{CPI} \qquad ETC = EAC - AC \]
