Introduction to SE

What is software, software crisis, myths, CMMI levels

What is Software?

Software is a collection of programs, documentation, and data that perform specific tasks on computer systems. It is a logical system element rather than a physical one — it is intangible and not constrained by physical laws.

Software consists of:

  • Programs — instructions that perform tasks when executed.
  • Documentation — manuals, design specs, user guides.
  • Data — structured information used by programs.

Software does not wear out but it does deteriorate due to changes in environment, bugs discovered over time, and performance degradation.

Software Crisis

The software crisis refers to the difficulties encountered in developing large, complex software systems within schedule and budget. It emerged in the late 1960s when the cost of software exceeded hardware costs and projects routinely failed.

Symptoms of the software crisis:

  • Projects running over budget and behind schedule.
  • Software is inefficient, unreliable, and hard to maintain.
  • Requirements are not clearly defined or keep changing.
  • Code quality is poor with many defects.
  • Difficulty in measuring progress and productivity.

The response was the emergence of software engineering as a discipline applying systematic, disciplined approaches to software development.

Software Engineering Definition

According to IEEE: "Software engineering is the application of a systematic, disciplined, quantifiable approach to the development, operation, and maintenance of software; that is, the application of engineering to software."

Software engineering combines principles from computer science, engineering, project management, and quality assurance to build reliable, efficient software on time and within budget.

Generic vs Custom Software

Generic (off-the-shelf) software: Developed for the mass market. Examples: MS Word, Photoshop, Android. Lower cost per unit, but may not perfectly fit any one user's needs.

Custom (bespoke) software: Developed for a specific customer to meet exact requirements. Higher cost, perfect fit, but limited market. Examples: banking systems, airline reservation.

Generic products have predictable, stable requirements; bespoke products have unique, evolving requirements.

Software Characteristics

  • Intangible — cannot be physically touched or seen.
  • Not constrained by physical laws — unlike hardware, doesn't wear out.
  • Custom-built — each project is different from the previous.
  • Complex — large systems have many interacting components.
  • Flexible — easy to change, but changes can introduce new bugs.
  • No manufacturing step — only development, then replication at near-zero cost.

Software Myths

Myths are false beliefs held by managers and practitioners that lead to poor practices.

  • Management myths: "We already have a book of standards — that should be enough." "If we're behind, add more programmers." "If we outsource, we can relax."
  • Customer myths: "A general statement of requirements is enough." "Software is flexible, so changes can be done easily anytime."
  • Practitioner myths: "Once we write the program and it works, our job is done." "Until the program runs, there is no way to assess quality." "The only deliverable for a successful project is a working program."

These myths lead to broken schedules, poor quality, and unsatisfied customers.

Software Process Framework

A process framework provides structure for software development. Five activities form the core:

  • Communication — collaborate with stakeholders to understand requirements.
  • Planning — define work schedule, resources, and tasks.
  • Modeling — create models to better understand requirements and design.
  • Construction — code generation and testing.
  • Deployment — deliver software to the customer for evaluation.

Umbrella activities (applied throughout): project tracking, risk management, quality assurance, configuration management, technical reviews.

SDLC Models

Waterfall, Spiral, V-Model, Incremental, RAD, Agile methodologies

What is SDLC?

SDLC (Software Development Life Cycle) is a framework that defines the process of building software from initial planning through deployment and maintenance. It provides a structured approach consisting of phases like requirement analysis, design, coding, testing, deployment, and maintenance.

An SDLC model is a representation of the process — choosing the right model depends on project requirements, complexity, team size, and customer involvement.

Waterfall Model

The Waterfall model is a linear, sequential approach where each phase must be completed before the next begins. Phases: Requirements → Design → Implementation → Verification → Maintenance.

Advantages: Simple, easy to manage; works well for small projects with clear requirements; documentation at each stage.

Disadvantages: No working software until late in the cycle; difficult to accommodate changes; high risk and uncertainty.

Iterative Model

The Iterative model starts with a small subset of requirements, builds an initial version, and progressively enhances it through repeated cycles. Each iteration produces a working version with added features.

Advantages: Early working version; easier to handle risks; customer feedback after each iteration.

Disadvantages: Requires more resources; iterative design may lead to architectural rework.

Spiral Model

The Spiral model combines iterative development with risk analysis. Each cycle has four phases: Planning → Risk Analysis → Engineering → Evaluation. Each loop produces a more refined version.

Advantages: Strong risk management; suitable for large, complex projects; accommodates changes.

Disadvantages: Expensive; needs expertise in risk analysis; may not suit small projects.

V-Model

The V-Model (Verification and Validation Model) is an extension of the waterfall where each development phase has a corresponding testing phase. The shape forms a V — verification on the left going down, validation on the right going up.

Advantages: Emphasizes testing; defects found early; works well for safety-critical systems.

Disadvantages: Rigid and expensive; not suitable for changing requirements.

Incremental Model

The Incremental model delivers the system in increments (chunks). Each increment adds new functionality to the existing core. The first increment is the basic version with limited features, and subsequent increments add features.

Advantages: Early delivery of partial functionality; easier to test and debug; customer feedback after each increment.

Disadvantages: Requires good upfront planning; total cost may exceed single delivery.

RAD (Rapid Application Development)

RAD is an incremental model with very short development cycles (typically 60–90 days). It emphasizes component-based construction and reuse. It uses prototyping, workshops, and user involvement heavily.

Advantages: Fast delivery; high user involvement; reduced risk through feedback.

Disadvantages: Requires highly skilled teams; not suitable for large, complex projects.

Agile Methodology

Agile is an iterative approach focused on collaboration, customer feedback, and rapid delivery. It breaks work into small increments (sprints) with minimal planning. The Agile Manifesto values: individuals over processes, working software over docs, customer collaboration over contracts, responding to change over following a plan.

Popular Agile frameworks:

  • Scrum: Uses sprints (2–4 weeks), daily stand-ups, product backlog, and roles like Scrum Master and Product Owner.
  • Extreme Programming (XP): Emphasizes engineering excellence — pair programming, TDD, continuous integration, frequent releases.

Advantages: Adaptive to change; early delivery; high customer satisfaction.

Disadvantages: Requires experienced team; less predictable scope; can lack documentation.

Prototyping Model

The Prototyping model builds a working prototype (mock-up) of the system, lets the user evaluate it, and then refines it based on feedback until an acceptable version is built. Useful when requirements are unclear.

Requirements & Design

Requirement engineering, SRS, coupling, cohesion, UML diagrams

Requirement Engineering Process

Requirement Engineering (RE) is the systematic process of developing requirements through four sub-activities:

  • Elicitation (Inception): Discover requirements from stakeholders, identify risks, and define scope. Techniques: interviews, questionnaires, observation, workshops.
  • Analysis (Negotiation): Refine and prioritize requirements, resolve conflicts between stakeholders, and determine feasibility.
  • Specification: Document requirements formally in an SRS (Software Requirements Specification) document.
  • Validation: Review, inspect, and validate that requirements correctly represent the system and are testable.

Functional vs Non-Functional Requirements

Functional requirements describe what the system does — features, functions, and behavior. Example: "The system shall allow users to reset their password."

Non-functional requirements describe how the system performs — quality attributes like:

  • Performance — response time, throughput.
  • Reliability — uptime, fault tolerance.
  • Usability — ease of learning, user-friendliness.
  • Security — authentication, authorization.
  • Maintainability — ease of modification.
  • Portability — ability to run on different platforms.

SRS Document Characteristics

SRS (Software Requirements Specification) is a complete document describing the intended behavior and constraints of the system.

Characteristics of a good SRS (per IEEE standard 830):

  • Correct — accurately reflects requirements.
  • Unambiguous — only one interpretation possible.
  • Complete — covers all significant requirements.
  • Consistent — no conflicting requirements.
  • Ranked for importance and stability — priorities clearly identified.
  • Verifiable — testable and demonstrable.
  • Modifiable — easy to change without losing consistency.
  • Traceable — origin and evolution trackable.

SRS Components (per IEEE 830): Introduction, Overall Description, Specific Requirements, Appendices.

Software Design Concepts

Modularity — dividing the software into smaller, manageable modules. Each module performs a specific function. Benefits: easier maintenance, testing, debugging, and parallel development.

Coupling — degree of interdependence between modules. Goal: LOW coupling. Types (from worst to best): content, common, control, stamp, data, message coupling.

Cohesion — degree to which elements within a module belong together. Goal: HIGH cohesion. Types (from worst to best): coincidental, logical, temporal, procedural, communicational, sequential, functional.

Architectural Design

Software architecture is the high-level structure of the software system — how components are organized and interact. Architectural styles include:

  • Layered (n-tier): Presentation → Business Logic → Data Layer.
  • Client-Server: Clients request services from a central server.
  • Microservices: Small, independent services communicating via APIs.
  • Pipe-and-Filter: Data flows through a series of transformations.
  • MVC (Model-View-Controller): Separates data, UI, and control logic.

Function-Oriented vs Object-Oriented Design

Function-Oriented Design (FOD): Decomposes the system into a hierarchy of functions. Uses DFDs (Data Flow Diagrams). Top-down approach. Examples: structured design, Jackson Structured Programming.

Object-Oriented Design (OOD): Decomposes the system into objects that combine data and behavior. Uses UML diagrams. Bottom-up approach. Examples: Booch, Rumbaugh, Jacobson methods.

UML Diagrams

UML (Unified Modeling Language) is a standard visual language for specifying, visualizing, constructing, and documenting software systems.

Common UML Diagrams:

  • Use Case Diagram: Shows actors and their interactions with the system. Captures functional requirements.
  • Class Diagram: Shows classes, attributes, methods, and relationships (association, inheritance, aggregation).
  • Sequence Diagram: Shows object interactions in time order — emphasizes message passing.
  • Activity Diagram: Shows workflows and business processes — like flowcharts with parallel support.
  • State Chart Diagram: Shows states and transitions of an object during its lifecycle.
  • Component Diagram: Shows software components and their dependencies.
  • Deployment Diagram: Shows physical architecture — hardware nodes and software deployment.
Key Concept: A well-designed system has high cohesion (elements within a module work together) and low coupling (modules are independent). This makes the system easier to maintain, test, and reuse.
Exam Tip: For UML questions, practice drawing neat diagrams with proper notation — stick figures for actors, rectangles for use cases, classes with three compartments, arrows for messages in sequence diagrams.

Explain coupling and cohesion.

Coupling measures the degree of interdependence between modules. Lower coupling is better.

  • Data coupling (best): Modules share only data via parameters.
  • Stamp coupling: Modules share a data structure but use only part of it.
  • Control coupling: One module controls the logic of another by passing control information.
  • Content coupling (worst): One module directly references another's internal code.

Cohesion measures how strongly elements within a module belong together. Higher cohesion is better.

  • Functional (best): All elements contribute to a single well-defined function.
  • Sequential: Output of one element is input of the next.
  • Communicational: Elements operate on the same data.
  • Coincidental (worst): Elements are grouped arbitrarily with no meaningful relationship.

Best design: low coupling + high cohesion.

Testing & Maintenance

V&V, test strategies, debugging, maintenance types, reverse engineering

Testing Fundamentals

Software testing is the process of evaluating a system to find defects and ensure it meets requirements. Goals: discover defects, gain confidence in quality, prevent future bugs, and validate functionality.

Key principles of testing:

  • Testing shows the presence of defects, not their absence.
  • Exhaustive testing is impossible — prioritize with risk and resources.
  • Early testing saves time and money.
  • Defects cluster in a few modules (Pareto principle).
  • Test should be tailored to the application.

Verification vs Validation (V&V)

Verification: "Are we building the product right?" Confirms the software correctly implements specified functions. Involves reviews, walkthroughs, inspections. Static testing — no code execution.

Validation: "Are we building the right product?" Confirms the software meets the user's actual needs. Involves actual testing. Dynamic testing — code is executed.

Testing Strategies

  • Unit Testing: Tests individual modules in isolation. Performed by developers. Uses stubs and drivers.
  • Integration Testing: Tests interaction between integrated modules. Approaches: top-down, bottom-up, sandwich.
  • System Testing: Tests the complete system against requirements. Includes performance, security, usability tests.
  • Acceptance Testing: Final test by end-users to determine if system is ready for delivery. Includes alpha (in-house) and gamma (in real environment).

Black-Box vs White-Box Testing

Black-Box Testing: Tests functionality without knowledge of internal code. Tester provides inputs and checks outputs. Techniques: equivalence partitioning, boundary value analysis, decision tables.

White-Box Testing: Tests internal structure of code. Tester examines paths, branches, conditions. Techniques: statement coverage, branch coverage, path coverage, condition testing.

Grey-Box Testing: Combines both — partial knowledge of internals with black-box testing.

Regression Testing

Regression testing is re-running existing tests after a code change (bug fix, new feature) to ensure the change has not broken existing functionality. It is a critical part of any maintenance cycle.

Strategy: maintain a regression test suite, automate where possible, run after every change.

Test Cases and Debugging

A test case specifies: preconditions, inputs, test procedure, expected outputs, and postconditions. Well-designed test cases expose defects efficiently.

Debugging is the process of finding and fixing the cause of a defect after testing has identified a failure. Strategies: brute force, backtracking, cause elimination, program slicing, using debugging tools (breakpoints, watchers).

Software Maintenance Types

Maintenance refers to changes made after delivery to fix faults, improve performance, or adapt to changes.

  • Corrective Maintenance: Fixing bugs and defects discovered after deployment.
  • Adaptive Maintenance: Adapting software to changes in environment (OS, hardware, regulations, business rules).
  • Perfective Maintenance: Adding new features or improving performance based on user requests.
  • Preventive Maintenance: Refactoring code to prevent future problems — improving maintainability.

Reverse Engineering and Re-engineering

Reverse Engineering: Analyzing an existing system to identify its components and their interrelationships, often to understand legacy systems. No change to the system — purely a knowledge extraction process.

Re-engineering: Improving the internal structure of an existing system without changing its external behavior. Includes reverse engineering + restructuring + forward engineering. Goal: improve maintainability and extend life.

Key Concept: Maintenance accounts for over 60% of the total cost of software. Preventive maintenance reduces future corrective work. Automated regression testing is essential for ongoing maintenance.
Exam Tip: When asked to differentiate verification and validation, remember the mnemonics: "Verification = Specs vs Product" (static), "Validation = User needs vs Product" (dynamic). A common trick: verification is internal; validation is external.

  • Focuses on inputs and outputs only.
  • Performed by testers, not developers.

  2. Adaptive: Adapting software to environmental changes — new OS, hardware, regulations, business rules.
  3. Perfective: Adding new features or improving performance/usability based on user requests.
  4. Preventive: Refactoring and improving code to prevent future bugs and improve maintainability.

Explain software testing in detail. Discuss different testing strategies, black-box and white-box testing techniques. Also explain types of software maintenance.

Software Testing: Process of evaluating software to find defects and verify it meets requirements.

Testing Strategies:

  • Unit Testing: Tests individual modules in isolation using stubs and drivers.
  • Integration Testing: Tests combined modules — top-down, bottom-up, or sandwich approach.
  • System Testing: Tests the entire integrated system against requirements — performance, security, load testing.
  • Acceptance Testing: Final test by users — alpha (in-house) and beta (real users).

Verification & Validation: Verification (static — reviews) checks "are we building it right?" Validation (dynamic — execution) checks "are we building the right thing?"

Black-Box Techniques:

  • Equivalence Partitioning: Divide inputs into classes that behave the same — test one from each class.
  • Boundary Value Analysis: Test at edges — min, min+1, max-1, max.
  • Decision Tables: Test combinations of inputs and their associated actions.
  • Cause-Effect Graphing: Map causes (inputs) to effects (outputs).

White-Box Techniques:

  • Statement Coverage: Execute every statement at least once.
  • Branch Coverage: Test both true and false branches.
  • Path Coverage: Test all independent paths through code.
  • Condition Coverage: Test all combinations of Boolean sub-conditions.

Regression Testing: Re-run existing tests after code changes to ensure no breakage.

Maintenance Types:

  • Corrective: Fix bugs (40-50% of maintenance).
  • Adaptive: Adapt to environment changes (25-30%).
  • Perfective: Add features / improve performance (20-25%).
  • Preventive: Refactor to prevent future issues.

Project Management

Planning, estimation, COCOMO, risk management, PERT/CPM

Project Planning

Project planning sets the foundation for a successful software project. It defines scope, identifies tasks, estimates resources and time, and produces a roadmap.

Key elements of a software project plan:

  • Scope — what will be built.
  • Objectives — measurable goals.
  • Schedule — timeline of activities.
  • Resources — people, hardware, software.
  • Estimation — cost and effort.
  • Risks — potential problems and mitigations.

Project Size Estimation — LOC & FP

LOC (Lines of Code): Measures size by counting source code lines. Simple but language-dependent; harder to estimate early in the project.

FP (Function Points): Measures size by functionality delivered to the user, independent of programming language. Components:

  • External Inputs (EI) — user inputs.
  • External Outputs (EO) — outputs to user.
  • External Inquiries (EQ) — interactive queries.
  • Internal Logical Files (ILF) — data maintained within system.
  • External Interface Files (EIF) — referenced data in other systems.

FP = unadjusted FP × complexity adjustment factor. Better than LOC for early estimation.

COCOMO Model

COCOMO (Constructive Cost Model) is a procedural cost estimation model by Barry Boehm (1981). Uses basic size (KLOC — thousands of lines of code) to estimate effort, schedule, and cost.

Three levels of COCOMO:

  • Basic: Quick estimate using project size only. Formula: Effort = a × (KLOC)^b (in person-months).
  • Intermediate: Considers 15 cost drivers (product, hardware, personnel, project attributes).
  • Detailed: Extension of intermediate with phase-by-phase estimation.

Putnam Model

The Putnam model is based on the Norden/Rayleigh curve. Effort = (Size / (Productivity × Time^(4/3))) × (Time factor). It emphasizes manpower buildup over time and is used for large projects.

Risk Management

Risk is a potential problem that may or may not occur. Risk management is the systematic process of identifying, analyzing, and responding to risks.

Types of Risks:

  • Project risks: Affect schedule, budget, resources (e.g., staff turnover).
  • Product risks: Affect quality and performance (e.g., incorrect algorithms).
  • Business risks: Affect the organization (e.g., changing market).
  • Technical risks: Related to technology (e.g., unreliable third-party components).

Risk Management Process

  • Risk Identification: List potential risks. Techniques: brainstorming, checklists, expert judgment, Delphi method.
  • Risk Analysis (Projection): Estimate probability and impact. Categorize as low/medium/high. Use Risk Exposure = Probability × Impact.
  • Risk Mitigation: Develop strategies — avoid, transfer, accept, or mitigate. Create contingency plans for high-risk items.
  • Risk Monitoring: Continuously track risks and update the risk profile throughout the project.

Project Scheduling — Gantt Chart

A Gantt chart is a horizontal bar chart that shows tasks along the y-axis and time on the x-axis. Bars represent the duration and start/end of each task. Useful for visualizing task dependencies and progress.

Advantages: Easy to read, shows progress visually, helps in resource allocation.

Disadvantages: Hard to show complex dependencies; doesn't show critical path.

PERT and CPM

PERT (Program Evaluation Review Technique): Three-time estimate method using optimistic (t_o), pessimistic (t_p), and most likely (t_m) times. Expected time: t_e = (t_o + 4t_m + t_p) / 6. Variance = ((t_p - t_o) / 6)^2. Useful when activity durations are uncertain.

CPM (Critical Path Method): Identifies the longest path through the project network — the critical path. Tasks on the critical path have zero slack; any delay delays the project. Uses deterministic time estimates.

Both use network diagrams with nodes (events) and arrows (activities) to model dependencies.

Staffing and Quality Assurance

Staffing: Choosing the right people, organizing them into effective teams. The W5HH principle (Why, What, When, Who, How, How much) helps plan staffing.

Software Quality Assurance (SQA): Systematic set of activities that ensure software processes and products conform to requirements, standards, and procedures. Includes technical reviews, software testing, process monitoring, and process improvement.

ISO 9000 and Six Sigma

ISO 9000: International quality management standard. Defines requirements for quality systems. For software, ISO 9001 specifies requirements for design, development, production, installation, and service.

Six Sigma: Quality management philosophy targeting 3.4 defects per million opportunities (DPMO). Uses DMAIC cycle: Define, Measure, Analyze, Improve, Control. Originally from Motorola, widely used in software quality.

Key Concept: Effective project management requires balancing the iron triangle: scope, schedule, and cost. Quality is at the center. Changing one affects the others.
