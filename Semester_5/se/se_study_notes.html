Software Process & Process Models

Characteristics · Software crisis · Process framework · CMMI · Waterfall · Incremental · Spiral · V-Model · RAD · Agile · DevOps

Quick Revision: Software is engineering discipline applying computer science to build products cost-effectively. Key characteristics: maintainability, dependability, efficiency, acceptability. Process models: Waterfall (linear), Incremental (phased), Spiral (risk-driven), V-Model (verification/validation), RAD (rapid), Agile (iterative). CMMI has 5 maturity levels.

1.1 Software Characteristics

Good software should exhibit:

  • Maintainability: Easy to correct, adapt, enhance after delivery.
  • Dependability & Reliability: Works correctly under stated conditions; handles failures gracefully.
  • Efficiency: Does not waste CPU, memory, or network resources.
  • Acceptability: Easy to learn and use for intended users (usability).

1.2 Software Crisis & Need for SE

The Software Crisis refers to the difficulties in developing useful, efficient software in the 1960s–70s. Symptoms:

  • Projects running over budget and over schedule.
  • Software was unreliable and difficult to maintain.
  • Requirements were poorly understood.
  • Quality was unpredictable.

Software Engineering emerged as a disciplined engineering approach to address these problems — applying theories, methods, and tools to produce high-quality software cost-effectively.

1.3 Software Process Framework

A Software Process is a set of activities, methods, and practices used to develop and maintain software. Framework activities:

  • Communication: Understanding stakeholder needs.
  • Planning: Estimating resources, schedule, risks.
  • Modeling: Creating analysis & design models.
  • Construction: Code generation, unit & integration testing.
  • Deployment: Deliver software to users, feedback loop.

Umbrella Activities cross-cut the framework: SQA, configuration management, measurement, risk management, review/audit.

1.4 CMMI — Capability Maturity Model Integration

CMMI provides a structured framework for process improvement with 5 maturity levels:

LevelNameDescription
1InitialProcess is unpredictable, chaotic. Success depends on individual effort.
2ManagedProjects are planned, performed, measured, and controlled at the project level.
3DefinedProcess is well characterized and understood; organization-wide standard.
4Quantitatively ManagedProcess is measured and controlled using statistical & quantitative techniques.
5OptimizingContinuous process improvement via quantitative feedback and innovation.

1.5 Process Models Overview

Software Process Models are abstract representations of the software development process:

  • Waterfall: Linear sequential phases; each must finish before next begins.
  • Incremental: Software delivered in increments; each increment adds functionality.
  • Spiral: Risk-driven; four quadrants per loop — determine objectives, identify/ resolve risks, develop & test, plan next iteration.
  • V-Model: Each development phase has a corresponding testing phase (verification vs validation).
  • RAD: Rapid Application Development; uses workshops, prototyping, and iterative development for fast delivery.
  • Agile: Iterative and incremental; values individuals, working software, customer collaboration, responding to change.

1.6 Agile Methodologies

Scrum: Work organized in sprints (2–4 weeks). Roles: Product Owner, Scrum Master, Development Team. Artifacts: Product Backlog, Sprint Backlog, Increment.

Kanban: Visualize work on a board (To Do / In Progress / Done); limit WIP; manage flow.

Extreme Programming (XP): Practices include pair programming, test-driven development (TDD), continuous integration, refactoring, small releases.

DevOps: Combines software Development and IT Operations. Focuses on CI/CD pipelines, infrastructure as code, monitoring, and automation to shorten development cycles.

5 Marks

Explain the Spiral Model in detail. What are its advantages?

The Spiral Model (Boehm, 1988) is a risk-driven process model that represents the development process as a spiral. Each loop (iteration) represents a phase and is divided into four quadrants:

Quadrant 1 — Determine Objectives: Identify objectives for this iteration and alternative ways to achieve them.
Quadrant 2 — Identify & Resolve Risks: Analyze risks; use prototyping, simulation, or benchmarking.
Quadrant 3 — Develop & Test: Build the next version of the software (code + test).
Quadrant 4 — Review & Plan: Review results with customer; plan next iteration.

Advantages: Risk handling is built in; good for large, complex projects; customer feedback incorporated each loop; supports incremental delivery. Limitation: Complex to manage, requires risk assessment expertise.

Explain Scrum methodology with its key artifacts and ceremonies.

Scrum is an Agile framework for managing product development. Work is done in Sprints (time-boxed iterations of 2–4 weeks).

Roles:
• Product Owner: Represents stakeholders; manages Product Backlog.
• Scrum Master: Facilitates the process, removes impediments.
• Development Team: Self-organizing, cross-functional (5–9 members).

Ceremonies: Sprint Planning, Daily Scrum (15-min stand-up), Sprint Review, Sprint Retrospective.

Artifacts: Product Backlog (prioritized features), Sprint Backlog (tasks for this sprint), Increment (shippable product).

Benefits: Faster delivery, transparent progress, adaptability to change.

DevOps = Development + Operations. It is a cultural and technical movement that aims to unify software development and IT operations.

Key Practices:
• CI/CD: Continuous Integration (merge code frequently + automated testing) and Continuous Delivery/Deployment (automate release pipeline).
• Infrastructure as Code (IaC): Manage infrastructure (servers, networks) through code (Terraform, Ansible).
• Monitoring & Logging: Real-time application performance monitoring (APM), centralized logging.
• Automated Testing: Unit, integration, regression tests run on every commit.
• Microservices: Decompose application into small, independently deployable services.

Benefits: Faster time-to-market, higher reliability, better collaboration between teams, automated rollback on failures.

15 Marks

Describe CMMI levels and explain how process maturity is assessed. Also discuss the importance of software process improvement.

CMMI (Capability Maturity Model Integration) is a framework developed by the Software Engineering Institute (SEI) to help organizations improve their software processes. It defines five maturity levels:

Level 1 — Initial: The organization does not have a stable environment for developing software. Processes are ad-hoc and chaotic. Success depends entirely on individual effort and heroics. Projects often exceed budget and schedule. No standardized procedures exist.

Level 2 — Managed: Project processes are planned, performed, measured, and controlled. Requirements management, project planning, monitoring & control, supplier agreement management, measurement & analysis, process & product quality assurance are established at the project level. Key process areas (KPAs): Requirements Management, Project Planning, Project Monitoring & Control, Configuration Management, etc.

Level 3 — Defined: Processes are well characterized and understood, and are described in standards, procedures, tools, and methods. The organization has a set of standard processes that are tailored for individual projects. Focus areas: Organizational Process Definition, Organizational Training, Integrated Software Management, Intergroup Coordination, Peer Reviews.

Level 4 — Quantitatively Managed: The organization sets quantitative quality goals for process and product. Detailed measurements are collected and analyzed. Process performance is understood using statistical and quantitative techniques. Sub-processes are selected and controlled.

Level 5 — Optimizing: The organization focuses on continuous process improvement through quantitative feedback and piloting innovative ideas. Defect prevention, causal analysis, and resolution are practiced. The organization proactively identifies and addresses weaknesses.

LevelNameKey FocusRisk Level
1InitialUnpredictableVery High
2ManagedProject managementHigh

Importance of Software Process Improvement (SPI): SPI leads to higher quality products, reduced development cost and time, improved predictability, better customer satisfaction, and competitive advantage. Organizations at higher CMMI levels consistently deliver better products on time and within budget.

Software Requirements Engineering

Requirements process · Types · Elicitation techniques · SRS (IEEE format) · Validation · Use Case Diagrams · RTM

Quick Revision: Requirements engineering is the process of establishing stakeholder needs, analyzing them, documenting them in SRS, and verifying. Functional requirements = what the system does. Non-functional = how well it does it. SRS follows IEEE 830-1998 format. Use cases model interactions. RTM traces requirements through design, code, and test.

2.1 Types of Requirements

Functional Requirements (FR): Describe what the system should do — computations, data handling, user interactions. Example: "The system shall validate user credentials before login."

Non-Functional Requirements (NFR): Describe how well the system performs — quality attributes. Categories:

  • Performance: Response time, throughput, resource utilization.
  • Security: Authentication, authorization, encryption.
  • Reliability: MTBF, failure rate, recovery time.
  • Usability: Ease of learning, interface design.
  • Portability: Ability to run on different platforms.
  • Scalability: Ability to handle growing workload.

2.2 Requirements Elicitation Techniques

Techniques to gather requirements from stakeholders:

  • Interviews: One-on-one or group discussions with stakeholders.
  • Questionnaires/Surveys: Structured questions for large groups.
  • Workshops/JAD Sessions: Facilitated group sessions with users, developers, domain experts.
  • Observation/Shadowing: Observe users in their work environment.
  • Prototyping: Build a mock-up to clarify requirements.
  • Document Analysis: Study existing systems, manuals, reports.
  • Use Case Analysis: Identify actors and their interactions with the system.

2.3 SRS Document Structure (IEEE 830-1998)

The Software Requirements Specification (SRS) is a comprehensive document describing the system from the user's perspective. IEEE standard sections:

  1. Introduction: Purpose, scope, definitions, references, overview.
  2. Overall Description: Product perspective, functions, user characteristics, constraints, assumptions.
  3. Specific Requirements: Functional, external interface, performance, design constraints, software system attributes, other requirements.
  4. Appendices: Detailed analysis models, hardware/software descriptions.
  5. Index

Good SRS characteristics: Correct, Unambiguous, Complete, Consistent, Ranked for importance, Verifiable, Modifiable, Traceable.

2.4 Use Case Diagrams

A Use Case Diagram shows the functional requirements of a system as interactions between actors (users or external systems) and use cases (functionalities). Elements:

  • Actor: Person or system interacting with the system (stick figure).
  • Use Case: Oval representing a specific functionality.
  • System Boundary: Rectangle enclosing use cases.
  • Associations: Lines connecting actors to use cases.
  • Include: One use case always includes another (dashed arrow with «include»).
  • Extend: One use case optionally extends another (dashed arrow with «extend»).

2.5 Requirement Validation & RTM

Requirement Validation ensures the documented requirements are correct, complete, consistent, and unambiguous. Techniques: reviews, prototyping, test-case generation, automated consistency checking.

Requirement Traceability Matrix (RTM): A table that traces each requirement through design, code, and test cases. Ensures every requirement is implemented and tested.

RTM Columns: Req ID → Req Description → Design Doc → Code Module → Test Case → Test Status

The Requirements Engineering process consists of:

2. Requirements Elicitation: Gather requirements from stakeholders using interviews, surveys, observation, workshops, and prototyping.

Software Design & Architecture

Design concepts · Cohesion & Coupling · Software Architecture · Design Patterns · Documentation types

Quick Revision: Design transforms requirements into an implementation blueprint. Key concepts: abstraction (hide details), refinement (elaborate), modularity (divide), cohesion (internal strength), coupling (inter-dependence). Architecture styles: Client-Server, 3-tier, n-tier, Pipe & Filter. Patterns: Factory, Singleton, Observer, Strategy.

3.1 Design Concepts

  • Abstraction: Hiding complexity by focusing on essential features. Example: A function name describes its purpose without exposing implementation.
  • Refinement: Elaborating a high-level specification step by step into detailed design. Top-down design approach.
  • Modularity: Dividing the system into separate, manageable modules with well-defined interfaces.
  • Software Architecture: The overall structure of the system — components, their relationships, and the environment.
  • Control Hierarchy: How control is organized among modules — centralized vs. decentralized.
  • Structural Partitioning: Dividing the program horizontally or vertically.
  • Data Structure: Organization of data (arrays, lists, trees, databases).

3.2 Cohesion & Coupling

Cohesion = how strongly related the elements within a single module are. Higher cohesion is better.

3.3 Software Architecture Styles

  • Client-Server: Clients request services; servers provide them. Separates UI from data. Example: Web applications, email.
  • 3-Tier Architecture: Presentation layer (UI), Business Logic layer (processing), Data layer (storage). Each layer can be deployed independently. Example: Banking apps.
  • n-Tier Architecture: Extension of 3-tier with more layers for scalability. Example: E-commerce with separate layers for presentation, business, data access, and database.
  • Pipe & Filter: Data flows through a series of processing components (filters) connected by pipes. Example: Compilers, UNIX shells.
  • Repository (Blackboard): Shared data repository accessed by independent components. Example: Speech recognition, AI systems.
  • Layered Architecture: Services organized in layers; each layer uses only the layer below. Example: OSI model, enterprise apps.
  • Microservices: Application as a collection of small, independent services communicating via APIs. Example: Netflix, Amazon.

3.4 Design Patterns

Design Patterns are reusable solutions to commonly occurring problems in software design (Gang of Four):

  • Factory Pattern (Creational): Creates objects without specifying exact class. A factory method returns an instance of one of several classes based on input. Use when class selection depends on runtime conditions.
  • Singleton Pattern (Creational): Ensures only one instance of a class exists. Provides a global access point. Use for logging, configuration managers, thread pools.
  • Observer Pattern (Behavioral): Defines a one-to-many dependency; when one object changes state, all dependents are notified automatically. Use for event handling, MVC architectures.
  • Strategy Pattern (Behavioral): Encapsulates interchangeable algorithms; makes them independently changeable. Use when multiple variants of an algorithm exist.

3.5 Software Documentation Types

  • User Documentation: Manuals, help files, tutorials for end users.
  • System Documentation: Requirements spec, design documents, architecture diagrams, source code comments.
  • Technical Documentation: API references, installation guides, database schemas, algorithms.
  • Process Documentation: Project plans, schedules, status reports, meeting minutes.

5 Marks 2023

Explain different types of cohesion with examples.

Functional Cohesion: All elements contribute to a single, well-defined task. Example: A module that computes employee salary. Best cohesion.

Sequential Cohesion: Output of one element serves as input to the next. Example: readFile() produces data consumed by parseData().

Communicational Cohesion: Elements operate on the same data. Example: Functions that all read/update a Student record.

Procedural Cohesion: Elements follow a specific execution order. Example: open(), read(), close() in sequence.

Temporal Cohesion: Elements are related by timing (executed at the same time). Example: System initialization functions.

Logical Cohesion: Elements are logically grouped but perform different tasks. Example: All print-related functions (printReport, printInvoice) in one module.

Coincidental Cohesion: No meaningful relationship; worst type. Example: Unrelated utility functions dumped together.

5 Marks

Explain different types of coupling.

Data Coupling: Modules share data only through parameters. Best type — independent modules. Example: Module A calls B(x, y) with data values.

Stamp Coupling: Modules share composite data structures (e.g., records) but use only parts. Example: Passing an entire Employee record when only the name field is needed.

Control Coupling: One module controls the flow of another by passing flags or control signals. Example: A main module passing a control flag to a sub-module.

External Coupling: Modules share external I/O devices or files. Example: Two modules both writing to the same physical printer.

Common Coupling: Multiple modules access and modify the same global data. Risky — changes affect many modules.

Content Coupling: One module directly modifies internal data of another. Worst type — modules are tightly interwoven.

Explain the Observer and Strategy design patterns.

Observer Pattern (Behavioral): Defines a one-to-many dependency between objects. When the subject's state changes, all observers are notified automatically. Uses push or pull mechanism.

Example: A YouTube channel (Subject) notifies subscribers (Observers) when a new video is uploaded. Each subscriber gets the notification independently.

Strategy Pattern (Behavioral): Encapsulates a family of algorithms and makes them interchangeable. The strategy object is passed to the context, which delegates behavior to it.

Example: A Navigation app supports different route strategies: ShortestPath, FastestRoute, ScenicRoute. The user can switch strategies without changing the Navigation class.

Software Testing

Testing objectives · Levels · White Box vs Black Box · Test Case Design · Cyclomatic Complexity · McCabe V(G) · Mutation · Regression

Quick Revision: Testing finds defects. Levels: Unit, Integration, System, Acceptance. White Box (structural) tests code paths; Black Box (functional) tests inputs/outputs. BVA tests boundaries. Equivalence Class partitions input. Decision Table tests combinations. Cyclomatic Complexity V(G) = E - N + 2P (McCabe) measures independent paths.

4.1 Testing Objectives, Principles & Levels

Objectives:

  • Finding defects that were not discovered during earlier phases.
  • Demonstrating that the software meets its requirements.
  • Preventing defects through good design and reviews.
  • Building confidence in the software's reliability.

Principles:

  • All tests should be traceable to customer requirements.
  • Tests should be planned long before testing begins.
  • The Pareto principle applies: 80% of errors come from 20% of modules.
  • Testing should begin "in small" and progress toward testing "in large".
  • Exhaustive testing is impossible — focus on risk areas.

Test Levels:

LevelWhat is TestedWho TestsWhen
Unit TestingIndividual modules/functionsDeveloperAfter coding
Integration TestingInteractions between modulesDeveloper/TesterAfter unit testing
System TestingComplete integrated systemIndependent testerAfter integration
Acceptance TestingSystem against user requirementsEnd user / CustomerBefore delivery

4.3 Test Case Design Techniques

1. Boundary Value Analysis (BVA): Test at the boundaries of equivalence classes. For a range [1, 100], test: 0, 1, 2, 99, 100, 101. Boundary values are more error-prone.

2. Equivalence Class Partitioning (ECP): Divide input domain into equivalence classes; test one representative from each. For [1, 100]: class-valid [1,100], class-invalid (<1), class-invalid (>100).

3. Decision Table Testing: Test combinations of conditions and actions using a table. Useful when multiple conditions interact. Each column = one test case.

4. State Transition Testing: Test valid and invalid state transitions in a system. Useful for systems with states (e.g., ATM: idle, card-inserted, PIN-entered, etc.).

4.4 Cyclomatic Complexity — McCabe V(G)

Cyclomatic Complexity measures the number of linearly independent paths through a program's control flow graph. It indicates testability and complexity.

McCabe's Formula:
V(G) = E − N + 2P
where E = number of edges, N = number of nodes, P = number of connected components (usually 1).

Alternative: V(G) = Number of decision points + 1
Numerical Example
Consider the following program:
IF A > 0 THEN
  IF B > 0 THEN X = X + 1
  ELSE X = X + 2
  END IF
ELSE
  X = X + 3
END IF

Decision points = 2 (IF A>0, IF B>0)
V(G) = 2 + 1 = 3 independent paths.

Paths:
1. A>0, B>0 → X=X+1
2. A>0, B<=0 → X=X+2
3. A<=0 → X=X+3

4.5 Mutation Testing

Mutation Testing evaluates the quality of a test suite by introducing small faults (mutants) into the source code and checking if the test suite detects them.

  • Mutant: A version of the program with a small change (e.g., replacing > with <, changing + to −).
  • Killed Mutant: A mutant that is detected (test fails) — good.
  • Survived Mutant: A mutant not detected — indicates weak test suite.
  • Mutation Score: (Killed / (Killed + Survived)) × 100%. Higher is better.

4.6 Regression Testing

Regression Testing re-runs previously executed tests after a change to ensure that the change has not introduced new defects in existing functionality. Methods:

  • Re-test all: Run the entire test suite (expensive but thorough).
  • Selective re-testing: Run only tests related to the changed component.
  • Prioritized re-testing: Run high-priority tests first based on risk and criticality.

5.5 Re-engineering & Reverse Engineering

Reverse Engineering: Analyzing an existing system to identify its components and interrelationships. Creates representations at a higher level of abstraction. Used to recover lost documentation, understand legacy systems.
