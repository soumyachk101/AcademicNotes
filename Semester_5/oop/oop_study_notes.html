Class and Object

A class is a blueprint/template. An object is an instance of a class that occupies memory at runtime.

class Car {
    // Fields (state)
    String brand;
    int speed;

    // Constructor
    Car(String brand, int speed) {
        this.brand = brand;
        this.speed = speed;
    }

    // Method (behavior)
    void accelerate() {
        speed += 10;
        System.out.println(brand + " at " + speed + " km/h");
    }
}

// Creating objects
Car c1 = new Car("Toyota", 60);
Car c2 = new Car("Honda", 45);

The Four Pillars of OOP

1. Encapsulation

Bundling data and methods that operate on it. Data is hidden using private and accessed via public getters/setters.

class BankAccount {
    private double balance;  // hidden data

    public void deposit(double amount) {
        if (amount > 0) balance += amount;
    }
    public double getBalance() {
        return balance;
    }
}

2. Abstraction

Hiding complex implementation, exposing only essential features. Achieved via abstract classes and interfaces.

3. Inheritance

A child class acquires properties and methods from a parent class. Promotes code reuse. Uses extends keyword.

4. Polymorphism

Same interface, different implementations. "Many forms." Compile-time (overloading) and runtime (overriding).

Constructors and Destructors

Constructor Rules

  • Name must match the class name exactly.
  • No return type (not even void).
  • Called automatically when new is used.
  • If no constructor is defined, Java provides a default no-arg constructor.

Constructor Types

Constructor Chaining

this() calls another constructor in the same class. super() calls the parent constructor. Must be the first statement.

Destructors: Java has no explicit destructors. Garbage Collection handles cleanup via finalize() (deprecated) or AutoCloseable / try-with-resources.

Super Keyword

super is used to access the parent class's members when they are hidden by the child class.

  • super.variable — access parent's field
  • super.method() — call parent's method
  • super() — call parent's constructor (must be first statement)
class Parent {
    String name = "Parent";
    Parent() { System.out.println("Parent()"); }
}
class Child extends Parent {
    String name = "Child";
    Child() {
        super();              // calls Parent()
        System.out.println(super.name);  // "Parent"
    }
}

Dynamic Method Dispatch

Runtime polymorphism. The JVM determines which overridden method to call based on the actual object type, not the reference type.

class Shape {
    void draw() { System.out.println("Drawing shape"); }
}
class Circle extends Shape {
    @Override void draw() { System.out.println("Drawing circle"); }
}
class Square extends Shape {
    @Override void draw() { System.out.println("Drawing square"); }
}

// Runtime dispatch
Shape s1 = new Circle();   // ref: Shape, obj: Circle
Shape s2 = new Square();   // ref: Shape, obj: Square
s1.draw();  // "Drawing circle"  ← runtime resolution
s2.draw();  // "Drawing square"
Dynamic dispatch only works for overridden methods. Overloaded methods are resolved at compile-time.

Abstract Classes and Interfaces

Abstract Class

  • Cannot be instantiated.
  • Can have abstract methods (no body) and concrete methods (with body).
  • Can have fields, constructors, static methods.
  • Child class must implement all abstract methods OR be abstract itself.

Interface

  • All methods are implicitly public abstract (pre-Java 8).
  • All fields are implicitly public static final.
  • Java 8+: default methods and static methods allowed.
  • Java 9+: private methods allowed.
  • A class can implement multiple interfaces.

  • Unchecked: Runtime exceptions (NPE, Arithmetic). Optional handling.

Try-Catch-Finally Blocks

try {
    // code that may throw an exception
    int result = 10 / 0;
} catch (ArithmeticException e) {
    System.out.println("Cannot divide by zero: " + e.getMessage());
} catch (Exception e) {
    System.out.println("General exception: " + e);
} finally {
    // ALWAYS executes (even if return in try/catch)
    // Use for cleanup: close files, connections
    System.out.println("Cleanup done");
}

Try-with-Resources (Java 7+)

try (FileInputStream fis = new FileInputStream("file.txt")) {
    // resource auto-closed at end
} catch (IOException e) {
    e.printStackTrace();
}
finally does NOT execute if System.exit() is called, or if the JVM crashes. Use it for cleanup, not for business logic.

Thread Creation Methods

Method 1: Extend Thread Class

class MyThread extends Thread {
    public void run() {
        System.out.println("Thread running: " + getName());
    }
}
MyThread t = new MyThread();
t.start();  // NOT t.run() — that runs on same thread!

Method 2: Implement Runnable Interface

class MyRunnable implements Runnable {
    public void run() {
        System.out.println("Thread running");
    }
}
Thread t = new Thread(new MyRunnable());
t.start();
Runnable is preferred because Java doesn't support multiple class inheritance. If you extend Thread, you cannot extend any other class. With Runnable, you still can.

Synchronization and Deadlock

Synchronization ensures only one thread accesses a shared resource at a time.

class Counter {
    private int count = 0;
    public synchronized void increment() {  // synchronized method
        count++;
    }
    // OR synchronized block:
    public void add(int n) {
        synchronized (this) {
            count += n;
        }
    }
}

Deadlock Conditions (Coffman conditions — all four must be true)

  1. Mutual Exclusion: Only one thread holds a resource at a time.
  2. Hold and Wait: Thread holds one resource and waits for another.
  3. No Preemption: Resources cannot be forcibly taken.
  4. Circular Wait: Circular chain of threads each waiting for next.
Deadlock prevention: Break any ONE Coffman condition. E.g., enforce a global lock ordering.

wait(), notify(), notifyAll()

These methods enable inter-thread communication. They must be called from within a synchronized block.

MethodDescription
wait()Releases lock, waits until notified
wait(long ms)Waits with timeout
notify()Wakes up ONE waiting thread
notifyAll()Wakes up ALL waiting threads
synchronized (sharedObj) {
    while (!condition) {
        sharedObj.wait();   // releases lock, waits
    }
    // condition met — proceed
    sharedObj.notifyAll(); // wake other waiting threads
}
Always use wait() inside a while loop (not if), to handle spurious wakeups. Always call notifyAll() rather than notify() to avoid "lost notify" bugs.

Generics & Collections Framework

Generics — Advantages & Syntax

Advantages

  1. Type Safety: Compile-time type checking. No ClassCastException at runtime.
  2. No Casting: Eliminates explicit type casting when retrieving elements.
  3. Reusability: One class works with multiple types.
// Without generics (raw type — unsafe)
List list = new ArrayList();
list.add("hello");
String s = (String) list.get(0);  // manual cast needed

// With generics (type-safe)
List list = new ArrayList<>();
list.add("hello");
String s = list.get(0);  // no cast needed, compile-time checked

class Box {

    public T get() { return value; }

Box intBox = new Box<>();
Box strBox = new Box<>();

Type Erasure

Java generics are implemented using type erasure. All generic type information is removed by the compiler and replaced with raw types or casts. Generics are a compile-time feature only.

// Source code
List list = new ArrayList<>();
list.add("hello");
String s = list.get(0);

// After type erasure (bytecode)
List list = new ArrayList();
list.add("hello");
String s = (String) list.get(0);  // compiler inserts cast
Because of type erasure, new T() is illegal (no Class object at runtime). Use Class<T> parameter to work around this. Also, you cannot create generic arrays: new T[10] is illegal.

    String s = it.next();

Member Inner Class

class Outer {
    private int x = 10;

    class Inner {  // member inner class
        void display() {
            System.out.println("x = " + x);  // access outer private
        }
    }
}

// Usage
Outer outer = new Outer();
Outer.Inner inner = outer.new Inner();
inner.display();

Static Nested Class

class Outer {
    static int staticVar = 5;
    int instanceVar = 10;

    static class StaticNested {
        void display() {
            System.out.println("staticVar = " + staticVar);
            // System.out.println(instanceVar); // ERROR — no outer instance
        }
    }
}

// Usage — no outer object needed
Outer.StaticNested nested = new Outer.StaticNested();
nested.display();

Local Inner Class

Declared inside a method or block. Can only access final or effectively final local variables (Java 8+).

public void process(int param) {
    final int localVar = 100;  // must be effectively final

    class LocalInner {
        void show() {
            System.out.println(param);     // OK — method parameter (effectively final)
            System.out.println(localVar);  // OK — final local
        }
    }

    LocalInner li = new LocalInner();
    li.show();
}
After Java 8, variables just need to be effectively final (not explicitly declared final, but never reassigned). This is a common exam question.

Anonymous Inner Class

Declared and instantiated simultaneously. Used primarily for overriding methods on the fly, especially with interfaces and abstract classes.

// With an interface
interface Greeting {
    void greet();
}

Greeting g = new Greeting() {
    @Override
    public void greet() {
        System.out.println("Hello from anonymous class!");
    }
};
g.greet();

// With a Thread
Thread t = new Thread(new Runnable() {
    @Override
    public void run() {
        System.out.println("Running...");
    }
});
t.start();

// Lambda equivalent (Java 8+)
Greeting g2 = () -> System.out.println("Hello from lambda!");
Runnable r = () -> System.out.println("Lambda thread");
An anonymous class can implement an interface or extend a class (but not both). It must implement ALL abstract methods of the interface (unless it's a SAM interface, in which case a lambda works).

Singleton Design Pattern

Ensures only ONE instance of a class exists. Provides a global access point.

Eager Initialization (Thread-Safe)

public class Singleton {
    private static final Singleton INSTANCE = new Singleton();

    private Singleton() {}  // private — prevent external instantiation

    public static Singleton getInstance() {
        return INSTANCE;
    }

    public void doSomething() {
        System.out.println("Singleton working...");
    }
}
// Usage
Singleton s = Singleton.getInstance();

Lazy Initialization (Thread-Safe)

public class SingletonLazy {
    private static volatile SingletonLazy instance;

    private SingletonLazy() {}

    public static SingletonLazy getInstance() {
        if (instance == null) {
            synchronized (SingletonLazy.class) {
                if (instance == null) {
                    instance = new SingletonLazy();
                }
            }
        }
        return instance;
    }
}
The double-check locking pattern needs volatile to prevent instruction reordering. Bill Pugh Singleton (static inner holder) is the cleanest approach.

Factory Design Pattern

Creates objects without specifying the exact class. A factory class decides which subclass to instantiate based on input.

// Product interface
interface Vehicle {
    void drive();
}

// Concrete products
class Car implements Vehicle {
    public void drive() { System.out.println("Driving a car"); }
}
class Bike implements Vehicle {
    public void drive() { System.out.println("Riding a bike"); }
}

// Factory
class VehicleFactory {
    public static Vehicle getVehicle(String type) {
        switch (type.toLowerCase()) {
            case "car":  return new Car();
            case "bike": return new Bike();
            default: throw new IllegalArgumentException("Unknown type");
        }
    }
}

// Usage
Vehicle v = VehicleFactory.getVehicle("car");
v.drive();  // "Driving a car"
Factory pattern decouples object creation from usage. Adding a new product type only requires changes to the factory, not to client code. Open/Closed Principle.

Class Loader Subsystem

  • Bootstrap ClassLoader: Loads core Java classes (rt.jar). Written in native code.
  • Extension ClassLoader: Loads from jre/lib/ext.
  • Application ClassLoader: Loads from classpath.

Memory Areas

  • Method Area: Class-level data (fields, methods, constant pool). Shared across threads.
  • Heap: All objects and arrays. Shared across threads. Garbage collected.
  • Stack: Per-thread. Stack frames with local vars, operands, return address.
  • PC Register: Per-thread. Holds address of currently executing JVM instruction.
  • Native Method Stack: Per-thread. For native (non-Java) method calls.

Garbage Collection Basics

When is an Object Eligible for GC?

  1. All references to the object are set to null.
  2. The reference variable goes out of scope.
  3. Re-assigned to point to another object.

Finalize()

protected void finalize() throws Throwable {
    // Called by GC before object is collected
    // DEPRECATED in Java 9 — do NOT rely on it
}

GC Methods

System.gc();        // Suggests GC (JVM may ignore)
System.runFinalization();  // Runs pending finalize() methods

Common GC Algorithms

AlgorithmHow It Works
Mark and SweepMark reachable objects, sweep (free) unmarked. Causes fragmentation.
CopyingTwo semi-spaces. Copy live objects, clear source. No fragmentation.
Mark and CompactMark live objects, compact them to one end. No fragmentation, no waste.

JVM uses generational GC by default. Minor GC is fast (Young Gen is small). Major GC is slower (Old Gen is larger).

  • Confusing overloading (compile-time) with overriding (runtime).
  • Using == instead of .equals() for wrapper/String comparison.
  • Calling t.run() instead of t.start() for threads.
  • Forgetting that Java does NOT support multiple class inheritance.
  • Missing @Override annotation — subtle signature errors won't be caught.
  • Not calling super() in child constructor when parent has no default constructor.
  • Catching Exception before specific subclasses (wrong order).
  • Calling wait() outside a synchronized block — throws IllegalMonitorStateException.

Q: What is constructor chaining? Explain with an example using this() and super().

Constructor chaining is the process of calling one constructor from another. In Java, this() calls another constructor in the same class, while super() calls the parent class constructor. Both must be the first statement in the constructor body.

class Person {
    String name;
    int age;

    Person() {
        this("Unknown", 0);  // calls parameterized constructor
        System.out.println("Person default constructor");
    }

    Person(String name, int age) {
        this.name = name;
        this.age = age;
        System.out.println("Person parameterized constructor");

}

class Student extends Person {
    int roll;

        super();  // calls Person() — must be first
        this.roll = 0;

        super(name, age);  // calls Person(String, int)
        this.roll = roll;

}

Chaining avoids duplicate initialization code. If super() is not explicitly written, the compiler inserts it automatically — but only if the parent has a no-arg constructor. If the parent has only parameterized constructors, you must explicitly call super(args).

Q: Explain checked vs unchecked exceptions with examples. Why are checked exceptions controversial?

Checked Exceptions are verified at compile time. The compiler forces you to either catch them with a try-catch block or declare them with the throws keyword. Examples: IOException, ClassNotFoundException, SQLException.

Unchecked Exceptions (runtime exceptions) extend RuntimeException. They are not checked at compile time — handling is optional. Examples: NullPointerException, ArithmeticException, ArrayIndexOutOfBoundsException.

// Checked — must be handled
try {
    BufferedReader br = new BufferedReader(new FileReader("file.txt"));
    String line = br.readLine();
} catch (IOException e) {
    e.printStackTrace();
}

// Unchecked — optional handling
int result = 10 / 0;  // ArithmeticException at runtime

Controversy: Checked exceptions were introduced to force error handling, but in large applications they lead to verbose boilerplate code. Many modern JVM languages (Kotlin, Scala) eliminate checked exceptions entirely, treating all exceptions as unchecked.

Q: Describe the different states in a thread's lifecycle with a diagrammatic explanation.

A Java thread can exist in six states defined by the Thread.State enum:

  1. NEW: Thread is created but start() has not been called yet. The thread is not yet eligible to run.
  2. RUNNABLE: The thread is executing or ready to execute. The JVM/OS scheduler decides when it actually runs on the CPU.
  3. BLOCKED: The thread is waiting to acquire a monitor lock to enter a synchronized block or method. This happens when another thread holds the lock.
  4. WAITING: The thread is waiting indefinitely for another thread to perform a specific action. Caused by Object.wait(), Thread.join(), or LockSupport.park().
  5. TIMED_WAITING: The thread is waiting for a specified maximum time. Caused by Thread.sleep(ms), Object.wait(timeout), or Thread.join(timeout).
  6. TERMINATED: The thread has completed execution (the run() method returned) or was terminated abnormally.

    catch (InterruptedException e) { }
});
System.out.println(t.getState());  // NEW
t.start();
System.out.println(t.getState());  // RUNNABLE (briefly)
// After sleep: TIMED_WAITING
// After completion: TERMINATED

Q: What are wrapper classes? Explain autoboxing and unboxing with a common pitfall example.

Wrapper classes convert Java primitives into objects. They are needed because collections and generics work only with objects, not primitives. Each primitive has a corresponding wrapper: int → Integer, double → Double, char → Character, etc.

Autoboxing (Java 5+) automatically converts a primitive to its wrapper. Unboxing automatically converts a wrapper back to a primitive.

// Autoboxing
Integer i = 10;       // int → Integer automatically
ArrayList list = new ArrayList<>();
list.add(5);          // int → Integer automatically

// Unboxing
int n = i;            // Integer → int automatically
int sum = i + 5;      // auto unbox, add, auto re-box

Common pitfall: Using == to compare wrapper objects. The == operator compares references (memory addresses), not values. Java caches Integer objects in the range -128 to 127, so Integer a = 100; Integer b = 100; a == b returns true. But Integer a = 128; Integer b = 128; a == b returns false because 128 is outside the cache range. Always use .equals() for value comparison.

Q: What are the different types of inner classes in Java? Explain the concept of "effectively final" variables.

Java has four types of inner classes:

  1. Member Inner Class: Declared at the class level (non-static). Has access to all members of the outer class, including private ones. Created via outer.new Inner().
  2. Static Nested Class: Declared with static. Can only access static members of the outer class. Does not need an outer instance. Created via new Outer.StaticNested().
  3. Local Inner Class: Declared inside a method or block. Can access all members of the outer class and local variables.
  4. Anonymous Inner Class: Declared and instantiated simultaneously, without a name. Used mainly for implementing interfaces or extending classes on the fly.

Effectively final: A local or parameter variable is "effectively final" if its value is never changed after assignment. Before Java 8, such variables had to be explicitly declared final to be accessed from an inner class. Java 8 relaxed this rule — the compiler detects effectively final variables automatically. However, if the variable is reassigned even once, it is no longer effectively final and the inner class cannot access it.

Q: Explain the four conditions for deadlock (Coffman conditions) and how to prevent deadlock.

A deadlock occurs when two or more threads are blocked forever, each waiting for resources held by the others. All four Coffman conditions must hold simultaneously:

  1. Mutual Exclusion: Only one thread can hold a resource at a time. Resources are not shareable.
  2. Hold and Wait: A thread holding at least one resource is waiting to acquire additional resources held by other threads.
  3. No Preemption: A resource cannot be forcibly taken from a thread. The thread holding it must voluntarily release it.
  4. Circular Wait: A circular chain of threads exists, where each thread holds a resource the next thread needs. e.g., Thread A holds R1 and waits for R2, Thread B holds R2 and waits for R1.

Prevention: Break any one of the four conditions. The most practical approach is to enforce a global lock ordering — all threads must acquire locks in a predefined order. This eliminates circular wait. Alternatively, use tryLock() with timeouts from java.util.concurrent.locks.Lock to avoid indefinite waiting.

Q: Write a detailed Java program demonstrating multithreading, synchronization, and inter-thread communication using wait() and notifyAll(). Include producer-consumer pattern.

Threads allow concurrent execution. Synchronization ensures mutual exclusion for shared resources. The producer-consumer problem is a classic example where one thread produces data and another consumes it, with a shared buffer of fixed capacity.

class SharedBuffer {
    private final int[] buffer;
    private int count = 0, in = 0, out = 0;

    public SharedBuffer(int size) { buffer = new int[size]; }

    // Producer calls this
    public synchronized void produce(int value) throws InterruptedException {
        while (count == buffer.length) {
            wait();  // buffer full — wait
        }
        buffer[in] = value;
        in = (in + 1) % buffer.length;
        count++;
        System.out.println("Produced: " + value);
        notifyAll();  // wake up waiting consumers
    }

    // Consumer calls this
    public synchronized int consume() throws InterruptedException {
        while (count == 0) {
            wait();  // buffer empty — wait
        }
        int value = buffer[out];
        out = (out + 1) % buffer.length;
        count--;
        System.out.println("Consumed: " + value);
        notifyAll();  // wake up waiting producers
        return value;
    }
}

class Producer implements Runnable {
    private final SharedBuffer sb;
    Producer(SharedBuffer sb) { this.sb = sb; }

    @Override
    public void run() {
        for (int i = 1; i <= 10; i++) {
            try { sb.produce(i); Thread.sleep(100); }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }
    }
}

class Consumer implements Runnable {
    private final SharedBuffer sb;
    Consumer(SharedBuffer sb) { this.sb = sb; }

    @Override
    public void run() {
        for (int i = 0; i < 10; i++) {
            try { sb.consume(); Thread.sleep(150); }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }
    }
}

public class ProducerConsumerDemo {
    public static void main(String[] args) {
        SharedBuffer buffer = new SharedBuffer(5);
        Thread producer = new Thread(new Producer(buffer));
        Thread consumer = new Thread(new Consumer(buffer));

        producer.start();
        consumer.start();

        try {
            producer.join();
            consumer.join();
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
        System.out.println("All items produced and consumed.");
    }
}

(1) Both produce() and consume() are synchronized — only one thread can execute either at a time. (2) wait() is called inside a while loop, not an if-statement, to handle spurious wakeups. (3) notifyAll() wakes all waiting threads so both producers and consumers can re-check conditions. (4) Using notify() instead can cause a "lost notify" where the wrong thread type is woken. (5) The circular buffer uses modulo arithmetic for wrap-around indexing.

Q: Explain the Java Collections Framework hierarchy in detail. Compare ArrayList, LinkedList, HashSet, TreeSet, HashMap, and TreeMap with time complexities and use cases.

The Collections Framework provides a unified architecture for representing and manipulating collections. The root is the Collection interface, which branches into List, Set, and Queue. Map is a separate top-level interface.

List Implementations:

  • ArrayList: Backed by a dynamic array. O(1) random access, O(n) insertion/deletion in the middle. Best default choice. Not thread-safe.
  • LinkedList: Doubly linked list. O(1) insertion/deletion at known positions, O(n) random access. Use only when frequent insertions at both ends are needed.
  • Vector: Legacy synchronized dynamic array. All methods are synchronized, making it slower. Replaced by Collections.synchronizedList(new ArrayList<>()) or CopyOnWriteArrayList.

Set Implementations:

  • HashSet: Uses a HashMap internally. O(1) add/contains/remove. No ordering. Allows one null element.
  • LinkedHashSet: Maintains insertion order using LinkedHashMap. O(1) operations. Slightly slower than HashSet.
  • TreeSet: Backed by Red-Black Tree. O(log n) for all operations. Sorted order via natural ordering or Comparator. Does not allow null elements (if natural ordering is used).

Map Implementations:

  • HashMap: Hash table with buckets. O(1) get/put. Allows one null key, multiple null values. Not thread-safe. Not ordered.
  • LinkedHashMap: Maintains insertion or access order. O(1) operations.
  • TreeMap: Red-Black Tree based. O(log n). Sorted by natural order or comparator. No null keys.
  • Hashtable: Legacy synchronized map. Does not allow nulls. Use ConcurrentHashMap for thread-safe maps in modern code.
// Iterator — forward only, can remove
List list = new ArrayList<>(Arrays.asList("A","B","C","D"));
Iterator it = list.iterator();
while (it.hasNext()) {
    String s = it.next();
    if (s.equals("B")) it.remove();  // safe removal
}

// ListIterator — bidirectional, can add/set/remove
ListIterator lit = list.listIterator();
while (lit.hasNext()) { lit.next(); }
while (lit.hasPrevious()) {
    lit.previous();
    lit.set("X");  // modify
}
lit.add("E");     // add during iteration

Important: Map does NOT extend Collection. Iterating a HashMap can be done via entrySet(), keySet(), or values(). The entrySet() approach is most efficient as it gives direct access to both key and value in one iteration.

Q: Describe the Singleton and Factory design patterns. Explain thread-safety issues in Singleton and provide all standard implementations with their trade-offs.

Singleton Pattern ensures exactly one instance of a class exists and provides a global access point. It is used for logging, configuration, thread pools, and database connections.

Implementation 1 — Eager Initialization: The instance is created when the class is loaded. Thread-safe by default since the JVM handles class loading synchronization. Drawback: instance is created even if never used.

public class SingletonEager {
    private static final SingletonEager INSTANCE = new SingletonEager();
    private SingletonEager() {}
    public static SingletonEager getInstance() { return INSTANCE; }
}

Implementation 2 — Lazy Initialization (Double-Check Locking): Instance is created only on first request. Uses synchronized block for thread safety. The volatile keyword prevents instruction reordering.

public class SingletonLazy {
    private static volatile SingletonLazy instance;
    private SingletonLazy() {}

    public static SingletonLazy getInstance() {
        if (instance == null) {                       // Check 1 (no lock)
            synchronized (SingletonLazy.class) {
                if (instance == null) {               // Check 2 (with lock)
                    instance = new SingletonLazy();    // volatile prevents reordering
                }
            }
        }
        return instance;
    }
}

Implementation 3 — Bill Pugh (Static Inner Holder): The cleanest approach. The inner static class holds the instance and is loaded only when getInstance() is called. Thread-safe without explicit synchronization.

public class SingletonBillPugh {
    private SingletonBillPugh() {}
    private static class Holder {
        static final SingletonBillPugh INSTANCE = new SingletonBillPugh();
    }
    public static SingletonBillPugh getInstance() {
        return Holder.INSTANCE;
    }
}

Factory Pattern decouples object creation from usage. A factory class determines which concrete class to instantiate based on input parameters. This follows the Open/Closed Principle — new types can be added by extending the factory, without modifying client code.

interface Payment {
    void pay(double amount);
}

class CreditCardPayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paid " + amount + " via Credit Card");
    }
}

class UPIPayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paid " + amount + " via UPI");
    }
}

class PaymentFactory {
    public static Payment createPayment(String type) {
        return switch (type.toLowerCase()) {
            case "card" -> new CreditCardPayment();
            case "upi" -> new UPIPayment();
            default -> throw new IllegalArgumentException("Unknown: " + type);
        };
    }
}

Serialization hazard: Singleton can be broken by deserialization (a new instance is created). Fix by adding readResolve() method. Reflection hazard: A constructor can be called reflectively. Fix by throwing an exception in the constructor if INSTANCE is not null. Cloning hazard: Override clone() to throw CloneNotSupportedException.

Q: Describe JVM architecture in detail, including class loading mechanism, memory areas, and garbage collection algorithms.

The JVM (Java Virtual Machine) is the runtime engine that executes Java bytecode. It consists of three main subsystems: the Class Loader Subsystem, the Runtime Data Areas, and the Execution Engine.

Class Loader Subsystem: Responsible for loading, linking, and initializing class files. It uses a parent-delegation model.

  • Bootstrap ClassLoader: Loads core Java classes from rt.jar (or the jmods directory in Java 9+). Written in native code. It is the parent of all class loaders.
  • Extension ClassLoader: Loads classes from jre/lib/ext. Child of Bootstrap.
  • Application ClassLoader: Loads classes from the classpath (CLASSPATH environment variable). Child of Extension.

Linking: Verification ensures bytecode correctness. Preparation allocates memory for static fields. Resolution replaces symbolic references with direct references. Initialization executes static initializers.

Runtime Data Areas:

  • Method Area: Stores class-level data: field metadata, method metadata, constant pool, static variables. Shared by all threads.
  • Heap: Stores all objects and arrays. Shared by all threads. Garbage-collected. This is where new allocates memory.
  • Stack: Each thread has its own stack. Contains stack frames with local variables, operand stack, and return address. Created when a thread starts, destroyed when it ends.
  • PC Register: Per-thread. Holds the address of the currently executing JVM instruction.
  • Native Method Stack: Per-thread. Used for native (non-Java) method invocations via JNI.

Execution Engine: The interpreter reads bytecode line by line. The JIT (Just-In-Time) compiler compiles frequently executed ("hot") bytecode into native machine code for performance. The Garbage Collector reclaims memory from unreachable objects.

Garbage Collection Algorithms:

  • Mark and Sweep: Traverses all reachable objects from GC roots (marks them), then frees unmarked objects. Causes memory fragmentation.
  • Copying: Uses two equal semi-spaces. Live objects are copied to the other space, then the source is cleared entirely. No fragmentation but wastes half the heap.
  • Mark and Compact: Marks live objects, then slides them to one end of the heap, eliminating fragmentation. Used for the Old Generation.
  • Generational GC: Divides the heap into Young Generation (Eden + Survivor spaces) and Old Generation. Objects that survive multiple minor GCs in Young Gen are promoted to Old Gen. Minor GC (Young Gen) is fast and frequent. Major/Full GC (Old Gen) is slower and causes longer pauses.

Object eligibility for GC: An object becomes eligible when no reachable reference points to it — i.e., all references are set to null, the reference goes out of scope, or the reference is reassigned. The finalize() method (deprecated in Java 9) was the only chance to perform cleanup before collection. Modern code should use try-with-resources or explicit cleanup methods instead.

Q: Explain exception handling in Java in detail. Cover the exception hierarchy, checked vs unchecked exceptions, try-catch-finally, custom exceptions, and the throw/throws keywords. Provide a complete program with a user-defined exception.

Java's exception handling provides a robust mechanism for handling runtime errors and exceptional conditions gracefully, separating error-handling code from normal business logic.

Exception Hierarchy: All exceptions inherit from Throwable, which has two main subclasses:

  • Error: Serious system-level problems (e.g., OutOfMemoryError, StackOverflowError). Applications should NOT catch these — they indicate JVM-level failures.
  • Exception: Conditions that programs can catch and recover from. Divided into:
    • Checked Exceptions: Subclasses of Exception (but NOT RuntimeException). Checked at compile time. Must be handled via try-catch or declared with throws. Examples: IOException, ClassNotFoundException, SQLException.
    • Unchecked (Runtime) Exceptions: Subclasses of RuntimeException. Not checked at compile time. Handling is optional. Examples: NullPointerException, ArithmeticException, IndexOutOfBoundsException, IllegalArgumentException.

try-catch-finally:

  • try: Encloses code that might throw an exception.
  • catch: Handles specific exception types. Multiple catch blocks are allowed. Must order from most specific to most general.
  • finally: Always executes (unless System.exit() is called or JVM crashes). Used for cleanup — closing files, releasing connections.
  • Java 7 introduced try-with-resources for automatic resource management.

throw vs throws: throw explicitly throws an exception object. throws declares that a method may throw certain exceptions (part of the method signature).

// Custom (user-defined) exception
class InsufficientFundsException extends Exception {
    private double deficit;

    public InsufficientFundsException(String message, double deficit) {
        super(message);
        this.deficit = deficit;
    }

    public double getDeficit() { return deficit; }
}

class BankAccount {
    private double balance;

    public BankAccount(double balance) { this.balance = balance; }

    public void withdraw(double amount) throws InsufficientFundsException {
        if (amount > balance) {
            throw new InsufficientFundsException(
                "Need " + (amount - balance) + " more", amount - balance);
        }
        balance -= amount;
    }

    public double getBalance() { return balance; }
}

public class ExceptionDemo {
    public static void main(String[] args) {
        BankAccount acc = new BankAccount(5000);

        try {
            acc.withdraw(7000);  // throws InsufficientFundsException
        } catch (InsufficientFundsException e) {
            System.out.println("Error: " + e.getMessage());
            System.out.println("Deficit: " + e.getDeficit());
        } finally {
            System.out.println("Final balance: " + acc.getBalance());
        }

        // Chained exceptions
        try {
            readFile("data.txt");
        } catch (IOException e) {
            throw new RuntimeException("Failed to load data", e); // cause = e
        }
    }

    static void readFile(String path) throws IOException {
        throw new IOException("File not found: " + path);
    }
}

Best practices: (1) Catch the most specific exception first. (2) Never catch Exception generically unless re-throwing. (3) Never swallow exceptions with empty catch blocks. (4) Use custom exceptions for domain-specific errors. (5) Use try-with-resources for AutoCloseable resources. (6) The finally block runs even if a return statement is in try or catch.

Synchronization:

When multiple threads access shared data, race conditions can occur. synchronized ensures only one thread accesses the critical section at a time.

    public int getCount() { return count; }

    sharedData++;
}

Inter-Thread Communication:

Threads cooperate using wait(), notify(), and notifyAll() — all must be called from within a synchronized block/context.

class ProducerConsumer {
    private final Queue<Integer> queue = new LinkedList<>();
    private final int CAPACITY = 5;

    public synchronized void produce(int val) throws InterruptedException {
        while (queue.size() == CAPACITY) wait();  // wait if full
        queue.add(val);
        notifyAll();  // wake up waiting consumers
    }

    public synchronized int consume() throws InterruptedException {
        while (queue.isEmpty()) wait();  // wait if empty
        int val = queue.remove();
        notifyAll();  // wake up waiting producers
        return val;
    }
}

Key insight: Always use while loops (not if) with wait() to guard against spurious wakeups and re-check conditions after being notified.

Q: Explain the types of inheritance supported in C++ with a diagrammatic representation.

Q: Explain all types of inheritance in C++ in detail. Include single, multilevel, hierarchical, multiple, and hybrid inheritance with complete code examples for each.

Inheritance allows a class (derived) to acquire properties and behaviors from another class (base). C++ is unique in supporting all five types of inheritance.

1. Single Inheritance:

One base class, one derived class. The simplest form.

class Animal {

    string name;

    Animal(string n) : name(n) {}

A chain: A is base of B, B is base of C. C inherits from both B and A.

One base class, multiple derived classes.

Q: Explain polymorphism in detail. Cover compile-time (overloading) and runtime (overriding, virtual functions, dynamic binding) polymorphism with C++ examples. Also explain the virtual keyword, vtable, and why destructors should be virtual.

Polymorphism means "many forms." It allows a single interface to represent different underlying types. C++ supports two kinds:

1. Compile-Time (Static) Polymorphism — Function Overloading & Operator Overloading:

Resolved during compilation. The compiler determines which function to call based on the argument types.

class Printer {
public:
    void print(int x)       { cout << "Int: " << x << endl; }
    void print(double x)    { cout << "Double: " << x << endl; }
    void print(string s)    { cout << "String: " << s << endl; }
};

Printer p;
p.print(10);       // calls print(int)
p.print(3.14);     // calls print(double)
p.print("Hi");     // calls print(string)

2. Runtime (Dynamic) Polymorphism — Function Overriding with Virtual Functions:

Resolved during program execution. Achieved through inheritance and the virtual keyword. The correct function is chosen based on the actual object type, not the pointer/reference type.

class Shape {
public:
    virtual void draw() {  // virtual — enables overriding
        cout << "Drawing a shape\n";
    }
    virtual ~Shape() {}    // ALWAYS make destructor virtual
};

class Circle : public Shape {
public:
    void draw() override {  // overrides Shape::draw
        cout << "Drawing a circle\n";
    }
};

int main() {
    Shape* s = new Circle();  // upcasting
    s->draw();   // Output: "Drawing a circle" (runtime dispatch)
    delete s;    // calls Circle::~Circle() then Shape::~Shape()
}

How Virtual Functions Work (vtable):

When a class has virtual functions, the compiler creates a virtual table (vtable) — an array of function pointers. Each object of that class stores a hidden vptr pointer to the vtable. When a virtual function is called via a pointer/reference, the vtable entry is looked up at runtime.

Pure Virtual Functions & Abstract Classes:

class Shape {
public:
    virtual void draw() = 0;  // pure virtual
    virtual ~Shape() {}
};
// Shape is now abstract — cannot instantiate
// Derived classes MUST override draw()

Why Destructors Should Be Virtual:

If a base class pointer points to a derived object and delete is called, a non-virtual destructor causes only the base destructor to run. The derived portion is leaked. Making the destructor virtual ensures the full chain runs.

What Are Design Patterns?

Design patterns are reusable, proven solutions to commonly occurring software design problems. They are not finished code but templates that can be adapted. Originated from the "Gang of Four" (GoF) book. Categorized into Creational, Structural, and Behavioral patterns.

1. Singleton Pattern (Creational):

Ensures exactly one instance of a class exists and provides a global access point. Useful for logging, configuration, database connections, and thread pools.

// Thread-safe Singleton (C++11)
class DatabaseConnection {
private:
    static DatabaseConnection* instance;
    DatabaseConnection() { cout << "Connected\n"; }
    // Delete copy and move
    DatabaseConnection(const DatabaseConnection&) = delete;
    DatabaseConnection& operator=(const DatabaseConnection&) = delete;

public:
    static DatabaseConnection& getInstance() {
        static DatabaseConnection instance;  // lazy, thread-safe (C++11)
        return instance;
    }

    void query(string sql) { cout << "Executing: " << sql << endl; }
};

DatabaseConnection* DatabaseConnection::instance = nullptr;

// Usage
DatabaseConnection::getInstance().query("SELECT * FROM users");

Private constructor prevents external instantiation. Deleted copy constructor prevents cloning. static local variable in C++11 is initialized in a thread-safe manner (Meyers' Singleton).

2. Factory Pattern (Creational):

Creates objects without specifying their exact class. A factory method decides which class to instantiate based on input parameters.

// Product interface
class Shape {
public:
    virtual void draw() = 0;
    virtual ~Shape() {}
};

// Concrete products
class Circle : public Shape {
public: void draw() override { cout << "Drawing Circle\n"; }
};
class Square : public Shape {
public: void draw() override { cout << "Drawing Square\n"; }
};
class Triangle : public Shape {
public: void draw() override { cout << "Drawing Triangle\n"; }
};

// Factory
class ShapeFactory {
public:
    Shape* createShape(string type) {
        if (type == "circle")   return new Circle();
        if (type == "square")   return new Square();
        if (type == "triangle") return new Triangle();
        return nullptr;
    }
};

int main() {
    ShapeFactory factory;
    Shape* s = factory.createShape("circle");
    s->draw();  // Drawing Circle
    delete s;
}

Benefits: Decouples client code from concrete classes. Adding new shapes requires no changes to client code (Open/Closed Principle).

Abstraction:

Abstraction is the concept of hiding implementation details and showing only the essential features to the user. It reduces complexity by exposing only what is necessary. Achieved using abstract classes and interfaces.

// Abstraction — user only sees drive(), not how engine works
class Vehicle {
protected:
    int fuel;
public:
    Vehicle(int f) : fuel(f) {}
    virtual void drive() = 0;  // abstract — no implementation shown
    virtual void refuel(int amount) { fuel += amount; }
    virtual ~Vehicle() {}
};

class Car : public Vehicle {
public:
    Car(int f) : Vehicle(f) {}
    void drive() override {
        cout << "Car driving. Fuel: " << fuel << endl;
    }
};

// User interacts ONLY with the interface

v->drive();   // simple interface
v->refuel(20);

Encapsulation:

Encapsulation bundles data and the methods that operate on that data into a single unit (class) and restricts direct access using access specifiers. Data is hidden from outside access and can only be modified through controlled methods (getters/setters).

class BankAccount {
private:
    string accountNumber;  // hidden
    double balance;        // hidden

public:
    BankAccount(string acc, double bal)
        : accountNumber(acc), balance(bal) {}

    // Controlled access through methods
    double getBalance() const { return balance; }
    void deposit(double amount) {
        if (amount > 0) balance += amount;
    }
    bool withdraw(double amount) {
        if (amount > 0 && amount <= balance) {
            balance -= amount;
            return true;
        }
        return false;
    }
};

Data Hiding:

Data hiding is a subset of encapsulation. It specifically refers to making data members private so external code cannot access them directly. This prevents accidental or malicious modification.

class BoxInspector {
public:
    void inspect(Box& b) {

    }

Constructors and Encapsulation:

Constructors enforce encapsulation by ensuring objects are always created in a valid state. The object cannot exist without proper initialization. Destructors ensure resources are released properly, maintaining the integrity of the encapsulated resource management.

Q: Explain the JVM architecture in detail. Describe the role of class loader, bytecode verifier, JIT compiler, and garbage collector. Also explain how Java achieves platform independence.

JVM Architecture Overview:

The Java Virtual Machine (JVM) is the runtime engine that executes Java bytecode. It provides a layer of abstraction between the Java program and the underlying hardware/OS, enabling platform independence.

Components of JVM:

  • Class Loader Subsystem: Loads .class files into memory. Three built-in class loaders:
    • Bootstrap Class Loader: Loads core Java classes from rt.jar (e.g., java.lang). Written in native code.
    • Extension Class Loader: Loads classes from the jre/lib/ext directory.
    • Application Class Loader: Loads classes from the classpath (CLASSPATH).
    Loading follows three phases: Loading (read .class file), Linking (verify, prepare, resolve), and Initialization (assign static values).
  • Method Area (Metaspace): Stores class-level data — class name, fields, methods, static variables, and the constant pool.
  • Heap Memory: Stores all objects and arrays. Shared among all threads. Garbage collection happens here.
  • Stack Memory: Each thread gets its own stack. Stores frames for each method call with local variables, operand stack, and return address. LIFO structure.
  • PC Register: Program Counter — stores the address of the currently executing JVM instruction for each thread.
  • Native Method Stack: Supports native (non-Java) method calls.
  • Execution Engine: Contains:
    • Interpreter: Reads and executes bytecode line-by-line. Slower.
    • JIT (Just-In-Time) Compiler: Identifies "hot" (frequently executed) methods and compiles them to native machine code for faster subsequent execution.
    • Garbage Collector: Automatically reclaims memory from unreachable objects.
  • Java Native Interface (JNI): Allows Java code to call C/C++ libraries and vice versa.

How Java Achieves Platform Independence:

Java source code (.java) is compiled by the javac compiler into platform-independent bytecode (.class). This bytecode runs on any system with a JVM installed. Each platform has its own JVM implementation that interprets the same bytecode differently, converting it to the native machine code of that platform. This "write once, run anywhere" (WORA) principle is the core of Java's portability.

JIT Compilation:

The JIT compiler profiles running code and identifies methods that are called frequently ("hot spots"). It compiles these methods to native machine code, which is then cached. Subsequent calls use the compiled code directly, achieving near-native performance. Modern JVMs (like HotSpot) use tiered compilation: first interpret, then compile with C1 (client compiler), then recompile hot methods with C2 (server compiler) with aggressive optimizations.

Garbage Collection:

The GC automatically identifies objects that are no longer reachable (no live references). The most common algorithm is Mark and Sweep: the GC marks reachable objects starting from GC roots (stack variables, static fields), then sweeps away unmarked objects. Modern collectors like G1GC divide the heap into regions and collect incrementally, reducing pause times.

Operator Overloading:

Operator overloading gives special meaning to C++ operators when applied to user-defined types (classes/structs). It makes code more intuitive — c1 + c2 is clearer than c1.add(c2).

Rules:

  • Cannot create new operators — only overload existing ones.
  • Cannot change the number of operands (arity).
  • Cannot overload: ::, .*, ., ?:, sizeof.
  • At least one operand must be a user-defined type.
  • Cannot change operator precedence or associativity.

Member vs Friend Overloading:

this pointerYes (implicit left operand)No
Left operandMust be the class objectCan be any type

Complete Example — Complex Number Class:

#include <iostream>
using namespace std;

class Complex {
    float real, imag;
public:
    Complex(float r = 0, float i = 0) : real(r), imag(i) {}

    // 1. Binary operator overloading (MEMBER)
    // Adds another Complex to this one
    Complex operator+(const Complex& c) const {
        return Complex(real + c.real, imag + c.imag);
    }

    // 2. Prefix increment (MEMBER)
    Complex& operator++() {
        real++;           // increment real part
        return *this;     // return reference to modified object
    }

    // 3. Postfix increment (MEMBER)
    // Note: the int parameter is a DUMMY to distinguish from prefix
    Complex operator++(int) {
        Complex temp = *this;  // save current state
        real++;                // modify
        return temp;           // return OLD value
    }

    // 4. Subscript operator for accessing real(0) or imag(1)
    float operator[](int index) const {
        return (index == 0) ? real : imag;
    }
    float& operator[](int index) {
        return (index == 0) ? real : imag;  // non-const for assignment
    }

    // 5. Stream insertion — must be FRIEND (left operand is ostream)
    friend ostream& operator<<(ostream& out, const Complex& c) {
        out << c.real;
        if (c.imag >= 0) out << " + " << c.imag << "i";
        else out << " - " << -c.imag << "i";
        return out;
    }

    // 6. Stream extraction — FRIEND
    friend istream& operator>>(istream& in, Complex& c) {
        in >> c.real >> c.imag;
        return in;
    }
};

int main() {
    Complex a(2, 3), b(1, -4);

    // Binary operator
    Complex sum = a + b;           // calls a.operator+(b)
    cout << sum;                   // 3 - 1i

    // Prefix vs Postfix
    cout << ++a;                   // 3 + 3i  (increments first)
    cout << b++;                   // 1 + -4i (returns old, then increments)

    // Subscript
    cout << a[0];                  // 4 (real part)
    a[1] = 10;                      // set imaginary part
    cout << a[1];                  // 10

    // Stream operators
    Complex c;
    cin >> c;                      // user enters: 5 6
    cout << c;                     // 5 + 6i
}

Special Notes:

  • Prefix ++ returns Complex& (reference to modified object).
  • Postfix ++ returns Complex (copy of old value). The int parameter is not used — it only differentiates the signature.
  • Assignment operator (=) should return *this by reference to support chaining: a = b = c;
  • Overloading << and >> as friends is essential because the left operand (ostream/istream) is not a Complex object.

Q: Explain run-time polymorphism and dynamic method dispatch in Java. Cover method overriding, the super keyword, type casting, and how the JVM resolves method calls at runtime. Include a comprehensive example demonstrating upcasting and downcasting.

Runtime Polymorphism:

Runtime polymorphism (also called dynamic method dispatch) is the mechanism by which a call to an overridden method is resolved at runtime rather than compile time. It allows a parent class reference to invoke the overridden method of a child class object.

Key Conditions:

  • Method overriding (same method signature in parent and child).
  • A parent reference pointing to a child object (upcasting).
  • The method must be non-static, non-private, and non-final.
  • The method should not be static (static methods are resolved at compile time).

Comprehensive Example:

class Animal {
    String name;

    Animal(String name) { this.name = name; }

    void sound() {
        System.out.println(name + " makes a sound");
    }

    void eat() {
        System.out.println(name + " is eating");
    }
}

class Dog extends Animal {
    String breed;

    Dog(String name, String breed) {
        super(name);       // call parent constructor
        this.breed = breed;
    }

    // Override sound()
    @Override
    void sound() {
        System.out.println(name + " (" + breed + ") barks: Woof!");
    }

    // Dog-specific method
    void fetch() {
        System.out.println(name + " is fetching the ball");
    }
}

class Cat extends Animal {
    Cat(String name) { super(name); }

    @Override
    void sound() {
        System.out.println(name + " meows: Meow!");
    }
}

public class RuntimePolymorphismDemo {
    public static void main(String[] args) {
        // UPCASTING — parent reference, child object
        Animal a1 = new Dog("Buddy", "Golden Retriever");
        Animal a2 = new Cat("Whiskers");

        // Calls resolved at RUNTIME based on actual object type
        a1.sound();  // "Buddy (Golden Retriever) barks: Woof!"
        a2.sound();  // "Whiskers meows: Meow!"

        // Both can call parent methods
        a1.eat();    // "Buddy is eating"
        a2.eat();    // "Whiskers is eating"

        // a1.fetch();  // COMPILE ERROR — Animal reference doesn't see fetch()

        // DOWNCASTING — cast back to child to access child-specific methods
        Dog d = (Dog) a1;   // safe — a1 actually IS a Dog
        d.fetch();           // "Buddy is fetching the ball"

        // Risky downcast — will throw ClassCastException at runtime
        // Dog d2 = (Dog) a2;  // a2 is a Cat, not a Dog
    }
}

The super Keyword:

super has two uses:

  • super(): Calls the parent class constructor. Must be the first statement in the child constructor. If omitted, Java calls the default parent constructor automatically.
  • super.method(): Calls the parent's version of an overridden method from within the child class.
class Person {
    String name;
    Person(String name) { this.name = name; }
    void introduce() { System.out.println("I'm " + name); }
}

class Student extends Person {
    int roll;
    Student(String name, int roll) {
        super(name);       // must be first statement
        this.roll = roll;
    }

    @Override
    void introduce() {
        super.introduce();   // call parent version
        System.out.println("My roll number is " + roll);
    }
}

How JVM Resolves Overridden Calls:

Every non-abstract class in Java has a virtual method table (vtable). When a method is overridden, the child's vtable entry replaces the parent's entry. When a virtual method is called via a reference, the JVM looks up the actual object's vtable to find the correct implementation — this is the virtual method invocation.

Type Casting:

  • Upcasting (implicit): Child → Parent. Always safe. Dog d = new Dog(); Animal a = d;
  • Downcasting (explicit): Parent → Child. Risky without instanceof check.
  • Use instanceof to safely downcast:
Animal a = new Dog("Rex", "Labrador");
if (a instanceof Dog) {
    Dog d = (Dog) a;       // safe — we verified the type
    d.fetch();
}
