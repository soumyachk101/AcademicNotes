1

Describe the two basic operations on a semaphore. Explain whether any integer variable with similar operations can act as a semaphore or not. What is a race condition? Explain Peterson's solution to avoiding a race condition. What are the conditions for a solution to the mutual exclusion problem? Mention the conditions for achieving mutual exclusion.

Semaphore (Dijkstra, 1965): a non-negative integer on which only two atomic operations are defined — the classical names are V() (release) and P() (acquire), modern names signal() and wait().

typedef struct { int value; ... } semaphore;

P(S) / wait(S)        V(S) / signal(S)
-------------------   -------------------
while (S.value <= 0)  S.value++;
  ; /* no-op spin */  /* wake one process blocked in wait, if any */
S.value--;

P (probeit) decrements and, if the value goes negative, blocks the calling process; V (vor) increments and wakes one blocked waiter. The whole test-and-decrement / test-and-increment must be atomic — no interrupt may arrive between the read of value and its update.

Can an ordinary integer work? No. A plain C int implements a non-atomic read-modify-write: with two processes, P1 may read S=1, P2 reads S=1 before P1 writes, both write S=0 — two processes entered the critical section although only one should have. The operation must be indivisible at the hardware level (atomic exchange / test-and-set, or disabling interrupts in kernel mode).

Race condition: the final result depends on the relative, unpredictable timing (interleaving) of concurrently executing processes — a non-deterministic bug, e.g. two threads reading, modifying and writing a shared counter and losing an update.

Peterson's solution (two processes, shared flag array and turn; read-modify-write of one shared variable is atomic on most real hardware — Dijkstra's "atomicity assumption"):

// Process Pi
do {
  flag[i] = true;
  turn = j;                       // let the OTHER process go first
  while (flag[j] && turn == j)    // yield: spin while j wants in AND j's turn
    ;                             // busy wait
  /* critical section */
  flag[i] = false;               // announce exit
  /* remainder section */
} while (true);

Mutual exclusion: if both are at the test and turn = j, Pi spins because turn == j; Pj passes. The invariant "at most one in the CS" holds. Progress (turn-taking): after Pi exits (flag[i]=false), Pj sees it and proceeds; if Pj is in its remainder section while Pi retries, Pi passes since flag[j] is false. A third condition, bounded waiting, also holds: a process waits only one turn. Extension to N processes: two locks sharing a counter (a lock per pair of processes), or a shared entry array scanned before entering.

Conditions for a correct mutual-exclusion solution: (1) Mutual exclusion — never two in the CS; (2) Progress — if no process is in the CS and some wish to enter, only those outside the CS may decide who enters next, and the decision is not postponed forever; (3) Bounded waiting — a bound exists on how long other processes may enter after a request. (A practical fourth: the algorithm must not depend on relative speeds or timing.)

2

What is the critical section problem? What are the requirements that must be met by a solution to the critical section problem? Explain the race condition in the context of process synchronization. What is a mutex? How are semaphores used to solve the critical section problem?

Critical section problem: every process has a code segment that accesses shared data (the critical section, or CS); the problem is to design an algorithm so that whenever several processes execute CS code, at most one is in its CS at any instant. The part after the CS is the remainder section.

Requirements for a solution (three classical, one practical):

  1. Mutual exclusion: no two processes are simultaneously in their critical sections.
  2. Progress: if no process is executing in its CS and one or more wish to enter, only processes outside their CS can take part in deciding which enters next, and that decision cannot be postponed indefinitely.
  3. Bounded waiting: there is a finite upper bound on the number of times other processes can enter their CS after a process has requested to enter and before that request is granted.
  4. (Practical) No timing assumption: correctness must not depend on relative speeds of processors or on absolute timing; and no process may be permanently denied (no starvation).

Race condition in synchronization: the outcome of the program depends on the relative timing of concurrently running processes. Example: counter++ compiled as temp = counter; temp = temp+1; counter = temp; — if P1 and P2 read counter=7 before either writes, the result is 8 instead of 9. Two concurrent executions that share a memory location (a shared variable) "race" to reach the correct write; the fix is a mutual-exclusion protocol around the shared code.

Mutex: a mutual-exclusion lock — a binary semaphore with value in {0, 1}, whose only purpose is to serialize entry to a CS: one process acquires it (P(lock)), the rest block; the holder releases it on exit (V(lock)). It is the canonical primitive of locking.

Semaphores solve the CS problem by pairing a mutex with each shared resource:

semaphore mutex = 1;            // binary, one per resource

void main() {
  P(mutex);
  /* critical section */
  V(mutex);
  /* remainder section */
}

Because P and V are atomic hardware primitives, two processes cannot both pass the P(mutex) when the value is 1: the first decrements it to 0, the second sees 0 and blocks. Mutual exclusion holds; exactly one blocked process is woken on each V; progress and bounded waiting are satisfied by the kernel's wake-up discipline (the scheduler guarantees no process blocks forever — the wake-up queue is FIFO on most kernels, giving bounded waiting).

What are the operations on a semaphore? What is a semaphore? What is the problem with these operations if they follow the classical definition? What is the possible remedy to the above problem? Write Peterson's algorithm for the two-process critical section problem.

Semaphore: a synchronization primitive introduced by Dijkstra — an integer variable S ≥ 0 with only two atomic operations:

P(S) / wait(S)          V(S) / signal(S)
-------------------      -------------------
while (S.value <= 0)     S.value++;
  ; /* busy wait */      /* wake one waiting process if any */
S.value--;

P = probe/test ("wait to acquire"), V = release ("signal to release"). Both are indivisible at the hardware level.

Problem with the classical definition: the classical P is written as a busy-wait (spin) loop — while (S.value <= 0) ;. Two serious defects: (i) Wasted CPU time — the blocked process occupies a CPU and burns cycles doing nothing; on a uniprocessor this is fatal, because a preempted spinning process will never get another chance to retest while the process it is waiting for is the one running the CPU. (ii) Priority inversion — a low-priority process spins while a high-priority process it would unblock is starved of the CPU. The classical test-then-decrement is also non-atomic if implemented with ordinary load/store instructions, which is exactly the race condition we are trying to remove.

Remedy: (a) Hardware support for atomicity. Modern CPUs provide an atomic test-and-set (exchange) instruction: TA&S(loc) { temp = *loc; *loc = 1; return temp; } executed as a single instruction; the CS becomes while (TA&S(lock)); followed by *lock = 0;. Or an atomic swap / compare-and-swap instruction. (b) Kernel sleep instead of spin. When P finds S ≤ 0, the kernel blocks the process on the semaphore's waitQ and the CPU is released to other work; V moves one waiting process to the ready queue. This removes the wasted-CPU defect.

Peterson's algorithm — two processes, shared int turn; and bool flag[2]; (initially turn = 0, flag[0] = flag[1] = false; each read-modify-write of a single shared variable is assumed atomic, Dijkstra's assumption):

// Process Pi, with j = 1 - i
do {
  flag[i] = true;
  turn = j;                       // "please go first"
  while (flag[j] && turn == j)
    ; /* yield — busy wait */
  /* critical section */
  flag[i] = false;               // announce departure
  /* remainder section */
} while (true);

Mutual exclusion is proved by contradiction: suppose both are in the CS. Pi can be in it only because when it last tested, flag[j] was false or turn was i. Pj can be in it only by the symmetric condition. But the last write to turn set it to one value; say turn = j. Then Pi passes only if flag[j] was false; Pj, being in the CS, has already set flag[j] = true — contradiction. Progress: the last process to arrive sets turn to the other's index, so the other enters. Bounded waiting: a process waits at most one other's turn. N-process extension: one lock array per pair of processes, entry guarded by the two locks that include process i; or a single shared turn pointer combined with per-process flag bits scanned in order.

State the producer-consumer problem. Give a solution to the producer-consumer problem, using a semaphore. Justify that your solution guarantees mutual exclusion. What is message passing? What are event counters?

Producer-consumer (bounded buffer) problem: N producer processes generate data and deposit it into a shared fixed-size buffer; M consumer processes remove data and process it. The buffer cannot overflow (full → producer must wait) or underflow (empty → consumer must wait), and the buffer must be accessed by at most one process at a time.

Semaphore solution (three semaphores: full counts the number of used slots, empty counts the number of free slots, mutex is the buffer lock):

semaphore empty = N;   // N free slots at start
semaphore full  = 0;   // no data in the buffer
semaphore mutex = 1;   // one at a time in the buffer

// Producer
do {
  item = produce();
  P(empty);            // wait for a free slot
  P(mutex);            // exclusive buffer access
  insert(item);
  V(mutex);            // release the buffer
  V(full);             // announce a data item
} while (true);

// Consumer
do {
  P(full);             // wait for a data item
  P(mutex);            // exclusive buffer access
  item = remove();
  V(mutex);
  V(empty);            // announce a free slot
  consume(item);
} while (true);

Why mutual exclusion holds: the pair P(mutex); … V(mutex) is serialized by a binary semaphore; no two processes can both hold mutex. Moreover the invariants full + empty = N always and 0 ≤ full ≤ N hold in every reachable state. Suppose a producer is in the critical region: it holds mutex; the number of free slots it sees is empty, which is at least 1 because it just performed P(empty) successfully. A simultaneous consumer would need full ≥ 1 AND mutex. But while the producer is between V(mutex) and V(full), it holds neither, so the invariant is not broken; the only way to break mutual exclusion would be for both to hold mutex at once, which the binary semaphore forbids. Hence at most one process accesses the buffer at a time.

Message passing: an inter-process communication model in which processes exchange data by send(destination, message) and receive(source, &message) system calls, with no shared memory. The message is a copy; the kernel handles routing and buffering. It contrasts with shared-memory synchronization (semaphores, locks, monitors). Two variants exist: synchronous send blocks until the receiver reads the message; asynchronous send returns immediately and the message is queued. The receiver can specify a source set and/or a message-type predicate to select which messages to match — this is the mechanism by which processes coordinate without sharing memory.

Event counters (Dijkstra): a semaphore specialized to count occurrences of a completed event. The counter starts at 0 and only goes up when the event occurs; a process calls P(e) to wait for the nth occurrence. Unlike a general counting semaphore, an event counter never goes negative because it is incremented exactly once per event and decremented once per wait. In producer-consumer, full and empty are event counters: full counts "an item has been inserted"; empty counts "a slot is free". They are used to order events (consumer must wait for producer to finish inserting before removing), not to exclude simultaneous access to a shared variable, which is what the mutex does.

What is the Readers-Writers problem? How to implement a solution to the Readers-Writers problem with the use of semaphores? What is the bounded buffer problem? Explain with the solution. Differentiate between binary and counting semaphore. What is the advantage of using a counting semaphore than a binary semaphore?

Readers-Writers problem: a shared data object (a database file, a table) is accessed by readers (which only read, many can be inside at the same time) and writers (which write, only one can be inside, and no reader may be inside while a writer writes). Three policies: first problem — no starvation, fair between readers and writers; second problem — reader-preferred: no reader waits while any reader is active; third problem — writer-preferred: once a writer requests access, no subsequent reader may enter.

Reader-preferring (second problem) — readers share; writers are exclusive:

semaphore mutex = 1;   // protects counter
int readCount = 0;     // readers currently in the CS
semaphore RWlock = 1;  // exclusive for writers

// Reader
P(mutex);
readCount++;
if (readCount == 1)
  P(RWlock);           // first reader locks the whole object
V(mutex);

/* read the shared object */

P(mutex);
readCount--;
if (readCount == 0)
  V(RWlock);           // last reader releases the lock
V(mutex);

// Writer
P(RWlock);
/* write */
V(RWlock);

This is reader-preferred: readers that arrive after the first reader do not wait (they increment readCount and proceed without touching RWlock). A writer may be starved if readers keep arriving — the second problem accepts that.

Writer-preferred (third problem) — one extra semaphore writeCount:

semaphore RWlock = 1, writeGate = 0, mutex = 1;
int writeCount = 0;   // writers waiting (protected by mutex)
int readCount  = 0;   // readers in the object (protected by mutex)

// Reader
P(mutex);
if (writeCount > 0) { V(mutex); P(writeGate); P(mutex); }
readCount++;
if (readCount == 1) P(RWlock);       // first reader locks the object
V(mutex);
/* read */
P(mutex);
readCount--;
if (readCount == 0) {
  V(RWlock);
  if (writeCount > 0) V(writeGate);  // let the next waiting writer in
}
V(mutex);

// Writer
P(mutex);  writeCount++;  V(mutex);
if (writeCount > 1) P(writeGate);    // queue behind earlier writers
P(RWlock);
/* write */
V(RWlock);
P(mutex);
writeCount--;
if (writeCount > 0) V(writeGate);    // release the next queued writer
V(mutex);

Because a reader blocks on writeGate whenever writeCount > 0, once any writer arrives it gets the object before subsequent readers — writer preference without starving writers, while readers that arrive when no writer is waiting proceed without waiting.

Bounded buffer problem: N producers write items to a fixed-size array of N slots; M consumers read them. A producer must wait when the buffer is full; a consumer must wait when it is empty; only one process accesses the buffer at a time.

Solution (three semaphores):

semaphore empty = N;   // N free slots
semaphore full  = 0;   // no items yet
semaphore mutex = 1;   // exclusive buffer access

// Producer
P(empty);  P(mutex);  insert();  V(mutex);  V(full);
// Consumer
P(full);   P(mutex);  remove();  V(mutex);  V(empty);

Binary vs counting semaphore:

AspectBinary semaphoreCounting semaphore
Value range{0, 1} — a lock0 … N — a counter
PurposeMutual exclusion on a shared resourceLimits concurrent access; counts resources or events
ExampleLock on the shared buffer (mutex)full, empty in bounded buffer; count of free device instances

Advantage of a counting semaphore: a counting semaphore expresses "at most k may be inside at once" in one line — semaphore S = k; with P(S)/V(S) around the shared region. Modeling "at most 5 processes" with five separate binary semaphores and a mutex that assigns one of them requires a table plus a lock; the counting semaphore does it in one primitive. It also carries a quantitative state (the number of waiting processes is the value itself), which a binary semaphore cannot. This makes counting semaphores the natural choice for bounded buffers, device pools, and event counters.

What is the Dining Philosophers problem? How can a semaphore be used for the Dining Philosophers problem? How does synchronization and scheduling go hand in hand? What are the problems of busy-wait implementation of a semaphore? Explain how it is solved.

Dining Philosophers problem: five philosophers sit around a circular table with one fork between each pair; to eat, a philosopher must pick up both the left and right fork. The problem is to design an algorithm that prevents deadlock — all five holding one fork each and waiting forever for the other.

Classic 5-fork solution (one semaphore per fork):

semaphore fork[5] = {1,1,1,1,1};  // one per fork

// Philosopher i (forks i and (i+1)%5)
do {
  P(fork[i]);
  P(fork[(i + 1) % 5]);
  /* eat */
  V(fork[i]);
  V(fork[(i + 1) % 5]);
  /* think */
} while (true);

This solution deadlocks if all five simultaneously pick up their left fork: the circular wait is formed (P1 holds fork 1, wants fork 2; … P5 holds fork 5, wants fork 1).

Deadlock-breaking solutions:

  1. Asymmetric pickup: philosopher 4 picks up the right fork first, others the left. At least one philosopher breaks the circular chain — mutual exclusion and progress are preserved by the ordering asymmetry.
  2. Resource hierarchy: number the forks 1–5; every philosopher picks up the lower-numbered fork first. A cycle is impossible because the fork numbers around the loop would have to strictly increase and then decrease — this is the classic Coffman prevention of circular wait.
  3. Waiter semaphore: only 4 of 5 may sit at a time — semaphore in = 4; each does P(in) before the first fork, V(in) after both. With 4 seated, the 5th fork is always free — the circular-wait condition cannot form.

Synchronization and scheduling go hand in hand: synchronization is the protocol that decides which process may use which resource; scheduling is the mechanism by which the OS picks which ready process runs. A process blocked on a semaphore goes to its waitQ and the CPU goes to another ready process; a signal() moves one waiter to the ready queue. The two must stay consistent on what "blocked" and "ready" mean: a fork-holder that is preempted is still a holder, and a woken process that is preempted again must still be counted as waiting.

Problems of busy-wait (spin-wait) semaphores:

  1. CPU waste: a process calling P(S) with S = 0 spins in a tight loop doing no useful work — on a multiprocessor it idles one core; on a uniprocessor it is catastrophic, since the spinner occupies the CPU while the process that must call V(S) is starved of it.
  2. Priority inversion: a low-priority spinner occupies the CPU; a high-priority process that must call V(S) to make progress is starved, because the spinner is not being preempted. The OS must preempt the spinner to let the woken process run — defeating the purpose of the spin.

Solution — kernel sleep (waitQ): when P(S) finds S ≤ 0, the kernel blocks the process on the semaphore's waitQ and gives the CPU to another ready process; when V(S) is called and waitQ is non-empty, the kernel moves one process from waitQ to the ready queue. No CPU cycles are wasted. The cost is a context switch on every P that blocks — expensive for a lock held only briefly — so spin locks are still preferred for very short critical sections on multiprocessors.

Explain how the use of monitors guarantee mutual exclusion?

Monitor (Hoare, 1974): a language-level module in which all shared data and the procedures that access it live, and in which the compiler enforces that at most one process is inside the monitor at any time. The monitor is a record with a set of procedures; entry is serialized by the monitor's intrinsic mutual-exclusion protocol — the compiler inserts a lock at the top of every monitor procedure and releases it on exit.

monitor database {
  int read_count = 0, write_count = 0;
  condition can_read, can_write;

  procedure read() {
    read_count++;
    if (write_count > 0)
      wait(can_read);     // a writer is active or waiting — yield
  }

  procedure end_read() {
    read_count--;
    if (read_count == 0 && write_count > 0)
      signal(can_write);  // last reader gone — wake a waiting writer
  }

  procedure write() {
    write_count++;
    if (write_count > 1 || read_count > 0)
      wait(can_write);    // wait for exclusive access
  }

  procedure end_write() {
    write_count--;
    if (write_count == 0)
      signal(can_read);   // no writer left — wake waiting readers
    else
      signal(can_write);  // pass the turn to the next writer
  }
}

How mutual exclusion is guaranteed: (i) Intrinsic lock — the monitor is entered through exactly one procedure; the compiler inserts a binary lock at the entry of each procedure and releases it on every exit path. Two processes cannot both be inside the monitor body at once — this is the guarantee of mutual exclusion. (ii) Condition variables — a condition c has two operations: wait(c) releases the monitor's lock, blocks the calling process on c's queue, and re-acquires the lock when the process is woken; signal(c) moves one waiting process from c's queue to the ready state. Because only the lock-holder may call wait/signal, and because a process inside wait(c) holds no part of the invariant it protects, the monitor's data invariant (here: "at most one writer active, and no writer while read_count > 0") remains true on entry and on every exit — no process can observe or corrupt it mid-step. (iii) No busy-wait — blocking is done by the kernel on the condition's queue, so the CPU is not wasted on spinning, unlike a classical semaphore.

Contrast with semaphores: semaphores are low-level — the programmer must get the P/V ordering right; a misplaced V before a P can corrupt state. Monitors are high-level — the compiler serializes entry and exit, and condition variables replace the waitQ + mutex dance with two clean operations wait(c) and signal(c). The monitor encapsulates the shared data and its synchronization protocol, making it a safe data structure in the language sense. The main cost: a monitor is a language construct, so it must be supported by the compiler and the OS; semaphores are a hardware/kernel primitive, so they are always available.

What is deadlock? What is starvation? Give the difference between deadlock and starvation. Explain Banker's algorithm. Show how it is helpful to overcome deadlock. "All unsafe states may not lead to deadlock" - why or why not? Describe the necessary and sufficient conditions for the occurrence of deadlock.

Deadlock: a set of processes is deadlocked if each process in the set is waiting for an event that only another process in the same set can cause; none can make progress. The four Coffman conditions must all hold:

  1. Mutual exclusion — at least one resource is non-shareable.
  2. Hold and wait — a process holds at least one resource while waiting for another.
  3. No preemption — a resource can be released only voluntarily by the holder.
  4. Circular wait — a closed chain of processes exists, each waiting for a resource held by the next.

Starvation: a process is indefinitely delayed — it waits forever for a resource that is perpetually granted to others. Starvation needs no closed loop; it is an unfairness in the scheduling/allocation policy.

AspectDeadlockStarvation
StateClosed circular wait among the setNo closed loop; one process is always delayed
CauseResource-allocation cycleScheduling/priority policy (unfairness)
RecoveryTerminate / preempt / roll backChange the priority policy; add a fairness bound

Banker's algorithm (Dijkstra, 1965) is a deadlock-avoidance algorithm. Each process declares its maximum claim per resource type before it starts. A request is granted only if the resulting state is safe — i.e. a safe sequence P1, …, Pn exists such that for each k, Pk's remaining need ≤ (available + resources held by P1 … Pk−1). If no such sequence exists the state is unsafe and the request is refused.

How it helps overcome deadlock: by confining the system to safe states — and since every deadlock is an unsafe state — no deadlock can ever be reached: it is avoidance, checked at every allocation.

Worked example. Five processes, three resource types A(10), B(5), C(7) — 22 instances total. Initial state:

Allocation (A B C)Max (A B C)Need = Max − Alloc (A B C)
P00 1 07 5 37 4 3
P12 0 03 2 21 2 2
P23 0 29 0 26 0 0
P32 1 12 2 20 1 1
P40 0 24 3 34 3 1

Available = (3, 3, 2). Find a safe sequence. P1: need (1,2,2) ≤ avail (3,3,2)? Yes. P1 finishes: avail ← (3,3,2) + (2,0,0) = (5,3,2). P3: need (0,1,1) ≤ (5,3,2)? Yes. avail ← (5,3,2) + (2,1,1) = (7,4,3). P4: need (4,3,1) ≤ (7,4,3)? Yes. avail ← (7,4,3) + (0,0,2) = (7,4,5). P0: need (7,4,3) ≤ (7,4,5)? Yes. avail ← (7,4,5) + (0,1,0) = (7,5,5). P2: need (6,0,0) ≤ (7,5,5)? Yes. Safe sequence ⟨P1, P3, P4, P0, P2⟩ — the state is safe.

Now test an unsafe request. P0 requests (0, 0, 2): P0's need is (7,4,3), so the request is valid (0 ≤ 7, 0 ≤ 4, 2 ≤ 3). Simulate the grant: P0's allocation becomes (0,1,2), and Available ← (3,3,2) − (0,0,2) = (3,3,0). Search for a safe sequence: P1 needs 2 C but 0 available; P3 needs 1 C; P4 needs 1 C and 4 A; P0 needs 4 C; P2 needs 6 A but only 3 available. No process can finish — the state is unsafe, so the request must be refused and P0 must wait until some process releases resources.

"All unsafe states may not lead to deadlock" — why? An unsafe state is one in which no safe sequence exists for the current allocation. But a process may still release resources and exit; a safe state may be reachable by a future release. Deadlock requires that no process in the circular-wait set can ever proceed — an unsafe state is necessary but not sufficient for deadlock. The system may enter an unsafe state and still recover.

Necessary and sufficient condition for deadlock: a deadlock occurs if and only if the resource-allocation graph contains a cycle and every resource type in that cycle is single-instance (at most one instance per type, so no free instance can break the loop). The four Coffman conditions are the necessary ones; the cycle criterion is the sufficient one.

2

Critically comment on the following topic: A cycle in a resource allocation graph does not always imply the occurrence of deadlock. What is the optimistic assumption made in the deadlock detection algorithm? How can this assumption be violated?

Resource Allocation Graph (RAG): a directed graph with two kinds of vertices: processes (circles) and resource types (squares, with one dot per available instance). A request edge P → R means P is waiting for an instance of R; an assignment edge R → P means P currently holds an instance. The key theorem:

Single-instance resource types: if the system has at most one instance per resource type, then a cycle in the RAG is both necessary and sufficient for deadlock. Necessity: deadlock requires circular wait, and circular wait is exactly a cycle in the RAG. Sufficiency: if every resource in the cycle has exactly one instance and each process in the cycle is waiting for the instance held by the next, no process in the cycle can ever be released, so the cycle is a permanent deadlock.

Multi-instance resource types: if a resource type has more than one instance, a cycle is necessary but not sufficient for deadlock. A cycle may exist while a process in the cycle still has access to enough instances of every resource it needs (because it is not the only one waiting for that type). The process can complete and release its resources, breaking the cycle. A cycle in a multi-instance RAG may be resolved; it is not a proof of deadlock. To detect deadlock in a multi-instance system, one must use a deadlock-detection algorithm (e.g. a wait-kill graph or the resource allocation cycle search) that walks the request-and-hold relationships across all instances.

Optimistic assumption in the detection algorithm: the algorithm assumes that the system will eventually reach a safe state — that is, every process will eventually release the resources it holds, so the detection algorithm can find a deadlock-free schedule. In other words, the detection algorithm assumes that no process will hold a resource indefinitely (no indefinite hold, no livelock). This is the optimism of the detection approach: it does not prevent a process from acquiring a resource and then never releasing it; it only detects the deadlock after it has formed.

How the assumption is violated: (i) A bug in the user program: a process may have a coding error that causes it to hold a resource forever without ever releasing it. The detection algorithm sees the cycle and reports deadlock, but the "deadlock" is actually a bug — the process is not waiting for another process; it is simply broken. (ii) Livelock: two or more processes may constantly change state in response to each other, making no progress. A polite-diners example: two people in a narrow hallway each step to the right to let the other pass, but they both step right at the same time, then both step left, and so on, in an endless synchronized cycle. No process is blocked; no process makes progress. A detection algorithm that looks for a cycle in the waiting graph will not find one — the processes are not waiting on each other in a closed loop; they are actively changing state. The livelock is not a deadlock, but it has the same observable effect: no progress. (iii) Priority inversion: a high-priority process may be blocked by a low-priority process that holds a resource; the high-priority process can never run to release its own resources, so the system appears deadlocked. The detection algorithm may flag it as a deadlock, but the root cause is the scheduling policy, not a circular wait.

With an example, describe if resources are not properly allocated to the processes it may lead from a safe state to an unsafe state. Available: A = 3 − 2 = 1, B = 3 − 3 = 0. Safe sequence: P0 needs (1,0) ≤ avail (1,0) → P0 completes, releasing its 2 A → avail (3,0). P2 needs (2,0) ≤ (3,0) → P2 completes, releasing its 1 B → avail (3,1). P1 needs (0,1) ≤ (3,1) → P1 completes. ⟨P0, P2, P1⟩ — the system is in a safe state.

Now P2 requests 1 instance of A (it already holds 1 B; after the request it holds 1 A + 1 B, still below its max of 2 A). Granting it leaves Available = A: 0, B: 0, and P2's remaining need is (1,0). No process can complete: P0 and P2 each need 1 A but none is available, and P1 needs 1 B while all 3 B are held. The state is unsafe — in fact a deadlock, since P0 waits for the A held by P2, P2 waits for the A held by P0, and P1 waits for B held by P2. The Banker's algorithm, simulating the grant, finds no safe sequence and refuses the request; P2 waits, and the system stays safe. The same request granted without checking takes the system from a safe state to an unsafe one.

Linear ordering prevents circular wait. Assign to every resource type a strict total order R1 < R2 < … < Rn; each process may request resources only in increasing index order, and a request is granted only if the resource's index exceeds the index of every resource the process currently holds.

Proof: suppose a circular wait exists: Pi waits for ri, which Pi+1 holds. By the ordering rule, Pi may request ri only if index(ri) exceeds the index of every resource Pi holds; and Pi+1 may request ri+1 only if index(ri+1) > index(ri) (since Pi+1 holds ri). Going once around the loop gives index(rn) > index(rn−1) > … > index(r1) > index(rn) — a contradiction, since a strict total order cannot cycle. Hence no circuit can form in the RAG; circular wait is broken and deadlock is impossible. ∎

Methods for handling deadlock:

  1. Prevention — break one or more of the four Coffman conditions: make the resource shareable (mutual exclusion); require all resources to be requested and allocated at once (hold-and-wait); allow the OS to forcibly take a resource (no-preemption); impose a linear ordering on resource requests (circular wait).
  2. Avoidance — dynamically check the state before each grant and refuse requests that would make it unsafe (Banker's algorithm); the system stays in the safe region.
  3. Detection and recovery — allow deadlock to occur, periodically find a cycle in the RAG / wait-for graph, then recover by terminating processes, preempting resources, or rolling back to checkpoints.
  4. Ignore the problem (treatment) — the OS takes no action; the application detects deadlock (e.g. by timeouts) and kills the process. This is the approach of most real operating systems (UNIX, Linux, Windows).

State four necessary conditions for deadlocks. Explain circular wait for the occurrence of deadlock and how it can be prevented. What is livelock? List down the methods of deadlock detection and deadlock avoidance. Explain how deadlock can be recovered through deadlock.

Four Coffman necessary conditions for deadlock: (1) Mutual exclusion — at least one resource is non-shareable; (2) Hold and wait — a process holds at least one resource and waits for another; (3) No preemption — a resource can only be released by the holder; (4) Circular wait — a closed chain of processes exists such that each waits for a resource held by the next.

Circular wait: the most directly exploitable condition for prevention — a closed loop P1 → P2 → … → Pn → P1 in which Pi waits for a resource held by Pi+1. Prevention methods that break circular wait: (a) Linear ordering — assign a total order to resource types; each process requests resources only in increasing index order, which makes a cycle impossible. (b) All-or-nothing allocation — a process requests all the resources it will need before it starts; the OS allocates them all at once or makes the process wait, breaking hold-and-wait (which in turn destroys circular wait). (c) Resource hierarchy — a process may request only types of lower index than any it holds, the same argument as (a).

Livelock: a set of processes is constantly changing state in response to each other but making no progress. The classic polite-diners example: two people in a narrow hallway each step right to let the other pass, then both step left, endlessly. No process is blocked, but none makes progress. Livelock is not deadlock: in deadlock the processes are blocked (waiting); in livelock they are active (changing state). It is also not starvation: in starvation a single process is indefinitely delayed; in livelock all processes are actively moving, yet no progress is made.

Methods of deadlock detection: (i) RAG cycle detection — for single-instance resources, a cycle in the resource allocation graph is a deadlock; search with DFS. (ii) Wait-for graph — for multi-instance resources, an edge P → Q means P waits for a resource that Q holds; a cycle is a deadlock. (iii) Timeouts — each process sets a timer; if it fires before the resource is acquired, a deadlock is assumed (simple, but a slow process may be falsely flagged). (iv) Wait-kill graph — encodes "P waits for Q, so kill Q"; the algorithm finds a minimal set of processes to kill to break the deadlock.

Methods of deadlock avoidance: (i) Banker's algorithm — the process declares its maximum claim; a request is granted only if the resulting state is safe. (ii) Restricted allocation — the OS restricts how many processes may be active at once (e.g. at most N−1 of N philosophers at the table). (iii) Resource hierarchy / linear ordering — a total ordering of resources; the OS allocates only in increasing order. (iv) Periodic detection with rollback — the OS checks for deadlocks and rolls one process back to its last checkpoint when found.

Deadlock recovery — when a deadlock is detected, the OS must break it:

  1. Process termination — kill one or more of the deadlocked processes. Simplest: kill the whole set; more conservative: kill one process at a time, re-checking the RAG until no cycle remains. Cost: the killed processes lose all their work.
  2. Resource preemption — the OS forcibly takes a resource from one process and gives it to another. Cost: a context switch and potential state corruption (a preempted process mid-transaction may hold inconsistent data).
  3. Rollback (checkpointing) — the OS restores a process to a checkpoint (a saved snapshot) and re-executes from there. The process must periodically save state; cost is re-execution time since the last checkpoint.

The choice depends on the cost of re-execution, the criticality of the work, and the number of deadlocked processes. In practice the OS detects the deadlock with a wait-for graph, rolls one process back to a recent checkpoint, and re-schedules the rest.
