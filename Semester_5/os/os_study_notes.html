Introduction to Operating Systems

Functions, types, structures, system calls, booting

1.1 What is an Operating System?

An Operating System (OS) is a system software that acts as an interface between the user and the computer hardware. It manages hardware resources, provides services to application programs, and ensures the system runs efficiently and securely.

Two views of an OS:

  • Resource Manager: Manages CPU, memory, I/O devices and files so that competing processes get fair, efficient access.
  • Extended Machine / Virtual Machine: Hides the messy details of hardware and presents a clean, abstract interface to the user.

Functions of an OS: Process management, Memory management, File management, I/O management, Security & protection, Command interpretation, Error detection.

1.3 OS Structures

  1. Simple / Monolithic Structure: No structure; entire OS is one big program. Used by MS-DOS. Fast but hard to maintain.
  2. Layered Structure: OS is divided into layers (0 = hardware, N = user). Each layer uses only lower-layer services. Easier to debug & maintain (THE, MULTICS).
  3. Microkernel: Kernel keeps only essential services (IPC, basic scheduling, address space). Other services (drivers, file systems) run in user space. Reliable & portable (QNX, Mach).
  4. Modular Structure: Kernel has a core module; other modules (drivers, file systems) can be loaded dynamically. Combines performance of monolithic with flexibility. (Linux, Solaris, modern Windows).
  5. Hybrid (e.g., macOS): Microkernel + modules for performance.

1.4 System Calls

A system call is the programmatic way a user process requests a service from the kernel. Examples: read(), write(), open(), fork(), exec(), wait(), exit().

Categories:

  • Process control (fork, exec, wait, exit)
  • File manipulation (open, read, write, close)
  • Device manipulation (ioctl, read, write)
  • Information maintenance (getpid, alarm, sleep)
  • Communication (pipe, socket, shmget)

Steps to execute a system call (e.g., read): user program → libc wrapper places args in registers → executes trap/syscall → kernel handles → return to user.

1.5 Booting Process

Booting = loading the OS kernel into memory and starting execution when the computer is switched on.

  1. Power-On Self Test (POST): Hardware diagnostic by BIOS/UEFI.
  2. Bootstrap loader: A small program in ROM/flash (BIOS or UEFI) reads the boot block from a configured disk.
  3. GRUB / boot loader: Locates the kernel image on disk and loads it into RAM.
  4. Kernel initialization: Sets up memory management, loads drivers, mounts root file system.
  5. init / systemd: First user-space process (PID 1) starts all system services and the login manager.

Explain the different types of operating systems. [2023]

  1. Batch OS: Jobs with similar needs are grouped into batches and run sequentially. No user interaction. Disadvantage: CPU idle during I/O.
  2. Multiprogramming OS: Several jobs are kept in memory simultaneously. When the running job waits for I/O, the CPU switches to another. Maximises CPU utilisation.
  3. Multitasking / Time-Sharing: Many users log in simultaneously. CPU time is divided into short slices (round-robin). Provides interactive use.
  4. Multiprocessor OS: Uses two or more CPUs that share memory, bus, clock. Provides true parallel execution, higher throughput, and graceful degradation.
  5. Real-Time OS: Guarantees response within a deadline. Hard RT (miss = catastrophe, e.g., aircraft), Soft RT (degrades gracefully, e.g., multimedia).
  6. Distributed OS: A collection of loosely-coupled computers networked such that users see a single integrated system. Resources are shared transparently.
Comparison: Batch < Multiprogramming < Time-Sharing < RT in terms of response time and complexity.

5 Marks

Explain system calls with an example. List their categories.

A system call is the only legal way a user program can request kernel services. The flow for read(fd, buf, n):

  1. Program calls the read wrapper in libc.
  2. Wrapper pushes args into registers and issues syscall/trap.
  3. Kernel invokes the appropriate handler from the system-call table.
  4. Driver performs the I/O; data is copied to buf.
  5. Return value (bytes read or error) is returned to user space.

Categories:

  • Process control: fork, exec, wait, exit, kill
  • File manipulation: open, read, write, close, lseek
  • Device manipulation: ioctl, read, write
  • Information maintenance: getpid, alarm, sleep, time
  • Communication: pipe, socket, shmget, msgget
  • Protection: chmod, chown, umask

5 Marks

Describe the booting procedure of a computer system.

  1. Power-On & POST: BIOS/UEFI runs the Power-On Self Test to verify RAM, keyboard, disk.
  2. Bootstrap Loader: A small program in ROM locates the configured boot device (HDD, SSD, USB) and reads its first sector (MBR / GPT).
  3. Stage-2 Bootloader: GRUB / Windows Boot Manager is loaded, presenting a menu and locating the OS kernel image on disk.
  4. Kernel Loading: Kernel is read into RAM and given control. It initialises MMU, interrupts, drivers, and mounts the root file system.
  5. User Space: The kernel starts init (PID 1) or systemd, which in turn starts login, services, and finally the GUI.

UEFI vs BIOS: UEFI is the modern replacement — supports GPT, Secure Boot, faster POST, and a 32/64-bit pre-OS environment.

Explain in detail the various types and structures of operating systems. [2022]

1. Types of Operating Systems

  • Batch OS: Jobs grouped; processed one after another; no interaction. Advantage: throughput. Disadvantage: no interaction, CPU idle during I/O.
  • Multiprogramming OS: Several jobs in memory; when one waits, OS switches to another. CPU utilisation ↑, throughput ↑.
  • Multitasking / Time-Sharing OS: Each user/job gets a small time slice (round robin); provides interactivity. Concepts: scheduler, context switch, swapping.
  • Multiprocessor / Multicore OS: More than one CPU; jobs can run in true parallel. Types: symmetric (SMP) and asymmetric (AMP).
  • Real-Time OS: Deterministic timing; hard (miss = system failure) vs soft (degrade). Used in embedded systems. Examples: VxWorks, RTLinux.
  • Distributed OS: Network of autonomous machines seen as one. Resource sharing, load balancing, fault tolerance. Examples: Amoeba, LOCUS.
  • Network OS & Mobile OS: Network OS provides network services (NFS, Samba). Mobile OS — Android/iOS — has its own kernel and APIs.

2. Operating-System Structures

  • Simple Structure (MS-DOS): No layering; applications can directly access BIOS and hardware. Fast but unreliable.
  • Layered Approach: OS split into hierarchical layers. Layer i uses only layer i-1. Easier debugging (THE, MULTICS).
  • Microkernel: Kernel keeps only minimum (IPC, scheduler, address space). Drivers & file systems run in user mode. Reliability, portability; small performance cost due to message passing.
  • Modular: Loadable kernel modules (LKMs) at run time; combines performance of monolithic with flexibility (Linux).
  • Hybrid: Mixes microkernel and modular; macOS (Mach microkernel + BSD monolithic layers).

3. System Calls & Booting

System calls are the only controlled entry into the kernel. Categories: process control, file manipulation, device I/O, information maintenance, communication, protection. The boot sequence runs POST, loads the bootloader (GRUB/UEFI), reads the kernel, sets up drivers, and starts init/systemd.

Conclusion: Modern OSs combine elements — Linux is modular-monolithic with a microkernel-inspired design for IPC. Choice of structure depends on requirements of performance, reliability, portability, and extensibility.

System Call = the controlled interface between a running user program and the OS kernel. Through it a user requests services that need privileged hardware access.

User vs Kernel Mode

User ModeKernel Mode
Normal execution mode of user processesPrivileged mode of OS kernel
Restricted instruction set; cannot access hardware directlyFull instruction set; can execute privileged I/O & memory ops
Crash affects only the processCrash can bring down entire system
Switch to kernel via system call / interrupt / trapReturns to user after servicing

Steps in executing a system call (e.g., read):

  1. User program invokes libc wrapper read(fd, buf, n).
  2. Wrapper copies arguments into registers and issues syscall instruction / INT 0x80.
  3. CPU switches to kernel mode (mode bit changed in PSW).
  4. Kernel's syscall dispatcher reads syscall number and invokes the right service routine.
  5. Service routine (e.g., read from a file) performs the I/O and copies data to user buffer (with bounds checks).
  6. Return value is placed in a register; mode bit set back to user; execution resumes in user program.

Types / Categories: Process control, file manipulation, device manipulation, information maintenance, communication (IPC), protection.

Why use system calls? Protection — only the kernel can touch hardware, ensuring safety, isolation and security. Abstraction — programs see a clean API instead of raw hardware.

Process Management

PCB, process states, context switching, IPC, threads

2.1 Process vs Program

A program is a passive file of code and data. A process is the active execution of a program — a program in motion. A single program may give rise to many processes (e.g., multiple chrome windows).

2.2 Process States (with Diagram)

The five-state model:

        +---------+    admit   +----------+  dispatch +---------+
        |  New    | ---------> |  Ready   | --------> | Running |
        +---------+            +----------+  <------- +---------+
                                   ^  |                 |   |
                              swap-in| |event occurs   |   | interrupt /
                                   |  | (I/O done)     |   | quantum
                                   |  v                |   | expiry
                              +----------+             |   v
                              |  Blocked | <-----------+ +--------+
                              | /Waiting |  I/O or     | | Exit   |
                              +----------+  event wait +--------+
  • New: Process being created.
  • Ready: Waiting in main memory for CPU.
  • Running: Currently executing on CPU.
  • Blocked/Waiting: Waiting for I/O or event.
  • Exit/Terminated: Finished or killed; resources being reclaimed.

Long-term scheduler controls degree of multiprogramming. Short-term (CPU) scheduler picks the next ready process. Medium-term scheduler can suspend / swap out a process.

2.3 Process Control Block (PCB)

A PCB is a kernel data structure that stores all information needed to manage a single process. Contents:

  • Process ID (PID), Parent PID, Credentials.
  • Process State: new, ready, running, waiting, terminated.
  • CPU Registers / Context: PC, SP, accumulators, etc.
  • Memory-management info: base/limit registers, page tables.
  • Scheduling info: priority, accounting, queue pointers.
  • I/O status info: list of open files, I/O devices allocated.

PCBs are linked into per-state queues: ready queue, wait queues for each device, etc.

2.4 Context Switching

Context switch = saving the state of the running process into its PCB and loading the state of the next process. Pure overhead (no useful work) — typically 1–1000 µs.

Steps: 1) Save state of P1 to PCB1. 2) Update pointers to PCB1/P2. 3) Load state of P2 from PCB2. 4) Switch to user mode, jump to P2's PC.

Hardware support via PCBs in memory + kernel stack of suspended process greatly speeds the switch.

2.5 Inter-Process Communication (IPC)

Two fundamental models:

Shared MemoryMessage Passing
Processes share a region of memory; reads/writes are direct.Kernel carries messages between processes via send/receive primitives.
Fast (no kernel on each access); needs synchronization (semaphores, mutexes).Slower (kernel-mediated); easier to build distributed systems.
Race conditions possible.Race-free; easier to reason about.
Examples: System V shm, POSIX shm, mmapExamples: Pipes, FIFOs, sockets, message queues, signals

2.6 Threads & Multithreading Models

A thread is a basic unit of CPU utilization; it shares code, data and OS resources with other threads of the same process but has its own thread ID, stack, registers.

Benefits: faster creation, low overhead communication via shared memory, better utilisation of multiprocessors.

Multithreading models:

  • Many-to-One: Many user threads → one kernel thread. Blocking syscalls block the whole process. (Green threads)
  • One-to-One: Each user thread maps to one kernel thread. Better concurrency; risk of exhausting kernel threads. (Windows NT, Linux)
  • Many-to-Many: Multiplexes m user threads onto n (n ≤ m) kernel threads. Most flexible. (Solaris, IRIX)
  • Two-level: Like many-to-many but allows one user thread bound to a kernel thread for critical cases.

5 Marks

Explain the 5-state process model with a neat diagram.

States: New (just created) → Ready (waiting for CPU) → Running (on CPU) → Blocked (waiting for I/O or event) → Exit (terminated).

  • New → Ready: admission by long-term scheduler.
  • Ready → Running: short-term scheduler dispatches.
  • Running → Ready: interrupt / quantum expiry.
  • Running → Blocked: I/O request or wait on event.
  • Blocked → Ready: completion of I/O or event.
  • Running → Exit: process terminates itself or is killed.

Ready processes wait in the ready queue; blocked processes wait in queues specific to the event (e.g., disk queue).

5 Marks

What is PCB? List its contents. Explain context switching.

PCB contents: PID, parent PID, process state, program counter, CPU registers, memory management info (page/segment tables), scheduling info (priority), list of open files, I/O status, accounting info (CPU time used).

Context switch steps:

  1. Save state of current process (PC, registers, etc.) into its PCB.
  2. Move PCB to appropriate queue (e.g., ready queue or wait queue).
  3. Pick next process from ready queue.
  4. Load saved state from new PCB into CPU.
  5. Resume execution of new process.

Context switch time is overhead — kernel tries to minimise it. TLB flushes during switch also incur cost.

Explain multithreading models. [2023]

Threads come from either the user library or the kernel. Their mapping defines the model:

  • Many-to-One: Many user-level threads → one kernel thread. Thread library schedules in user space. Drawback: one blocking syscall blocks all threads.

Explain the 5-state process model with a neat diagram. Discuss PCB and context switching in detail. [2022]

1. Five-State Process Model: New, Ready, Running, Blocked, Exit. (See Unit 2 §2.2 for diagram.)

Long-term scheduler admits processes to ready queue; short-term scheduler dispatches from ready queue to CPU. A running process may (a) be preempted back to ready, (b) request I/O → blocked, (c) exit.

2. Process Control Block: Central data structure for each process. Contains:

  • Identification: PID, PPID, UID, GID.
  • State info: current state, registers, PC.
  • Control info: scheduling priority, accounting, queue pointers.
  • Resource info: memory maps, open file descriptors, I/O devices allocated.

PCBs are stored in process tables; pointers link them into ready queue, device queues, etc.

3. Context Switching: Mechanism by which CPU switches from one process to another. Steps: (i) save state of old process in its PCB, (ii) update kernel data structures (move PCB to ready/wait queue), (iii) select next process, (iv) load its PCB state into CPU, (v) jump to its PC.

Cost factors: register save/restore time, memory access patterns, TLB flushes, cache pollution. Systems minimise switches by using larger quantum when context-switch overhead is high.

4. IPC & Threads: Once multiple processes/threads exist they need to cooperate: shared memory (fast, requires sync) or message passing (clean, slow, distributed-friendly). Threads share the process address space, making thread creation cheaper than process creation and enabling natural parallel execution on multicore systems.

15 Marks

Explain threads. Discuss user-level vs kernel-level threads and the various multithreading models with neat diagrams.

A thread = a flow of control within a process. Each thread has its own: thread ID, program counter, register set, stack. Threads of the same process share code segment, data segment, heap, and OS resources (open files, signals).

Why threads?

  • Faster creation (≈ 30×) and termination than processes.
  • Cheap communication via shared memory (no kernel).
  • Better utilisation of multiprocessors — one process can run on many cores simultaneously.
  • Responsive UI: blocking I/O in one thread doesn't freeze the application.

CPU Scheduling & Deadlock

FCFS, SJF, Priority, Round Robin, MLQ/MLFQ, Deadlock (Coffman + handling)

3.1 CPU Scheduling — Basics

CPU scheduling is the basis of multiprogrammed OS. The scheduler selects a process from the ready queue to run.

Scheduling criteria: CPU utilisation, Throughput, Turnaround time (TAT = completion − arrival), Waiting time (WT = TAT − burst), Response time, Fairness.

Types: Non-preemptive (FCFS, SJF, Priority) vs Preemptive (SRTF, Preemptive Priority, Round Robin).

3.2 FCFS (First-Come, First-Served)

Process that requests CPU first is allocated first. Simple but suffers the convoy effect — one long process delays all short ones behind it. Non-preemptive.

3.3 SJF / SRTF (Shortest Job First / Shortest Remaining Time First)

Process with the smallest next CPU burst is chosen. Optimal in terms of average WT. Non-preemptive (SJF) and preemptive (SRTF) variants. Hard to predict burst length; risk of starvation of long jobs.

3.4 Priority Scheduling

Each process is assigned a priority; CPU is given to the highest-priority process. Can be preemptive or non-preemptive. Starvation is solved by aging (gradually increasing the priority of waiting processes).

3.5 Round Robin

Each process gets a small time unit (quantum, q). After q expires, the process goes to the back of the ready queue. Preemptive, fair, good for time-sharing. Performance depends on quantum: small q ⇒ high context-switch overhead; large q degenerates into FCFS.

3.6 Multilevel Queue & Multilevel Feedback Queue

MLQ: Ready queue divided into multiple queues (e.g., system, interactive, batch, student). Each queue has its own scheduling algorithm.

MLFQ: A process can move between queues based on observed behaviour. A CPU-bound process that consumes its quantum is demoted to a lower queue; an I/O-bound process that frequently blocks stays in a higher queue. Approximates SJF without knowing the burst length.

3.7 Deadlock

A set of processes is deadlocked if each is waiting for an event that only another process in the set can cause. Usually refers to circular waiting for resources.

Coffman / 4 Necessary Conditions (all must hold):

  1. Mutual Exclusion: At least one resource is non-shareable.
  2. Hold & Wait: A process holds at least one resource while waiting for another.
  3. No Preemption: Resources cannot be forcibly taken; only the holder releases.
  4. Circular Wait: A circular chain of processes exists where each holds a resource wanted by the next.

Resource Allocation Graph (RAG): Circles = processes, Squares = resource classes; instances as dots. A cycle in a single-instance RAG ⇒ deadlock. In multi-instance RAG, a cycle is necessary but not sufficient.

Handling Deadlock:

StrategyIdeaUsed by
PreventionBreak one of the 4 conditions (e.g., require all resources up-front; impose total ordering).Embedded / hard RT
AvoidanceBanker's Algorithm: only grant a request if it leaves a safe state.Some mainframes

5 Marks

Explain the four necessary conditions for deadlock. [2022]

All four must hold simultaneously for a deadlock to occur:

  1. Mutual Exclusion: At least one resource is held in a non-sharable mode (e.g., a printer).
  2. Hold and Wait: A process is currently holding at least one resource and is waiting to acquire additional resources held by other processes.
  3. No Preemption: Resources cannot be preempted; they can only be released voluntarily by the process holding them.
  4. Circular Wait: There exists a set of waiting processes {P0, P1, …, Pn} such that P0 waits for a resource held by P1, P1 waits for P2, …, Pn waits for P0.

To break deadlock: prevent any one of these four conditions. For example, impose a total ordering on resource acquisition to break circular wait.

What is deadlock? Explain prevention, avoidance, detection & recovery methods with the Banker's algorithm. [2022]

Deadlock is a state where a set of processes are each waiting for a resource held by another process in the set, forming a circular chain. The four necessary (Coffman) conditions are mutual exclusion, hold & wait, no preemption, and circular wait.

1. Prevention — design the system so that at least one of the four conditions can never hold.

  • Mutual exclusion ⇒ use spooling for shareable devices (not always possible).
  • Hold & wait ⇒ require a process to request all resources up-front.
  • No preemption ⇒ allow OS to take back a resource if a process holding it requests another.
  • Circular wait ⇒ impose a total ordering on resources; processes must request in that order.

2. Avoidance — Banker's Algorithm (Dijkstra)

Inputs: Max matrix, Allocation matrix, Available vector. Computes Need = Max − Allocation. On a request, pretend to allocate; then run the Safety Algorithm — find a safe sequence using Work ≥ Need[i] for some i, mark done, release its allocation, repeat. If a safe sequence exists, grant the request; otherwise refuse.

Example: Available = [3,3,2]. Allocation: P0(0,1,0), P1(2,0,0), P2(3,0,2), P3(2,1,1), P4(0,0,2). Max given similarly. Safety check: safe sequence could be P1 → P3 → P4 → P0 → P2. So state is safe.

3. Detection & Recovery

Allow deadlock; periodically run a detection algorithm (RAG cycle check or wait-for-graph + Banker-style algorithm). Recovery options: (a) terminate one or more processes, (b) preempt resources — choose a victim, roll back its state, and restart.

4. The Ostrich Algorithm — used by Linux/Windows. The cost of prevention/avoidance is deemed higher than the cost of an occasional deadlock (which is rare).

Comparison: Prevention ⇒ low runtime overhead, very restrictive. Avoidance ⇒ flexible but every request analysed; not always possible (need Max in advance). Detection ⇒ maximum concurrency but recovery is hard. Ostrich ⇒ pragmatic.

Memory Management

Paging, segmentation, virtual memory, TLB, page replacement, thrashing, working set

4.1 Logical vs Physical Address

A logical address is generated by the CPU (the program's view). A physical address is the actual address in main memory. The MMU (Memory Management Unit) translates logical → physical at run time.

4.2 Contiguous Allocation

Each process occupies one contiguous region of memory. Schemes:

  • Fixed / Equal partition: simple, but internal fragmentation.
  • Variable partition: sized to process; suffers external fragmentation.

Compaction may move processes to coalesce holes, but it costs CPU time. Common placement strategies: First-fit, Best-fit, Worst-fit.

4.3 Paging

Memory is divided into fixed-size frames; a process's logical memory is divided into equal-sized pages. Any page can be loaded into any free frame. A page table maps page → frame.

Advantages: no external fragmentation, easy to swap, simple allocation. Disadvantage: small internal fragmentation (last page).

Effective Access Time for single-level paging: EAT = (1 − p)·m + p·(m + n) where p = page-fault rate, m = memory access time, n = page-table access overhead.

4.4 Segmentation

Memory is divided into variable-size logical units called segments (code, stack, heap, data). Each segment has a name and length. The address is a 2-tuple <segment-number, offset>. A segment table holds base + limit. Easy protection and sharing per-segment. Suffers external fragmentation.

4.5 Virtual Memory

Virtual memory allows execution of processes that may not be completely in memory. Only the required pages are loaded on demand. Benefits: programs can be larger than physical RAM, more processes in memory ⇒ higher CPU utilisation, isolation between processes.

4.6 Demand Paging

Pages are loaded only when referenced. When a reference hits a page not in memory → page fault: the OS issues disk I/O, finds a free frame, reads the page, updates the page table, restarts the instruction. A valid/invalid bit in the page table marks whether the page is in memory.

Effective Memory Access Time: EMAT = (1 − p) × ma + p × (page-fault service time). Typical ma = 100 ns, page-fault service ≈ 10 ms. Even small p severely degrades EMAT.

4.7 TLB (Translation Lookaside Buffer)

The TLB is a small, fast associative cache of recent page-table entries. Lookup: if hit (ratio α), memory access takes ma + t (TLB lookup). If miss (1 − α), page table must be walked: takes another ma. With TLB, average lookup is approximately:

EAT = (ma + t)·α + (ma + t + ma)·(1 − α) + (page-fault cost)·p

Typical hit ratios > 95%, making paging nearly as fast as physical addressing.

4.8 Page Replacement Algorithms

When memory is full and a new page must be brought in, we evict an existing page:

  • FIFO: Evict oldest page. Easy; suffers Belady's anomaly (more frames can mean more faults).
  • LRU (Least Recently Used): Evict page unused for longest time. Approximates optimal. Hardware-intensive; needs counters or stack.
  • Optimal (OPT / Belady): Evict page that will not be used for longest in the future. Theoretical lower bound; not implementable.
  • Clock / Second Chance: Approximation of LRU using a reference bit and a circular pointer.
  • LFU, MFU: Keep counters of frequency / recency. Less commonly used.

4.9 Thrashing

Thrashing occurs when a system spends more time swapping pages than executing instructions. Cause: too many processes, each getting too few frames ⇒ frequent page faults. Solutions:

  • Working-set model — give each process enough frames to cover its working set.
  • Page-fault frequency — suspend a process if it faults too often.
  • Swapping out a process entirely to reduce multiprogramming.

4.10 Working Set

The working set W(t, Δ) = set of pages referenced in the most recent Δ virtual time units. The OS tracks the working set size per process and tries to keep all pages resident. If total working-set demand > physical memory, thrashing begins.

Explain demand paging and the steps of a page fault.

Demand paging loads pages into memory only when referenced (lazy loading). Hardware supports a valid/invalid bit in each page-table entry.

Page-fault service routine:

  1. Trap to OS; save registers & PC of faulting process.
  2. Determine whether the reference is legal (in process's address space) — else segmentation fault.
  3. Find a free frame (or evict one via replacement algorithm).
  4. Schedule disk I/O to read the desired page into that frame.
  5. While the I/O runs, context-switch to another ready process.
  6. On I/O completion, update the page table to set the frame number and mark the entry valid.
  7. Restart the faulting instruction.

Explain virtual memory. Discuss demand paging, the TLB, and the EMAT formula. [2022]

Virtual Memory is a technique that allows execution of a process whose entire logical address space need not be in physical memory. Pages not currently needed stay on disk and are loaded only on demand. Benefits: processes can be larger than RAM, more processes ⇒ better CPU utilisation, isolation & protection between processes.

Demand Paging brings pages into RAM only when referenced. Each PTE has a valid/invalid bit. On a reference to an invalid page, a page fault occurs and the OS services it as listed in §4.6.

TLB caches recent page-table translations. TLB lookup takes time t (~10 ns); memory access time is ma (~100 ns). With hit ratio α:

EAT (no page faults) = α·(ma + t) + (1 − α)·(ma + t + ma)

With page-fault rate p and page-fault service time PFS (≈ 10 ms):

EMAT = (1 − p)·[α·(ma + t) + (1 − α)·(2ma + t)] + p·PFS

For α = 0.95, ma = 100 ns, t = 20 ns:

Normal EAT = 0.95·120 + 0.05·220 = 114 + 11 = 125 ns. With p = 0.001, PFS = 10 ms: EMAT = 0.999·125 + 0.001·10,000,000 ≈ 10,125 ns. Even tiny p dramatically increases EMAT.

Working Set & Thrashing: The OS keeps each process's working set resident. If total working-set demand > physical memory, the system thrashes — pages are evicted before being reused. Mitigation: working-set model, page-fault frequency control, swapping out entire processes.

File Systems & I/O

Files, directories, allocation, disk scheduling, I/O, spooling

5.1 File Concepts

A file is a named collection of related information stored on secondary storage. Attributes: name, type, size, protection, timestamps (created, modified, accessed). Operations: create, delete, open, close, read, write, append, seek, rename.

5.2 File Access Methods

  • Sequential Access: read in order from the beginning (tape model).
  • Direct / Random Access: jump to any byte/block by address (disk model).
  • Indexed Access: read via a key; the OS uses an index file. E.g., ISAM.

5.3 Directory Structures

  • Single-level: all files in one directory (old MS-DOS). Naming clashes.
  • Two-level: one directory per user. Solves naming conflicts, no grouping.
  • Tree-structured (hierarchical): directories contain subdirectories; unique absolute path. (UNIX, Windows.)
  • Acyclic graph: directories may contain shared subdirectories / files via links. No cycles allowed.
  • General graph: allows cycles — needs garbage collection to free unreachable blocks.

5.4 File Allocation Methods

ContiguousFile occupies a set of consecutive blocksSimple, fast sequential & directExternal fragmentation; hard to grow

5.5 Free Space Management

Methods to track free disk blocks:

  • Bit Vector / Bitmap: one bit per block. Simple; bit ops fast; needs contiguous storage.
  • Linked List: chain of free blocks. Cheap but slow traversal.
  • Grouping: first free block stores addresses of other free blocks. Faster traversal.
  • Counting: keep (first block, count) pairs for contiguous runs (best for contiguous allocation).

5.6 Disk Scheduling

Reduces seek time by reordering requests. Disk has cylinders numbered 0..N−1; head moves radially.

  • FCFS: arrival order. Fair; large seeks.
  • SSTF: nearest request first. Better but may starve.
  • SCAN (Elevator): sweep up then down servicing requests.
  • C-SCAN: sweep up; jump to start; sweep up again — uniform wait time.
  • LOOK / C-LOOK: like SCAN/C-SCAN but head stops at the last request, not the disk edge.

5.7 I/O Hardware, Buffering, Caching, Spooling

I/O Hardware: Device controllers + I/O ports. CPU communicates via programmed I/O, interrupt-driven I/O, or DMA.

Buffering: temporary memory area (single, double, circular) decouples producer & consumer rates.

Caching: copy of data in a faster store (e.g., page cache in RAM).

Spooling (Simultaneous Peripheral Operations On-Line): jobs queued on disk for a slow device (e.g., printer) so CPU is not blocked.

Explain the three file allocation methods with their pros and cons.

2. Linked Allocation: Each block contains a pointer to the next; directory stores first & last block. No external fragmentation, easy to grow; only sequential access is fast; pointer overhead; a single bad pointer loses the rest.

Explain buffering, caching and spooling.

Explain the layered I/O architecture: device drivers, controllers, kernel I/O subsystem, and user-level libraries. Discuss DMA, interrupts and buffering in detail. [2022]

I/O Hardware Layer: Physical devices — disks, keyboards, printers, NICs — communicate with the CPU through device controllers. Controllers expose a set of control registers that the CPU reads/writes via I/O instructions (port-mapped) or memory-mapped I/O. The controller attaches to the system bus and may have local buffer memory.

Three I/O Techniques:

  • Programmed I/O (Polling): CPU loops, reading the controller's status register. Simple but wastes CPU time. Suitable for fast devices.
  • Interrupt-driven I/O: CPU issues the I/O and continues other work. Controller raises an interrupt when the operation completes. CPU executes the device's ISR (Interrupt Service Routine).
  • DMA (Direct Memory Access): A DMA controller takes over the bus and moves data between device and RAM without CPU intervention. The CPU is free to do other work. The DMA engine raises one interrupt per buffer (or per block), not per byte. Best for high-throughput devices like disks.

Kernel I/O Subsystem: Provides buffering, caching, spooling, scheduling, and error handling. It maintains a buffer cache in memory, applies a common block-device interface (open, close, read, write), and orders requests to minimise disk seeks (disk scheduler).

Device Drivers: Software modules (one per device or class) that hide the controller's specifics and expose a uniform kernel API. They translate standard read/write requests into controller-specific register operations.

User-level I/O Libraries: Above the kernel, libraries (libc) wrap raw system calls with convenient primitives: printf, fopen, fread, etc. They also implement userspace buffering (stdio buffer).

Buffering: Holds data in transit between producer and consumer. Single buffer — one block at a time; double buffer — one being filled while another is consumed (concurrent I/O and computation); circular buffer — array of N buffers used as a ring (typical in audio/video). Goal: keep both sides busy.

Spooling & Scheduling: For shared, slow devices (printers), spooling stores the job queue on disk and lets the device drain it at its own pace. Disk scheduling (FCFS/SSTF/SCAN/C-SCAN/LOOK/C-LOOK) reorders head movements to reduce average seek time.

Together, these layers transform an irregular hardware interface into a clean, efficient set of abstractions for applications.
