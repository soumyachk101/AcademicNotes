Module 5 Questions

1

What is a reduce-reduce conflict in LR parsing? When does it appear? Give a minimal example. What is an SLR reduce-reduce conflict? Then give a table of ALL shift-reduce parser actions (shift / reduce / goto / accept) with their meaning and when each fires.

Reduce–reduce conflict: in a shift-reduce parser, state s and terminal a produce a conflict when the action table would need two different entries reduce r and reduce r' in the same cell (s, a). It appears when two handle candidates of different productions end in the same symbol and the parser cannot decide which is the true handle. The grammar is not LR(1); usually it is not SLR either, because both reductions are legal for the same SLR lookahead.

Minimal example (LR(0) item set with two reduce items):

S -> i A i .
S -> i B i .
F -> a | b | c

Item set after reading "i":
  S -> i . A i        shift A
  S -> i . B i        shift B

After reading "i a":
  S -> i A . i        reduce S -> i A i
  S -> i B . i        reduce S -> i B i
                      ^^^^^^^^^^^^^^^^^^^
                reduce-reduce on terminal i (no shift to i)
The dot has reached the end of two different productions in the same state, and both items carry the same lookahead set; the parser cannot commit to either reduction. The grammar is ambiguous (or at least not LR(0)) and must be rewritten — e.g. merge i A i and i B i into a single production S → i C i with C → A | B, which removes the conflict.

SLR reduce–reduce conflict: two items q1 → α . β and q2 → α . γ share the same core (state), and FOLLOW(q1) ∩ FOLLOW(q2) ≠ ∅. The conflict survives even when lookaheads are available, because SLR uses a single global FOLLOW set per non-terminal; it cannot distinguish the items. The resolution is to refine the grammar (rewrite it into an unambiguous equivalent) or, in practice, fall back to a full LR(1) parser that carries a per-item lookahead and can split the state.

All shift-reduce parser actions:

A shift-reduce parser's driver consults exactly one of four actions per step; the action table is built by the generator and is the only input to the runtime parser.

SLR conflict resolution (exam point): a shift-reduce conflict in an SLR table is resolved by choosing shift (the canonical convention). A reduce-reduce conflict has no automatic resolution; it indicates the grammar is not suitable for LR-based parsing and must be rewritten. A pure LR(1) parser can, however, split states by their item lookaheads and sometimes eliminate conflicts that SLR leaves behind.

The stack stores (symbol, state) pairs. After a reduce r : A → β is performed, the parser pops len(β) states and consults GOTO[prev_state, A] to find the new top state. The input buffer is read left-to-right, one terminal at a time, with an end-marker $.

Major advantages of LR(1):

  • Covers all practical programming-language constructs without left-factoring. Left recursion (a while, a for-loop, a - b - c) is a non-issue; LL(1) parsers must rewrite the grammar to eliminate it.
  • Single left-to-right pass — no backtracking, no multiple scans, no context-free ambiguity resolution at parse time. Amortised O(n).
  • Lookahead embedded in items — the parser never computes a FIRST set on the fly; the generator precomputes item-lookaheads and the runtime just indexes into the table.
  • Minimal context (usually 1 symbol of lookahead) — one terminal symbol determines the action; the table size is bounded and known in advance.
  • Handles non-LR(0) grammars — e.g. an if-else statement, two-statement blocks, and expression grammars that are not LR(0) but are LR(1) or LR(2).

Contrast with (top-down) predictive / LL(1) parsing:

In practice, most modern parsers use LALR(1) (an LR(1) optimisation that merges states with the same core and lookahead-set, shrinking the table while keeping LR(1) power). LALR(1) can introduce reduce-reduce conflicts that pure LR(1) avoids; Yacc and CUP default to LALR(1).

Compare the LR(1) table with the SLR table from Q4 (size + whether the conflicts disappear under LR(1) — explain why item lookaheads split the state). Then a short note on handle parsing: handles, rightmost derivation run in reverse, one worked handle-reduction trace for (i * i) + i.

LR(1) vs SLR(1) table for Q4 grammar:

Size: SLR uses 11 states (I0–I10 + I11 accept). LR(1) carries a lookahead symbol in each item, splitting states whose LR(0) cores are identical but whose lookahead sets differ. For this grammar, I9 and I10 each split into two sub-states: one with lookahead {i,a} (from the FOLLOW set, where shift dominates) and one with lookahead {$} (where no shift counterpart exists). The LR(1) table therefore has approximately 13 states vs SLR's 11, and the action table is the same width but with more rows.

Conflicts: The SLR shift/reduce conflicts in I9 (on i and a) and I10 (on i and a) disappear under LR(1). The reason: in SLR, all items in a state share the same production number and the lookahead is the global FOLLOW set of the non-terminal. In LR(1), each item is (A → α . β, a) where a is the specific terminal that can legally follow this particular item in context. Items in I9 with lookahead {i} and items with lookahead {a} end up in different states after closure, so the reduce action fires only on the specific terminal, and the shift action fires on the other — no conflict. This is the fundamental LR(1) advantage: item lookaheads split the state and make the table deterministic.

Handle parsing — short note: A handle is a substring of the input that can be reduced to a non-terminal using a single production, and which corresponds to the rightmost derivation step in reverse. Handle parsing (bottom-up) works by finding the handle in the current sentential form, reducing it, and repeating until the start symbol is reached. The parse is the reverse of the rightmost derivation: the last production applied in the rightmost derivation becomes the first reduction (handle) in the parse. Every sentential form in a handle parse is a suffix of some prefix of the input — this is the "left context" property that makes bottom-up parsing feasible without lookahead.

Correction at step 9–10: the reduce sequence is: (T)+T → F+T (reduce T to F via F → T, handle = T) → T+T is not a production; the actual chain is: (E)+T → reduce (E) to F: F+T → reduce F to T: T+T is still not a production; the correct path is: reduce (E) → F, then F + T has no production; instead, reduce the entire (E) sub-expression to T, giving T + T, which then reduces via E → T on the left side: E + T → E. The handle at each step is always the rightmost substring that is the RHS of some production in context — the parser never guesses; the handle is uniquely determined by the stack top and the action table.
