1
Describe the functions and roles of a compiler with examples of syntax error, semantic error, run-time error, and run-time logical error. What are the phases of compilation? What are the major tasks of a compiler?

A compiler is a program that reads a program written in a high-level source language (e.g. C, C++) and translates it into an equivalent program in a low-level target language (assembly or machine code) that can be loaded and executed. Its role is to give the programmer the convenience and clarity of the high-level language while giving the machine the efficiency of the target code. Unlike an interpreter, which executes the source line by line, a compiler produces a self-contained object program that can later be run many times without the source or the compiler being present.

Error Classes — with Examples

ErrorMeaningExample
Syntax errorViolation of the grammatical structure of the language; detected by the parser before code generation.if (x = 5) print x in strict mode, a missing semicolon int x = 5, an unmatched parenthesis sum = (a + b.
Semantic errorSyntax is correct but the statement is meaningless in context; detected by semantic analysis / type checking.adding two incompatible types "abc" + 5 in C, using a variable before declaring it, passing a string where an integer is expected.
Run-time errorCorrect code that fails only during execution because of bad input or environment.division by zero 10/0, stack overflow, array index out of bounds a[10] when the array has 5 elements, NullReferenceException.

Logical errors are the hardest to find because the program does not crash — the result is simply wrong.

  1. Lexical analysis (scanning): reads characters, groups them into tokens (identifiers, keywords, operators, numbers), and drops whitespace and comments. Token examples: if, x, =, 5.
  2. Syntax analysis (parsing): groups tokens according to the grammar of the language and builds a syntax/parse tree; detects missing commas, unmatched parentheses.
  3. Semantic analysis: verifies that constructs make sense — type checking, symbol-table maintenance, scope rules.
  4. Intermediate-code generation: converts the syntax tree into a machine-independent intermediate representation (three-address code, quadruples/triples, a DAG).
  5. Code optimization: transforms the intermediate code to make the target program run faster and use less memory, without changing its meaning.
  6. Code generation: emits target-machine code; allocates registers; maps memory references.

Major Tasks of a Compiler

  • Error detection and reporting: catch syntax, semantic, and where possible run-time errors; print clear messages with line numbers.
  • Code generation: translate source into efficient object code for the target machine.
  • Optimization: produce faster, smaller code — peep-hole, global and interprocedural optimizations.
  • Debugging aids: generate debugging information, trace files.
  • Runtime support: provide routines the generated code calls — function-call activation records, malloc-style allocation, I/O.

Handling Run-Time Errors

Most run-time errors (array bounds, divide-by-zero, heap overflow) cannot be detected at compile time, so the compiler inserts run-time checks into the generated code. For an array reference a[i] the compiler emits a test if (i < 0 || i >= n) trap error before the reference (bounds checking, which can be switched off for speed). For division it may emit a divide-by-zero test. It also generates exception-handling code (try/catch frames), provides run-time library routines the generated code calls, and produces a core-dump / trace facility and debugging info (symbol tables, DWHARF) so that when an error occurs the user can be told the program name, line number, and the offending expression. Some compilers (e.g. Ada, and -ftrapv-style C) make these checks mandatory.

Responsibilities of the Compiler

  • Translate source code into a target program (code generation).
  • Detect and report errors clearly (line number, error kind, suggested fix).
  • Optimize code to improve speed and size.
  • Provide runtime support routines and debugging aids.
  • Manage the symbol table and allocate storage.

Phases of Compilation

(1) Lexical analysis — tokens; (2) Syntax analysis — parse tree; (3) Semantic analysis — meaning/type checks; (4) Intermediate code generation; (5) Code optimization; (6) Code generation. The symbol table and error handling run alongside all phases.

The Two Major Functions

The two major functions of a compiler are: (1) error detection and reporting — finding mistakes the programmer made and explaining them, and (2) code generation — producing an efficient, correct object program equivalent to the source (with optimization as its sub-task).

Meaning of "Semantic"

Semantics is the meaning of a program — what it actually computes — as opposed to syntax, which is its grammatical form. A statement like a = b + 100 may be syntactically perfect but semantically wrong if a is a string and b an integer: the shapes fit, the meanings do not. Semantic analysis is the phase that enforces that all operations are of the right kinds (type checking), that identifiers are declared and used within scope, and that constraints (e.g. non-negative loop bounds in some languages) are respected.

Why Separate Phases?

  • Simplicity & modularity: each phase does one clearly defined job; phases can be designed, tested, and written separately, and recombined for different languages or targets.
  • Correctness: dividing the work makes it easier to prove each phase correct and to localize bugs.
  • Speed: simple, well-structured phases run faster; scanning tokenizes once so later phases need not re-read raw characters.
  • Portability: the lexer, parser, and intermediate code can be reused unchanged for new target machines; only code generation changes.
  • Single-pass performance: although divided conceptually, phases can be run in one pass through the source, so the division costs no extra input read.

How Many Passes?

A one-pass compiler performs all phases while scanning the source once — most modern compilers (C, Pascal) are one-pass because rereading the source is slow. A multi-pass compiler reads the source two or more times (e.g. FORTRAN 77 needed a first pass to collect declaration information and a second to generate code; two-pass assemblers resolve forward labels). The number of passes is about how many times the input is read; the phases are about the logical divisions of work — one pass can execute every phase.

1
What is a grammar? How do we use a grammar? What is a sentential form? What is a derivation? What are the components of a formal grammar? What is a CFG (context-free grammar)? What are the phases of a parser?

A grammar is a finite set of rules (productions) that generate every sentence in a language; formally it is the tuple G = (V, T, P, S) where V is the set of variables (nonterminals), T the terminal symbols, P the productions, and S the start symbol. A grammar "generates" a language: the language L(G) is exactly the set of strings of terminals it can derive.

Using a Grammar

A grammar is used two ways: (1) Generation — starting from S and applying productions repeatedly to build valid sentences (e.g. from S → aSb | ε we generate aabb); and (2) Recognition/parsing — given a string, deciding whether it belongs to the language by finding a derivation (this is what the syntax analyzer does, usually working backwards from the string to S).

Sentential Form & Derivation

A sentential form is any string of terminals and nonterminals that can be derived from the start symbol S. Example: with S → aAb, A → b, the string aAb is a sentential form (it still contains the nonterminal A). A derivation is the sequence of steps in which nonterminals are replaced by production bodies. A derivation ending only in terminals is a parse. If the leftmost nonterminal is replaced at every step the derivation is leftmost (used by top-down parsers); if the rightmost one is replaced, it is rightmost (used by bottom-up parsers); a rightmost derivation read in reverse is called the canonical (LR) form.

Components of a Formal Grammar

ComponentNameExample
VVariables / nonterminalsS, A, B
TTerminalsa, b, ;, +, if

Grammars are classified as Type-0 (unrestricted), Type-1 (context-sensitive), Type-2 (context-free), Type-3 (regular) in the Chomsky hierarchy.

Context-Free Grammar (CFG)

A CFG is a grammar in which the left side of every production is a single nonterminal — the replacement never depends on the symbols surrounding it (no "context"). Example: S → aSa | ε generates the language of odd-length strings of a's and b's centered on b, and arithmetic grammars E → E + T | T (plus precedence levels) are CFGs. Programming-language structures like statements and blocks are generated by CFGs, which is why parsing programming languages is context-free parsing.

Phases of a Parser

A parser's work unfolds in these stages: (1) input tokenization — it consumes tokens from the lexical analyzer; (2) top of stack management — it maintains a stack of grammar symbols (sentential forms in progress) and, in shift-reduce form, keeps track of the viable prefix; (3) decision-making — using the parse table (or a hand-coded prediction routine), it chooses an action: shift a token, reduce a handle to a nonterminal, accept, or report error; (4) action execution — applying the chosen rule; and (5) tree/output building — constructing the parse tree (or evaluating semantic actions in syntax-directed translation) and eventually signalling acceptance.

2
What is syntax analysis? What is the need for syntax analysis? What is a top-down parser? What are the two parsing techniques of top-down parsers? What are the characteristics of top-down parsers? What is a bottom-up parser?

Syntax analysis (parsing) is the second major phase of a compiler: it takes the stream of tokens produced by the lexical analyzer, checks that the sequence conforms to the grammatical rules (the grammar) of the language, and organizes the token structure into a hierarchy — the parse (syntax) tree — that shows how the input sentence is built from the productions.

Need for Syntax Analysis

  • Validates that the program is grammatically well-formed before expensive later phases run.
  • Produces the structural representation (parse tree or an equivalent) that semantic analysis and code generation need.
  • Localizes syntax errors and supports error recovery so one small mistake does not abort compilation.

Top-Down Parsing

A top-down parser starts at the start symbol S and works downward, choosing productions until it reaches a sequence of terminals that matches the input — i.e. it builds a leftmost derivation. While scanning the input left to right, it tries to match productions: when a nonterminal is about to be replaced it must decide which alternative to use, guided by the next input symbols.

The Two Top-Down Techniques

TechniqueIdea
Recursive descentOne procedure per nonterminal; each procedure tries to recognize that nonterminal's productions. The set of procedures recursively calls one another and mirrors the grammar. Simple to write; used in many modern compilers (lex/yacc alternatives, ANTLR, LL grammars).
LL(1) table-driven (predictive) parsingUses a prediction table indexed by (nonterminal, next terminal) to pick the correct production without backtracking; a single driver routine + table replaces the recursive procedures.

(A naive top-down parser may backtrack — try one production, fail, undo, try another — but backtracking is exponential in the worst case, which is exactly why LL(1)/table-driven parsing was developed.)

Characteristics of Top-Down Parsers

  • Start from S and grow down the parse tree to the input (leftmost derivation).
  • Decisions depend on looking ahead at input symbols; LL(1) needs one token of lookahead.
  • Fail unless the grammar has been rewritten to remove left recursion (infinite-loop hazard) and factored to remove the need to look further ahead than k symbols.
  • Easy to debug for recursive descent (call stack = parse stack); table-driven variants need a construction phase.

Bottom-Up Parsing

A bottom-up parser works from the input toward S: it scans tokens left to right, pushes them on a stack, and repeatedly replaces the rightmost substring that matches a production's right-hand side — a handle — with the production's left-hand side, until only S remains. This is essentially the reverse of a rightmost derivation, and it is the canonical form. Because the decision can often be delayed until a handle is definitely identified, bottom-up parsers can handle a strictly larger class of grammars (e.g. grammars ambiguous to LL(1), left-recursive grammars) with the same linear-time guarantee. The principal bottom-up family is the LR parsers (SLR, LALR, canonical LR), driven by shift-reduce transitions in a state machine.

Explain lexical analysis. What is lexical analysis? What is its function? What are the tasks of a lexical analyzer? What are the advantages of a lexical analyzer?

Lexical analysis (scanning) is the first phase of a compiler. It reads the source program character by character, groups the characters into the smallest meaningful units called tokens, and hands the token stream to the syntax analyzer. Whitespace and comments are skipped (unless they carry meaning), and each token is associated with its attribute — e.g. the identifier count gets a lexeme (the string "count") and a semantic value (the offset into the symbol table).

Function of Lexical Analysis

Its function is to reduce the problem size for the parser: the parser deals with a small alphabet of token types (id, num, op, keyword) instead of the raw character alphabet, and with lines of code instead of thousands of characters. A program containing 100 identifiers still has only one token type id, and the parser never sees a second whitespace or the letters of an identifier.

Tasks of the Lexical Analyzer

  • Collect characters into lexemes (words of the language).
  • Classify each lexeme into its token type and attach the attribute value (symbol-table offset for ids, numeric value for constants).
  • Strip blanks, tabs, newlines and comments.
  • Maintain a line/column count so the error handler can report "line 14, column 9: undefined variable x".
  • Generate a token stream for the syntax analyzer, and report lexical errors (illegal character, unterminated string literal, integer overflow).
  • In some designs, do macro expansion or keyword recognition.

Input-Buffer Structure (Classic Two-Pointer Scheme)

  buffer:  [ x  +  5  /  y  #  1 ]        (source text)
                ^           ^
              (1)         (2)
   (1) = lookahead pointer · (2) = current pointer
   The scanner reads until the current pointer is the last
   legal character. To avoid slowing down at the buffer's edge,
   it copies the next line of input to the far end of the buffer
   and sets a flag "buffer-full". When (2) reaches the tail, the
   tail is discarded, the front re-read, (1) and (2) advanced one
   line — the input is "rolled".

Two pointers plus a buffer full of source is all the lexer needs; no whole-program copy is ever required.

Advantages of a Separate Lexical Analyzer

  • Correctness: separating the phases makes each module easier to write and prove correct.
  • Performance: tokenizing characters is cheaper than parsing them; the parser receives a small token stream, and scanning a line at a time keeps memory usage bounded.
  • Portability: a single scanner is reusable across different languages/targets, and a single parser is reusable across different scanners.
  • Modularity: the scanner can be implemented automatically from regular expressions (lex/lex) independently of the grammar-driven parser (yacc/yacc).
  • Simplifies error reporting — every error gets a line/column number the lexer already tracks.

Write the rules and limitations of left recursion, left factoring, and ambiguity. Why are they problems for syntax analysis? What is a regular expression? Write its use?

Left Recursion

A grammar is left-recursive when a nonterminal can derive a sentential form whose leftmost symbol is itself, e.g. E → E + T | T (E generates E + ...). Rule to remove: for A → Aα | β, replace with A → βA′, A′ → αA′ | ε; for A → Aα1 | Aα2 | β1 | β2, use A → β1A′ | β2A′, A′ → α1A′ | α2A′ | ε. Limitation: a top-down/recursive-descent parser enters parse E, sees E again immediately, recurses infinitely, and the stack overflows. Left-recursive CFGs cannot be parsed without first removing the recursion.

Left Factoring

A grammar is left-factored when two alternatives of the same nonterminal begin with the same string of symbols, e.g. stmt → if id = expr . | if . — from the start symbol both alternatives start with if, so a one-symbol lookahead cannot decide which to take. Rule: factor the common prefix into its own nonterminal: stmt → if id = expr . | if . becomes stmt → stmt′ ... in general A → β A₁′ | β A₂′, A′ → A₁″ | A₂″. Limitation: LL(1) (and generally top-down LL(k)) parsers fail because the FIRST sets of the two alternatives overlap; the prediction table has a conflict. Left-factoring removes the common prefix so the decision can be made later.

Ambiguity

A grammar is ambiguous when some string has two or more distinct parse trees (two distinct leftmost or rightmost derivations). Example: stmt → if cond then stmt | if cond then stmt else stmt with if c1 then if c2 then s1 else s2 — the else can attach to the outer if or the inner one, two different trees. Rule of thumb: ambiguity is a property of the grammar, not of the string; to make a language unambiguous, rewrite the grammar so each construct has one parse shape (add a rule, or use a dangling else resolution — "else binds to the closest unmatched if"). Limitation: if the grammar is ambiguous, a table-driven parser will produce a table with multiple actions in one cell (shift/reduce or reduce/reduce conflict), and no LL(1) table exists. Resolution strategies: precedence rules, restrict the grammar, or use a non-ambiguous grammar.

Regular Expressions

A regular expression (RE) is a compact pattern notation over an alphabet that describes a class of strings (a regular language): the building blocks are single characters (a), concatenation ab, union (a | b), closure a*, a+, a?. Uses:

  • Define the tokens of a language: id = letter (letter|digit)*, num = digit+ ("." digit+)?.
  • Build lexical analyzers: lex/yacc compile REs into DFAs.
  • Pattern matching: search, validation (email, phone numbers, ISBN).
  • Simplify compiler design: instead of writing explicit character-level code, describe the token by its RE and let the tool generate the scanner.
5
How do you convert a regular expression to a lexical analyzer? Explain the 3 techniques. What is the structure of the input buffer?

A lexical analyzer's job is to match the current input string against each token's pattern. A regular expression such as id = letter (letter | digit)* describes a regular language. To turn a set of REs into a working scanner, we build an automaton (NFA/DFA) that recognizes the set and then drive it over the input. Three classical techniques:

Technique 1 — Regular-Expression-to-NFA Conversion (Thompson's Construction)

Each RE has an equivalent Nondeterministic Finite Automaton (NFA). The construction is recursive:

RENFA built
aOne state, one edge a to the next state.
εEdge ε from the start state directly to the accept state.
r | sNew start splits with ε edges to both r's and s's starts; both accepts ε-merge to one new accept.
rsConcatenate: the accept of r is also the start of s; new accept = accept of s.
r*Split to r with ε; ε edge from r's accept back to r's start and to the new accept.

The resulting NFA may have ε-transitions. In ε-closure we close under ε-moves and get the DFA-equivalent behavior. An NFA with n states takes O(n) space but is O(n) to simulate (ε-closure per step).

Technique 2 — NFA-to-DFA Conversion (Subset Construction / Power Set)

Each DFA state is a subset of NFA states: DFA δ(A, a) = ε-closure(move(∪ A, a)). The start DFA state is ε-closure(NFA start). Build the DFA states on demand. This converts any NFA to a minimal-ish DFA (no ε-moves, deterministic). Cost: DFA can have up to 2ⁿ states; a DFA with k states costs one transition lookup per input character.

Technique 3 — Direct Regex-to-DFA (Regular-Expression Minimization / Simultaneous Scanning)

Instead of the two-step NFA→DFA pipeline, some tools (e.g. lex) optimize the RE set directly: they build an NFA per RE, unify the starts and accepts, do ε-closure, then minimize to a DFA with a single start and a "longest-match" acceptance rule (for a set of patterns the DFA goes to the accept state that matches the longest prefix). This gives a single deterministic state machine that is the fastest possible — O(1) lookup per character in a state table. The DFA is stored as a two-dimensional array next[state][character].

Structure of the Input Buffer

The lexer reads the source through a bounded input buffer, not by holding the whole program in memory. The classic structure is a two-pointer buffer:

  ┌─────────────────────────────────────────────┐
  │  x  +  5  /  y  #  1  2  3 ...  (next line) │
  └─────────────────────────────────────────────┘
      ↑                    ↑
      (1) lookahead        (2) current
  (1) scans ahead for pattern match; (2) marks
  the last character that belongs to the current lexeme.
  When (2) reaches the end of the buffer, the "buffer-full"
  flag is set: the scanner copies the next line onto the
  buffer's tail, advances both pointers one character, and
  resets the flag. Two pointers + a flag; O(1) work per token.

What is Thompson's construction? Explain with an example. Consider the regular expression (a+b)* a (b+a)b. a) Generate the expression and construct the syntax tree of the above regular expression. b) Find FIRST(L) and LAST() for every internal node in the syntax tree. c) Find FOLLOW() for every node in the syntax tree. d) Construct the corresponding DFA for the given RE using FOLLOW().

Thompson's Construction

Thompson's construction (Ken Thompson, 1968) is a mechanical algorithm that converts any regular expression into an equivalent NFA with ε-transitions by structural induction on the RE. The key rule: each subexpression has exactly one new start state and one new accept state, and the three operations are built by adding ε edges only: r | s adds a split at the front and a merge at the back; rs glues the accept of r to the start of s with an ε edge; r* adds ε edges that skip and loop. The NFA may be nondeterministic, but it accepts exactly the language of the original RE, and it has at most 2 × |regex length| states.

(a) Syntax Tree of (a+b)* a (b+a)b

By operator precedence (union | is lowest, closure * next, concatenation highest) the tree is:

                          (*)
                       /      \
                    (+)        a
                    / \
                   a    b
                          \
                          b
                      (left branch: concat a with (b+a)b)
                    +
                    |
                (+)
                 / \
                b    a

Reading back: the root is (a+b) *, then a (concat), then (b+a) (union), then b (concat). So the whole RE is (a+b)* a (b+a)b. The tree has 7 internal nodes (4 unions/closures and 3 concatenations, counting leaves a and b as internal).

(b) FIRST(L) and LAST() for Every Internal Node

First(node) = the set of characters that can appear as the first character of a string generated from that node. Last(node) = the set of characters that can appear as the last character.

NodeExpressionFirstLast
N1(a+b){a, b}{a, b}
N2(a+b)*{ε, a, b}{ε, a, b}
N3a{a}{a}
N4(b+a){b, a}{b, a}
N5b{b}{b}
N6 (concat: N2·N3)(a+b)* a{ε, a, b}{a}
N7 (concat: N6·N4·N5)whole RE{ε, a, b}{b}

(c) FOLLOW() for Every Node

In parser theory, FOLLOW(X) = the set of terminals that can legally appear immediately to the right of a nonterminal/leaf X in any valid sentence. For a leaf node in a syntax tree the FOLLOW set is the set of symbols that can come right after that occurrence:

  • FOLLOW(N1: a+b) → {ε} (N1 is the root of the sub-tree in N2; it is closed under *, so N1 can be followed by ε, or by anything that follows N2).
  • FOLLOW(N2: (a+b)*) → {a} (the next symbol in the whole tree after the star is the literal a in N3).
  • FOLLOW(N3: a) → {b, a} (the next is the union b+a).
  • FOLLOW(N4: b+a) → {b} (the next symbol is the trailing b in N5).
  • FOLLOW(N5: b) → {ε} (end of the whole expression).

In practice these sets tell us what symbols can "follow" each node; they are also the basis of the FOLLOW-set construction used by LL(1) and LALR parser generators.

(d) DFA Construction Using FOLLOW()

The standard path from this RE to a DFA is: (1) apply Thompson's construction to the whole tree — the star node (a+b)* becomes an NFA with an ε-edge back to its start, and the trailing a (b+a) b becomes a chain of NFA states glued in order; (2) ε-closure gives the NFA's reachable states; (3) the Subset (Power Set) Construction turns the NFA into a DFA whose states are sets of NFA states. Because the FOLLOW set of the whole RE is {ε} (accept state), and the FOLLOW set of N2 is {a} (only a can follow it), the DFA transitions from the closure of (a+b)* on input a enter the "a has been seen" state, and from the (b+a) region the FOLLOW set {b} forces the DFA to transition only on b to the final accept state. Concretely the DFA has 5 states:

  q0 ──{a,b}──► q1         (closure of (a+b)*: {a,b} loop)
  q1 ──{a}──► q2            (first literal 'a')
  q2 ──{b,a}──► q3          (union (b+a))
  q3 ──{b}──► q4 (accept)   (final 'b')
  (any other input → qerror)

  q0: on a → q1; on b → q1
  q1: on a → q2; on b → q1  (back to star)
  q2: on b → q3; on a → q3
  q3: on b → q4 (FINAL)

  The DFA accepts exactly the language L((a+b)* a (b+a)b) =
  { strings of 0-or-more a/b, followed by 'a',
    followed by (a or b), followed by 'b' }

The FOLLOW sets tell us the expected symbols to appear at each point, so the DFA's transitions from each state are constrained to the symbols in that node's FOLLOW set — this is the basis of the construction.

What are the roles of a lexical analyzer?

A lexical analyzer (scanner, lexer) is the first phase of a compiler and acts as the boundary between raw characters and structured tokens. Its roles:

  • Collect characters into lexemes: read the source character by character and group them into the smallest meaningful units (words of the language).
  • Classify each lexeme: assign a token type — identifier, keyword, literal, operator, delimiter — and attach the attribute (symbol-table offset for identifiers, numeric value for constants).
  • Recognize keywords (reserved words like if, while) and identifiers (a string of letters, digits, underscores that is not a keyword).
  • Generate a token stream for the syntax analyzer, in the form (token_type, attribute) pairs.
  • Strip blanks, tabs, newlines, and comments unless they carry meaning.
  • Maintain line and column counts so the error handler can report "line 14, column 9: undefined variable x".
  • Detect and report lexical errors: illegal character, unterminated string literal, integer overflow, unmatched comment terminator.
  • Feed the symbol table: insert each new identifier, associate it with its offset, and report redeclarations or type conflicts to the semantic analyzer.
  • In some designs, perform macro expansion and generate pre-processed source (e.g. #include, #define substitution in C).

The overall result is a clean token stream — one entry per token, ordered left to right, with all whitespace and comments removed — that the parser can process without ever looking at a raw character.

What is a reduce-reduce conflict in LR parsing? When does it appear? Give a minimal example. What is an SLR reduce-reduce conflict? Then give a table of ALL shift-reduce parser actions (shift / reduce / goto / accept) with their meaning and when each fires.

Reduce–reduce conflict: in a shift-reduce parser, state s and terminal a produce a conflict when the action table would need two different entries reduce r and reduce r' in the same cell (s, a). It appears when two handle candidates of different productions end in the same symbol and the parser cannot decide which is the true handle. The grammar is not LR(1); usually it is not SLR either, because both reductions are legal for the same SLR lookahead.

Minimal example (LR(0) item set with two reduce items):

S -> i A i .
S -> i B i .
F -> a | b | c

Item set after reading "i":
  S -> i . A i        shift A
  S -> i . B i        shift B

After reading "i a":
  S -> i A . i        reduce S -> i A i
  S -> i B . i        reduce S -> i B i
                      ^^^^^^^^^^^^^^^^^^^
                reduce-reduce on terminal i (no shift to i)

The dot has reached the end of two different productions in the same state, and both items carry the same lookahead set; the parser cannot commit to either reduction. The grammar is ambiguous (or at least not LR(0)) and must be rewritten — e.g. merge i A i and i B i into a single production S → i C i with C → A | B, which removes the conflict.

SLR reduce–reduce conflict: two items q1 → α . β and q2 → α . γ share the same core (state), and FOLLOW(q1) ∩ FOLLOW(q2) ≠ ∅. The conflict survives even when lookaheads are available, because SLR uses a single global FOLLOW set per non-terminal; it cannot distinguish the items. The resolution is to refine the grammar (rewrite it into an unambiguous equivalent) or, in practice, fall back to a full LR(1) parser that carries a per-item lookahead and can split the state.

An interpretation of a grammar is a rule that assigns a meaning (value, action) to each production. Two forms: (i) Interpreted translation — the parse tree itself is evaluated by an interpreter; the grammar productions are annotated with semantic functions that compute the value of the node from its children. Attributed grammar: a grammar whose productions carry attribute rules (synthesized or inherited). The parse tree plus attribute rules forms the attributed parse tree; evaluating the rules is the translation.

Ambiguity: a grammar is ambiguous if some string has more than one leftmost (equivalently, rightmost) derivation, i.e. more than one parse tree — e.g. E → E + E | E * E for a + b * c. Ambiguity must be resolved because an unambiguous tree is needed for deterministic semantic action.

What is an input-buffering implementation? What problems can arise when implementing the input buffer (lookahead beyond a single character, token boundaries spanning buffer boundaries, end-of-file)? What is a sentinel and its use?

Input buffering: the compiler reads the source into a large buffer (input buffer) rather than character-by-character; the parser pulls tokens from the buffer via a next_token() routine. Each token is cached, with a pointer to the next character. The buffer must hold enough input for the parser's lookahead window.

Problems:

  • Lookahead > 1 character. If the buffer holds only one character, a token like == (2 chars) or an identifier abc (3 chars) cannot be emitted. The buffer must hold enough characters to see the complete next token. For a grammar with max k-lookahead, hold k characters.
  • Token boundary spans the buffer edge. A token may straddle the boundary between two read() chunks — e.g. a 512-byte buffer holds foo in the first chunk but bar in the second; the tokenization engine must not split identifiers, string literals or comments at the buffer edge. One must either (i) read the whole file at once, or (ii) implement a sliding buffer that holds the tail of the previous chunk plus the head of the new chunk so tokenization never straddles the join.
  • End of file. When the buffer runs out of characters the matcher must detect it without dereferencing *buffer_ptr = 0. The usual technique: append a special marker (sentinel) so the parser can recognise that no more input follows.

Sentinel: a special character — commonly $ or an internal EOF token — that the lexer consumes (recognises as "no more input") but that the parser never attempts to match against a grammar production. The sentinel terminates the input: a matching loop checks if (*buf == SENTINEL) return; before emitting a token; the parser's productions do not have $ on their right-hand side, so the parser only sees the sentinel to know the input has ended, not to parse it.

Why a sentinel matters: it separates the lexing concern (how far to read) from the matching concern (which production does this token match). Without it, every matcher must special-case the "is this the last character" check, and an unterminated identifier/string would otherwise be silently split at EOF. With it, the buffer can be refilled or exhausted; the sentinel is the fixed point the matcher converges on.

Mention different loop-optimization techniques. What is a dependency graph? What is an LR(1) parser (brief recap in the code-generation context)?

Loop-optimization techniques:

  • Loop unrolling: duplicate the loop body 2, 4 or k times so that the branch-per-iteration is amortised over k iterations. The loop bound n must be a compile-time multiple of k (or a residual tail loop handles the remainder). Speedup: 1/k fewer branch checks; code size: k× larger. Example: for(i=0;i<n;i+=4){b[i]=a[i]*2; b[i+1]=a[i+1]*2; b[i+2]=a[i+2]*2; b[i+3]=a[i+3]*2;}
  • Loop jamming: combine two (or more) consecutive loops over the same range into one loop over one array traversal, reducing memory traffic and instruction fetch. for(i) t[i]=a[i]+b[i]; jammed with for(i) c[i]=t[i]*2; becomes one loop.
  • Induction variable elimination (strength reduction): replace a costly induction variable (like i*k, the address calculation) with an add-by-constant chain. If i = i + 1 each iteration, addr = base + i*k becomes a addr = addr + k update, one integer add per iteration instead of a multiply.
  • Strength reduction: replace a hard operation with a cheaper equivalent on the path: x*8 → x << 3; pow(n,2) → n*n when n is small.
  • Peephole optimization: a local scan of a window of w instructions (usually a register or stack) that applies local rewrites: x = x + 0 delete; x = 1; x = x*2; → x = 2; LOAD t; LOAD s; → LOAD s.
  • Loop invariant code motion (LICM): hoist statements whose value does not change within the loop body out of the loop (e.g. addr = &mat[i][j] outside a for(k) { ... } loop that does not write i or j).

Dependency graph: a directed graph whose nodes are the statements of a loop; an edge Si → Sj means Sj reads a value that Si writes (a data dependency, i.e. flow). Two subcases: a loop-carried edge (Sj is in the next iteration of Si's value) is a true dependency that prevents parallel execution; a anti-dependency (write-after-read) can be removed by renaming registers/arrays. The graph exposes which iterations can be run simultaneously — the basis of loop parallelisation.

LR(1) parser (recap): a bottom-up (shift-reduce) parser that keeps a stack of states and reads exactly one lookaheads (hence "LR(1)"). It is constructed from the grammar by the item sets method: LR(0) items are a production with a dot in some position; the closure and goto functions close sets on non-terminals after the dot. The parser has a finite automaton of states; each state has LR(1) sets of (item, lookaheads) pairs that determine whether to shift or reduce. LR(1) can handle every language that is unambiguous in the sense of leftmost-derivation + 1 lookaheads — a strict superset of LL(1). In code generation it is the workhorse of bottom-up semantic evaluation: reductions give the bottom-up order needed for S-attributed SDDs; inherited attributes can be handled by passing values through the stack. LR(k) (k > 1) adds more lookahead but blows up the state table; k = 1 is the sweet spot — enough lookahead for most imperative-language grammars.

What are the types of type systems? What are the specifications of a simple type checker (type inference rules, unification, subsumption, environment)?

Types of type systems (classified on several axes):

  • Typed vs untyped: untyped (machine code, raw C with void*) — every expression has the same type; typed — every expression has a distinct type.
  • Strongly vs weakly typed: strongly — operations only between values of compatible types ("a" + 1 is an error); weakly — implicit conversions are allowed ("a" + 1 becomes "a1" in JavaScript); strong + strict = sound type system.
  • Explicit (nominal) vs implicit (structural): nominal — two types are identical only if the programmer named them identically (Java class Dog1 vs class Dog2); structural — two types are interchangeable if their shape (fields, methods) match (interface-style, in Go and in many functional languages).
  • Sound vs unsound: sound — if the type checker accepts a program, no run-time type error can occur; unsound — the checker lets through a program that will break at runtime (e.g. implicit any in TypeScript, unchecked generics in some languages).

Specifications of a simple type checker: A simple type checker assigns a type to every expression and verifies that every application matches its expected signature.

(1) Type inference rules. A set of rules of the form (Γ, E) → τ, where Γ is the environment (map from variable → type), E is an expression, and τ is the inferred type. Examples:

  • Literals: Γ ⊢ 42 : int; Γ ⊢ "hi" : string
  • Variables: if x : t ∈ Γ, then Γ ⊢ x : t
  • Application: Γ ⊢ e1 : t1 → t2 and Γ ⊢ e2 : t1 implies Γ ⊢ e1(e2) : t2
  • Let: Γ, x : t ⊢ e2 : t' and Γ ⊢ e1 : t implies Γ ⊢ let x = e1 in e2 : t' (with let-generalisation for polymorphic types)

(2) Unification. When two type expressions must be equal (e.g. function argument type = parameter type), the checker solves equations between type variables to make them compatible. E.g. unifying a → int with string → b binds a := string and b := int, giving the most general type string → int. The unifier is the engine of inference: it either succeeds with a binding, or fails with a type clash.

(3) Subsumption. A subsumption rule says that τ₁ ⊑ τ₂ (τ₁ is a subtype of τ₂) — a value of type τ₁ may be used where τ₂ is expected. A subsumption rule in a checker: if Γ ⊢ e : τ₁ and τ₁ ⊑ τ₂, then Γ ⊢ e : τ₂. Inheritance: a Dog value can fill a slot expecting Animal (Dog ⊑ Animal).

(4) Environment. The type environment Γ is a mapping from each free variable in scope to its declared type. It grows as new variables come into scope (Γ, x : t) and shrinks when they leave (Γ \ {x}). The checker keeps a stack of environments (one per scope); the most-inner binding shadows outer ones. The environment plus the rules defines the typing context; the checker's verdict is Γ ⊢ E : τ for some well-formed τ — or a type error if no τ exists.

Putting it together (the four pillars of a simple checker): the environment supplies the declared types; the inference rules walk the AST and assign types; unification solves the type-variable equations that arise; subsumption allows subtypes to fill supertype slots. A program type-checks iff it type-checks under all four rules simultaneously.

  1. Stack allocation — for variables whose lifetime follows the control structure of the program (automatic locals of a procedure, loop bodies). Allocated by moving a pointer, O(1), and released in exactly LIFO order when the block/procedure exits.

  3. Garbage collection — the runtime itself determines when heap objects are dead and reclaims them, so the programmer never deallocates.

Garbage collection fixes the "who frees it?" problem: reference counting keeps a count per object and frees it when it hits 0 (simple, but cyclic leaks and cost per access); mark-and-sweep periodically starts from the roots, marks reachable objects, then sweeps the rest (handles cycles, stops the world or runs in two passes). Heap + GC is the usual strategy for languages like Java; stack stays the default for ordinary automatic local variables.

Discuss the parameter-passing mechanisms with suitable examples: (a) call by value, (b) call by reference, (c) call by name, with a worked example where by-name changes the program result. Then the storage-allocation strategies: (a) stack allocation, (b) heap allocation, with snippets.

a) Call by value (copy semantics): the value of the actual argument is evaluated once at the call and copied into the formal parameter. The callee's modifications to the parameter are invisible to the caller — no side effects, no aliasing, safest and most common.

void inc(int x) { x = x + 1; }   // x is a copy
int main() { int a = 5; inc(a); printf("%d", a);  // prints 5 — a unchanged
}

b) Call by reference (pass by location): the callee receives the address of the actual variable; the formal and actual are aliases. The callee can modify the caller's variable — this is the mechanism for output parameters, but it also creates the aliasing danger:

void swap(int &p, int &q) { int t = p; p = q; q = t; }
swap(x, x);            // aliasing: p and q are the SAME place
                        // t = x; x = x; x = t  ->  no effect, not a swap
swap(x, x + 1);        // overlapping evaluation order -> undefined behaviour
Passing x and an expression of x mixes aliased lvalues; the same-variable call silently fails.

c) Call by name (lazy evaluation): the actual argument expression is substituted textually for the formal and re-evaluated every time the formal is used. It enables passing functions/expressions unevaluated, but re-evaluation can change the result:

// by-name: y and z are the EXPRESSION x, not its value
proc A(x)
  B(x, x)
A(4)
proc B(y, z)          // y, z formal-by-name
  y := 3
  z := y
end B
// global variable z is written

by value:  B copies x=4 for both y and z.
           y:=3  (writes the local copy);  z := y  ->  z = 4
by name:   y and z are both the expression "x".
           y := 3  substitutes x := 3  (x is now 3)
           z := y  substitutes z := x = 3  ->  z = 3
Different final value of z (4 vs 3) from one semantic choice.

Storage-allocation strategies:

// a) Stack allocation: LIFO, O(1) pointer move, lives with the control structure
int* p = stack_alloc(8 * 100);      // 800 bytes on the run-time stack
free(p);                             // released on scope exit — automatic

// b) Heap allocation: arbitrary lifetime, GC or explicit free needed
int* q = malloc(100 * sizeof(int));  // heap block, survives the caller's scope
free(q);                             // programmer's responsibility (or GC reclaims)

The stack is fast and automatic but supports only lifetimes that nest with the control structure; the heap is slower (free-list search + bookkeeping) but supports data that outlive the allocating procedure.

1

Translate the arithmetic expression 5 * a * (b + c) / d into (a) three-address code (temporaries t1…t4 shown) and (b) postfix notation.

a) Three-address code (TAC): each statement has at most three operands; every intermediate value is a temporary so that no address is reused before it is consumed. Operator precedence is honoured explicitly:

5 * a * ( b + c ) / d
--------------------------
t1 = b + c
t2 = 5 * a
t3 = t2 * t1
t4 = t3 / d
result = t4

Equivalent x86-style listing (target ISA: x86-64, EAX/EBX/ECX/EDX registers):

mov  ECX, 5
imul ECX, [a]          ; ECX = 5*a        (t2)
mov  EDX, [b]
add  EDX, [c]          ; EDX = b+c        (t1)
imul ECX, EDX          ; ECX = 5*a*(b+c)  (t3)
mov  EAX, ECX
idiv [d]               ; EAX = t3/d       (t4)  ; quotient in EAX, remainder EDX
mov [result], EAX

b) Postfix (reverse-Polish) notation: operands are listed left-to-right with each operator immediately following its operands; precedence is encoded by the ordering, so no parentheses are needed:

5 * a * (b + c) / d   -->    5 a * b c + * d /

Stack evaluation confirms it: 5 a * → t2; b c + → t1; * → t2*t1 = t3; d / → t3/d = t4. The postfix form is exactly what an interpreter or a stack machine executes — each operator pops its operands and pushes the result, which is why postfix code needs no precedence table and no parentheses.

Quadruples: one tuple (op, arg1, arg2, result) per statement; the result is an explicit 4th field (a named temporary), so values go to a temporary first and move only at the end — easy to reorder and to CSE.

Indirect triples: a separate list of triple numbers gives the execution order; reordering during optimization edits only the list, and final code is produced by patching that list.

What is backpatching? Give a worked mini-example (L1/L2 list patches for the code of if x < 10 goto L, showing next/prev fields). What are the issues in the design of a code generator?

Backpatching: when the code generator emits a jump whose target is not yet known (a forward branch), it writes the instruction with a placeholder target and records the instruction's address in a backpatch list. When the target is finally reached, the recorded addresses are patched — the placeholder is filled in with the true address. Each list entry stores the address of the instruction to patch plus next and prev links (a doubly-linked list) so old and new addresses can be appended at either end in O(1).

Worked example — statement if (x < 10) goto L plus an else fall-through body:

Code generated so far (jump targets are still "?"):
addr  instruction                    L1 list            L2 list
----  -----------------------------  --------           --------
  0   jump-if-true   x  10   ?      [0]                []
  1   jump           _  _    L      [0]                [1]   (patch #1 when L known)
  2   [ body of "if x < 10" ]
  3   [ else body ]
  4   [ code after the if-then-else ]

Patching step by step:
 backpatch(L1, 4):  the true branch targets addr 4
                    list entry #0:  next = NULL,  prev = NULL,  patch_addr = 4
                    code line 0 becomes:  jump-if-true x 10 4
 backpatch(L2, 3):  the else (fall-through) targets addr 3
                    list entry #1:  next = NULL,  prev = #0,  patch_addr = 3
                    code line 1 becomes:  jump _ _ 3
After both patches every jump has a real target; the
L1/L2 lists are empty and released.

Issues in code-generator design:

  1. Quality of generated code — the generator must be correct: the machine code's input-output behaviour must exactly match the source, even after aggressive transformations.
  2. Register allocation — deciding which values live in which registers, what spills to memory, and where spills occur; naive one-value-one-register is far from optimal; dynamic allocation with liveness is much better.
  3. Addressing-mode selection — choosing base-pointer, scaled-index, immediate or memory operands to minimize instruction count and memory references.
  4. Memory ordering and access patterns — respecting side effects (an lvalue must be evaluated where it may have effects) and minimizing loads/stores through the memory hierarchy.
  5. Code size vs speed — small code (shorter instruction count, fewer branches) vs fast code (more registers, more instructions); targets differ: embedded vs desktop.
  6. Machine-specific knowledge — the generator encodes the calling convention, data-type support, branch targets, and alignment requirements of the target ISA.
  7. Preserving semantics under optimization — every optimization must be provably meaning-preserving; the correctness criteria are the same as for optimization (same I/O on all inputs).

What are the properties of an efficient code generator? Discuss the optimization levels (local vs global vs interprocedural) briefly.

Properties of an efficient code generator:

  1. Correctness — the generated program must have exactly the same observable behaviour as the source for every input; no transformation may change lvalue evaluation order, side effects, or I/O order.
  2. Fast machine code — exploit the machine's addressing modes, use registers for frequently referenced values, minimize memory references, and choose branch targets that are usually taken (profile feedback when available).
  3. Short code — minimize instruction count where it does not hurt speed; important on cache-limited or embedded targets.
  4. Effective register allocation — keep hot values in registers; spill only what must live; a good allocator can beat a bad one by a wide margin.
  5. Minimum memory references — keep loop-carried values in registers across iterations; avoid reloading invariants inside loops.

Optimization levels:

LevelScopeTypical transformations
Localone basic block / statementconstant folding, common subexpression elimination, strength reduction, peephole patterns, copy propagation
Global (intra-procedural)whole procedure / flow graphloop-invariant code motion, dead-code elimination, induction-variable substitution, loop unrolling / jamming
Interproceduralacross call sites / whole programfunction inlining (removes call overhead, exposes more dataflow), argument duplication, partial evaluation of known calls

Local transformations are cheapest and run in the same pass as code generation; global transformations require data-flow analysis over the control-flow graph (liveness, reaching definitions, available expressions) and yield the biggest gains on loops; interprocedural analysis is the most powerful but the most expensive (the call graph can be large, inlining can blow up code size, and correctness across program boundaries must be preserved by respecting calling conventions and side effects).

What is peephole optimization (with a rules table)? What are dead code elimination, variable elimination, code motion, and reduction in strength?

Peephole optimization: look at a short "window" of adjacent instructions (the peephole) and apply a set of pattern-substitution rules that simplify the local code. It is the cheapest form of optimization — no data-flow analysis, just local algebra on the instruction stream.

PatternReplacementRationale

Dead code elimination: remove code that cannot affect the observable output. Two forms: (1) dead assignments — v := e where v is never read again before being redefined (v is "dead" at that point); (2) unreachable code — statements after an unconditional jump, or inside a condition that can never be true. Both require liveness / reachability information.

Variable elimination: replace every use of a variable with the expression that defined it (generalised copy propagation), provided no side effect is lost: the defining expression must be side-effect-free, and v must not be an lvalue anywhere (no &v, no array-of-pointers where v is an element). It collapses a variable into its value and exposes further optimizations like CSE.

Code motion: move code to a point where it is executed less often without changing semantics. The principal case is loop-invariant code motion: an expression whose value does not change inside the loop is moved before the loop. Legality conditions — all must hold: (1) the value of every operand is invariant over the loop body; (2) no operand's address is modified inside the loop (aliasing); (3) the operand is not the loop's induction variable; (4) evaluation order of side-effecting lvalues is preserved.

for (i = 0; i < n; i++)          for (i = 0; i < n; i++)
  a = a[i] + b + 1;                 a = a[i] + t;
                                   t = b + 1;              // moved out (invariant)

Reduction in strength: replace an expensive operator with a cheaper one computing the same value: multiplication → addition (x*x → 2*x when x is a power of 2), division by a power of 2 → right shift (x/8 → x >> 3 for unsigned), repeated addition → induction variable, pow(2,k) → 1 << k.

What is meant by redundant load/store statements? Explain with examples: (a) constant folding, (b) common sub-expression elimination, (c) loop unrolling, (d) loop jamming, (e) copy propagation — each with a short before/after.

Redundant load/store: a LOAD instruction that fetches a memory value which is already known (because the last store to that location is visible in the same window and the location has not been written since) is redundant; similarly a STORE followed by a LOAD of the same value with no intervening write is a redundant pair. The optimizer substitutes the known value for the load and deletes the store if the value is not otherwise needed:

before:  v = x + 1;  x = v;  y = x;       after:  v = x + 1;  y = v;  x = v;
(2 loads and 1 store collapsed; x's load deleted because v is live)

(a) Constant folding: evaluate an arithmetic expression whose operands are all compile-time constants, and replace it with the result:

before:  x = 2 + 3;          after:  x = 5;
        a = b * 4;          after:  a = b << 2;   (strength reduction folds too)

(b) Common subexpression elimination: if an expression e is computed, its value stored in a temporary t, and t has not been redefined, then every subsequent occurrence of e is replaced by t:

before:  t1 = a + b;  c = t1;  d = a + b;     after:  t1 = a + b;  c = t1;  d = t1;
(uses reaching-definitions analysis to know t1 still holds a+b)

(c) Loop unrolling: replicate the loop body k times and adjust the induction variable, to reduce branch and loop-control overhead:

before:  for (i = 0; i < 4; i++)  s = s + a[i];
after:   s = s + a[0]; s = s + a[1]; s = s + a[2]; s = s + a[3];
        (4 iterations, 3 fewer branch checks)

(d) Loop jamming: two (or more) loops that iterate over the same array at the same index are merged into one — the array element is loaded once instead of twice, halving memory traffic:

before:                              after:
for i:  a[i] = b[i] + c[i];        for i:  t  = b[i] + c[i];
for i:  d[i] = a[i] * 2;                 a[i] = t;
                                      d[i] = t * 2;
                                  (a[i] stored then re-loaded: eliminated;
                                   one pass, half the I/O)

(e) Copy propagation: replace uses of a variable with the value that was assigned to it, provided the variable is not an lvalue and the assigned expression has no side effect. It makes CSE and dead-code elimination possible:

before:  y = a;  x = y;  z = y + 1;      after:  x = a;  z = a + 1;
                                          (y's definition is now dead -> deleted)

y = a becomes a dead assignment — y is never used after propagation — so the compiler deletes it and both x and z read a directly: the classic pipeline copy propagation → CSE → dead-code elimination.
