1

What is a handle? How do you obtain a parse tree from a string? What is a right-linear grammar and how is left recursion eliminated? What is predictive parsing and how do top-down vs bottom-up parsers handle errors (panic mode, phase-level recovery)? Explain left factoring with a worked example. What is a context-free grammar and what are the roles of a parser? How does operator-precedence parsing work?

Handle & right-sentential forms: a right-sentential form is any string obtained from the start symbol by a rightmost derivation; a handle is the substring of it that reduces in exactly one step to the body of a production — leftmost such reduction is what a bottom-up parser reverses into a parse. For G: E → E + T | T; T → T * i | i, the handle-reduction trace of w = i + i * i (3 steps):

 step   string              handle     rule applied
 1     i + i * i           i          T → i
 2     i + i * T           i * T      T → T * i
 3     i + T               i + T      E → E + T
     E                     (accept)

Parse tree from a string: (a) expand it top-down: any leftmost derivation of w reads left-to-right as a walk of the tree; (b) expand it bottom-up: the handle sequence above reversed is the rightmost derivation, and the same tree falls out of the reduction order. Ambiguous strings yield more than one tree — that is the whole reason the table methods matter.

Right-linear grammar: every production has the form A → wB or A → w (w a terminal string, B one nonterminal). Such grammars generate exactly the regular languages, so a 2-state-style construction (rightmost nonterminal carries the "state") lets a finite automaton recognise them; e.g. A → 0A | 1B, B → 0B | 1A (even parity of 0s).

Eliminating left recursion: A → Aα | β becomes A → Bα, B → βB | ε (first remove indirect left recursion, then apply). Worked: L → L + id | id ⇒ L → id L′, L′ → + id L′ | ε. Predictive parsing is the LL(1) top-down scheme: each lookahead symbol decides the production to use, no backtracking.

Error handling — panic mode (worked example): on error, discard input tokens until a synchronizing token is hit, then restart at the nearest recoverable nonterminal. Input if (x < 3 y = 4; (missing )): the top-down parser hits the error at y after expanding E, discards y = 4, synchronizes on ;, reports "error at y", and resumes the statement list. Phase-level recovery: on error the current phase is restarted from the next token of its own phase input (scanner resynchronizes on a new token boundary; a failed parse restarts on the next top-level construct). Top-down recovery: for each nonterminal keep a small set of expected tokens; when the input is unexpected, report it and discard tokens until one expected token appears (cheap, per-symbol, but local). Bottom-up recovery: insert error productions (S → e S etc.) into the grammar and extend the LR table with an "e" column, so the parser pops the stack to a chosen point and shifts one token — more global, controlled by the table designer.

Left factoring: when a nonterminal's productions share a prefix, top-down predictive parsing must backtrack; factor the prefix out. G: S → id = E | id ≠ E | id > E  ⇒  S → id Q, Q → = E | ≠ E | > E — one lookahead suffices after "id".

Context-free grammar & parser roles: G = (V, Σ, P, S): all rules A → α with A ∈ V and α over (V ∪ Σ)* (e.g. G: S → ( S ) | ε generates ()(())). The parser: constructs the syntax tree / AST, verifies that the program is in the language (syntactic check), hands structure to the semantic analyser, detects and (locally) recovers from syntax errors, and supplies the basis for code generation.

Operator-precedence parsing: a single precedence function f(a,b) over terminal pairs plus a following function c(a); compare c(top-of-stack terminal) with f(top, input) to decide:

RelationMeaningAction
c(a) < f(a,b)b has higher precedence than the stack topSHIFT b
c(a) = f(a,b)equal precedenceSHIFT if left-associative, else ERROR
c(a) > f(a,b)reduce the handle on stackREDUCE

Prove that no LR(1) grammar can be ambiguous. State the contrapositive. Then exhibit a concrete ambiguous grammar with two parse trees for iii and confirm the conflict in its LR(1) item set.

Proof (by contradiction). Suppose G is ambiguous. Then some string w has two distinct parse trees, i.e. two distinct leftmost derivations of w, hence two distinct bottom-up reduction sequences of w. Consider w's reduction on the canonical LR(1) automaton: the two sequences differ at some stack configuration — the parser has built the same stack (the common prefix of the two reductions) but must perform two different reduces for the two remaining sub-derivations. In item-set terms there is a state I that contains two items [A → α . , a] and [B → β . , a] with the same lookahead a, so the LR(1) table must hold two reduce entries for one (state, a) cell — a reduce/reduce conflict. But a valid LR(1) table has exactly one action per (state, symbol) cell, so the contradiction shows G is not LR(1). Contrapositive: every LR(1) grammar is unambiguous.

Concrete example. G: S → i S | S S | i. String iii has two parse trees:

 tree 1: S ⇒ iS ⇒ iSS ⇒ iii          tree 2: S ⇒ SS ⇒ iSS ⇒ iii
        S                          S
      /   \                       /   \
     i     S                     S     S
          / \                   / \    |
         i   S                 i  S   i
              |                 |
              i                 i
 ((i i) i)      -- wait: tree 2 is (i·(i i))? No: S⇒SS: left S→i, right S→SS?

Both derivations exist: S ⇒ i S ⇒ i S S ⇒ i i i (left S → iS, right S → SS? no — S ⇒ iS, S ⇒ SS, S ⇒ i gives tree (i·(i·i)·i)… the two valid distinct leftmost derivations are: (1) S ⇒ iS ⇒ iSS ⇒ iii; (2) S ⇒ SS ⇒ iSS ⇒ iii (S → SS first, left S → i, right S → SS, S → i). Same string, two trees — G is ambiguous.

Item-set confirmation. Canonical sets: I₀ = { [S′ → . S, $], [S → . i S, $], [S → . S S, $], [S → . i, $] }; I₁ = { [S → i ., $], [S → i . S, $] } (closure: S → . i S, S → . S S, S → . i); I₃ = { [S → S S ., $] } (closure same as I₁'s). In the LR(0) automaton I₁ and I₃ merge into one state carrying both reduces [S → i .] and [S → S S .] on the same lookahead — a reduce/reduce conflict, as the proof predicts. FOLLOW(S) = {$, i} (S → S S: i = FIRST(S); start: $), so in the strict LR(1) table I₁ shows the same conflict as shift-vs-reduce on i (i ∈ FOLLOW(S), yet S → i S / S → S S demand shifting i) — either way G is not LR(1), confirming the theorem's contrapositive fails for it, i.e. G is not LR(1) because it is ambiguous.

When is recursive-descent parsing desirable? Its drawbacks? For the left-recursive grammar S → S b | ε (the sheet's i c S b | ε form), show why plain top-down recursion loops, then show an LL(1) table-driven blocking diagram for the same language.

When desirable: hand-written parsers for small grammars where the structure is known in advance; natural, readable code that mirrors the BNF one-to-one; excellent for embedded error reporting at the exact point of failure (each function knows its nonterminal) and for semantic actions interleaved during the descent (build AST/IR inline). It needs no table construction — good for compilers where the grammar is fixed and small.

Drawbacks: (a) recursion depth = parse depth — deep inputs risk stack overflow; (b) no built-in error recovery — a single bad token unwinds the whole call chain unless you write per-production recovery code by hand; (c) intractable on left-recursive grammars — the recursion never reaches a terminal, so it loops (next paragraph); (d) not table-driven, so changing the grammar means rewriting the parser; (e) lookahead beyond LL(1) is awkward (no automatic LALR/LR power).

Why plain top-down recursion loops. G: S → S b | ε (sheet form S → i c S b | ε, the recursion sits in the leftmost position: S ⇒ i c S b ⇒ i c i c S b b …). A recursive-descent function S() written for the left-recursive form calls S() on its own first symbol before consuming anything new — infinite self-call, no input consumed. The same language (strings of the form (ic)* b^n) is fine under table-driven LL(1) because the table decides S → ε vs S → S b from the lookahead symbol, not from a recursive call:

 stack        input        action
 ----------   -----------  -------------------------
 S $          b b b $      table[S,b] = S → S b : replace S by S b on stack
 S b $        b b b $      table[S,b] = S → S b again
 S b b $      b b b $      table[S,b] = S → S b again
 S b b b $    b $          table[S,$] = S → ε : discard S
 b b b $      b $          shift b
 b b $         b $          shift b
 b $           $            shift b
 $             $            ACCEPT

Stack-and-table parsing never "calls itself"; the stack holds the pending S-expansions and the table routes them to ε on $. This is the exact blocking-diagram shape expected: shift/reduce/accept columns with stack vs input tape side by side.
