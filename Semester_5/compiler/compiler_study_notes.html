Unit 1: Introduction to Compiling

3 Lectures · 9 Questions
Q: What is a compiler? 1M

A compiler is a program that translates source code written in a high-level language into an equivalent target program in machine language (object code) for a specific computer architecture. It performs analysis of the source and synthesis of the target.

Q: What is an assembler? 1M

An assembler translates assembly language programs into machine language. It is simpler than a compiler because assembly is closer to machine code. A compiler may invoke an assembler as one of its phases to produce the final object code.

Q: What is an interpreter? 1M

An interpreter directly executes source code line by line without producing an intermediate object file. It translates and executes each statement before moving to the next. Examples: Python (CPython), Ruby. Interpreters are slower than compilers but enable interactive debugging.

Q: List the main phases of a compiler. 1M

The six phases are:

  1. Lexical Analysis
  2. Syntax Analysis
  3. Semantic Analysis
  4. Intermediate Code Generation
  5. Code Optimization
  6. Target Code Generation
Q: What are the "cousins" of a compiler? 1M

The cousins of a compiler are: Preprocessors (macro expansion, file inclusion), Assemblers, Linkers (combine object files), Loaders (load into memory), and Editors/Debuggers (IDE tools).

Q: What is source program analysis? 1M

Source program analysis (the front-end) examines the source code to understand its structure and meaning. It includes lexical, syntactic, and semantic analysis. The output is an intermediate representation (IR) and a symbol table.

Q: Differentiate between analysis and synthesis phases. 1M

Analysis (front-end) breaks the source program into pieces and creates IR + symbol table. Synthesis (back-end) constructs the target program from the IR. Analysis is language-dependent; synthesis is machine-dependent.

Q: What is a cross-compiler? 1M

A cross-compiler runs on machine A (host) but generates machine code for machine B (target). Used in embedded systems where the target has limited resources.

Q: What is bootstrapping in compiler construction? 1M

Bootstrapping is the technique of writing a compiler in its own language. It uses a series of stages where each stage uses a simpler compiler to compile a more advanced version, eventually producing a self-hosted compiler.

Q: Explain the various phases of a compiler with a brief description of each. 5M

A compiler has six major phases:

  1. Lexical Analysis (Scanner): Reads input characters and groups them into tokens (lexemes). Removes whitespace and comments. Uses regular expressions and finite automata. Output: stream of tokens.
  2. Syntax Analysis (Parser): Groups tokens into grammatical phrases using context-free grammars. Builds a parse tree / syntax tree. Checks if the token sequence follows grammar rules. Output: parse tree.
  3. Semantic Analysis: Checks the source program for semantic consistency. Performs type checking, ensures declarations are consistent. Uses attribute grammars. Output: Annotated syntax tree.
  4. Intermediate Code Generation: Translates the annotated syntax tree into an intermediate representation (IR). Common forms: Three-Address Code (3AC). IR is independent of target machine.
  5. Code Optimization: Improves the IR to produce faster/smaller code. Techniques: constant folding, dead code elimination, loop optimization. Local (basic block) or global (entire procedure).
  6. Target Code Generation: Translates the optimized IR into the target machine language. Handles register allocation, instruction selection, and addressing modes.
Draw the 6-phase pipeline: Scanner → Parser → Semantic → IR Gen → Optimizer → Code Generator.

Q: Explain all the phases of a compiler in detail. Differentiate between analysis and synthesis phases. 15M

A. Analysis Phases (Front-End)

1. Lexical Analysis: Reads source character by character, groups into lexemes, produces tokens <token-name, attribute-value>. Removes whitespace and comments. Uses REs and finite automata.

2. Syntax Analysis: Uses token stream to construct a parse tree. Checks if the source follows CFG rules. Reports syntax errors. Output: parse tree / AST.

3. Semantic Analysis: Checks semantic consistency. Performs type checking, ensures identifiers are declared before use. Uses syntax-directed definitions (SDD). Output: Annotated syntax tree.

B. Synthesis Phases (Back-End)

4. Intermediate Code Generation: Translates the annotated syntax tree into IR (e.g., Three-Address Code). IR is platform-independent.

5. Code Optimization: Improves the IR to reduce execution time or space. Local optimization (within a basic block) and global optimization (across basic blocks).

6. Target Code Generation: Translates optimized IR into target machine code. Handles register allocation and instruction selection.

Unit 2: Lexical Analysis

6 Lectures · 13 Questions
Q: What is a token? 1M

A token is a pair (token-name, optional attribute-value). Token-name is an abstract symbol representing a kind of lexical unit; attribute-value points to the symbol table entry for the lexeme.

Q: What is a pattern? 1M

A pattern is a rule describing the set of lexemes that can represent a particular token. Often expressed as a regular expression.

Q: What is a lexeme? 1M

A lexeme is the actual sequence of characters in the source program that matches the pattern for a token. Example: For token id, lexemes could be x, count, _sum.

Q: Differentiate between lexeme and token. 1M

Q: Name two input buffering schemes used in lexical analysis. 1M

(i) One-buffer scheme — single buffer; lookahead character only. (ii) Two-buffer scheme (sentinel) — two halves concatenated with an EOF sentinel, allowing arbitrary lookahead.

Q: Define finite automata. 1M

A finite automaton (FA) is a 5-tuple (Σ, Q, δ, q₀, F) where Σ is input alphabet, Q is finite set of states, δ is transition function, q₀ is start state, and F ⊆ Q are accepting states.

Q: What is an NFA? 1M

A Non-deterministic Finite Automaton — a finite automaton where δ: Q × Σ → 2Q may return multiple next states (or none) for a given input. NFAs accept the same class of languages as DFAs (regular languages).

Q: What is a DFA? 1M

A Deterministic Finite Automaton — δ: Q × Σ → Q is a single-valued total function. No ε-transitions and no two transitions from the same state on the same symbol.

Q: What is a regular expression? 1M

A regular expression (RE) is a notation to describe a regular language. Built from: ε, ∅, symbols in Σ, and operators union (|), concatenation, Kleene closure (*).

Q: What is the role of a lexical analyzer? 1M

The lexical analyzer (scanner) reads source characters, groups them into lexemes, and produces tokens. It also strips comments/whitespace, tracks line numbers, and may store identifiers in the symbol table.

Q: Why separate lexical and syntax analysis? 1M

(1) Simplicity — Parser is cleaner without character-level detail. (2) Efficiency — Specialized buffering & I/O for tokens. (3) Portability — Lexer handles platform-specific characters; parser stays portable.

Q: Explain the role of the lexical analyzer in detail. 5M

The lexical analyzer is the first phase of a compiler. Its primary roles are:

  • Tokenization: Read input characters and group them into lexemes, then produce tokens of the form <token-name, attribute>.
  • Skip whitespace & comments: These have no meaning to later phases.
  • Correlate errors with line numbers: Track source positions for error reporting.
  • Symbol table interaction: For identifiers, install the lexeme into the symbol table; the token attribute points to that entry.
  • Lookahead: Decide between alternative patterns (e.g., = vs ==) using one or two characters of lookahead.

Advantages of separating lexer from parser: Simpler design, better efficiency, portability, and the ability to use specialized tools (Lex/Flex).

Q: Convert the regular expression (a|b)*abb to NFA using Thompson's construction. Then convert the NFA to DFA using subset construction. 5M

RE: (a|b)*abb

Step 1 — Thompson's NFA: Each sub-expression gets its own fragment:

  • For a: state A →a→ B
  • For b: state C →b→ D
  • For a|b: ε-branch from new start to A and C; ε-merge at new end.
  • For (a|b)*: new start with ε to old start, ε from old end back to old start, ε from new start to new end, ε from old end to new end.
  • For abb: chain three transitions on a, b, b.

Step 2 — Subset Construction (NFA → DFA):

Start: ε-closure(0) = {0,1,2,4,7} → D0 D0 on 'a' = ε-closure({3,8}) = {3,8,1,2,4,7,9} → D1 D0 on 'b' = ε-closure({5}) = {5,1,2,4,7,6} → D2 D1 on 'a' = ε-closure({3,8}) = D1 D1 on 'b' = ε-closure({5,9}) = {5,9,1,2,4,7,6,10} → D3 D1 on ... ... D3 on 'b' = {10,1,2,4,7} → D4 (accepting)

Final DFA states: D0, D1, D2, D3, D4. D4 is the only accepting state.

Always show: ε-closure of start, then for each new subset compute transitions on each input symbol.
Q: Explain the design of a Lex-based lexical analyzer generator. 5M

Lex (or Flex) is a tool that generates a lexical analyzer from a specification file .lex. The workflow:

  1. Lex source file contains: { definitions %}{ rules %}{ user code }.
    • Definitions: variable declarations and named regular expressions.
    • Rules: pairs of pattern { action }. Patterns are REs; actions are C code.
    • User code: auxiliary functions copied to the output.
  2. Lex compiler reads the .lex file and produces lex.yy.c (a C program implementing the DFA).
  3. C compiler compiles lex.yy.c with -lfl to produce the executable scanner.

Internally, Lex:

  1. Builds an NFA from the patterns using Thompson's construction.
  2. Merges all NFAs into one combined NFA with a new start state.
  3. Converts NFA → DFA via subset construction.
  4. Minimizes the DFA (Hopcroft's algorithm).

Conflict resolution: When multiple patterns match, Lex uses the rule with the longest match, and on ties the rule listed first.

Mention yylex(), yylval, yytext, ECHO, and yywrap().
Q: Explain the design of a Lexical Analyzer Generator (Lex). Discuss the role of RE → NFA → DFA conversion with a complete worked example. 15M

A. Lex Architecture

Lex is a tool that automates the construction of a lexical analyzer. The user provides a specification file containing:

  • Declarations: definitions, header inclusions, declarations of variables used in actions.
  • Translation rules: P1 { A1 } where Pi is a regular expression and Ai is a C action.
  • Auxiliary procedures: user-defined helper functions.

Lex produces lex.yy.c, which contains a tabular representation of the DFA and a driver yylex() that runs the scanner. Compile with C compiler + -ll (or -lfl).

B. Construction Pipeline

graph LR A["Lex source .lex"] --> B["Lex Compiler"] B --> C["lex.yy.c (C code)"] C --> D["C Compiler + lfl"] D --> E["a.out (Scanner)"] B -. NFA Construction .-> B B -. NFA → DFA .-> B B -. DFA Minimization .-> B

C. Worked Example — RE to NFA (Thompson's Construction)

Consider RE: (a|b)*abb

  1. Build NFA for a: two states with one transition.
  2. Build NFA for b: similar.
  3. Build NFA for a|b: ε-branching.
  4. Build NFA for (a|b)*: ε-loop.
  5. Build NFA for abb: chain three transitions.
  6. Concatenate to form the full NFA (start state 0, final state with double circle).

D. NFA to DFA (Subset Construction)

Algorithm: Start with ε-closure(start). For each subset S and each input symbol a, compute Dtran(S, a) = ε-closure(move(S, a)). Add new subset until no more.

Dstates = { ε-closure(0) } For each subset S in Dstates, for each symbol a: T = ε-closure(move(S, a)) if T not in Dstates: add T Dtran[S, a] = T

E. Worked DFA Construction

D0 = ε-cl(0) = {0,1,2,4,7} D0 --a--> D1 = {1,2,3,4,7,8,9} D0 --b--> D2 = {1,2,4,5,6,7} D1 --a--> D1 D1 --b--> D3 = {1,2,4,5,6,7,9,10} D2 --b--> D2 D2 --a--> D1 D3 --b--> D4 = {1,2,4,5,6,7,10} ← ACCEPTING D3 --a--> D1

DFA Minimization (Hopcroft): Partition states into accepting (D4) and non-accepting (D0, D1, D2, D3). Split groups until all members behave identically on every input.

F. Lex Action Execution

The driver yylex() simulates the DFA on the input buffer. When no further transition exists, the current state determines the matched token. The longest match wins; on ties, the rule listed first in .lex wins. yytext holds the lexeme and yyleng its length.

Always present: RE → Thompson's NFA → subset-construction DFA → minimized DFA. Note that Lex combines all patterns into one combined NFA before DFA conversion.

Unit 3: Syntax Analysis (Parsing)

6 Lectures · 15 Questions
Q: What is a context-free grammar (CFG)? 1M

A CFG is a 4-tuple G = (V, T, P, S) where V = set of variables, T = set of terminals, P = set of productions A → α, S = start symbol. CFGs generate context-free languages.

Q: Define left-most and right-most derivations. 1M

Left-most derivation: At each step, expand the leftmost variable. Right-most derivation: At each step, expand the rightmost variable. Every left-most derivation corresponds to a pre-order traversal of the parse tree.

Q: What is an LL(1) parser? 1M

An LL(1) parser is a top-down parser that reads Left-to-right, produces a Left-most derivation, using 1 token of lookahead. It uses a parsing table constructed from FIRST and FOLLOW sets.

Q: What is an LR parser? 1M

An LR parser is a bottom-up parser that reads Left-to-right, produces a Right-most derivation (in reverse). Variants: LR(0), SLR(1), CLR(1), LALR(1).

Q: What is FIRST(α) for a string α? 1M

FIRST(α) is the set of terminals that can begin strings derived from α. If α can derive ε, then ε ∈ FIRST(α).

Q: What is FOLLOW(A) for a non-terminal A? 1M

FOLLOW(A) is the set of terminals that can appear immediately to the right of A in some sentential form. If A can be the rightmost symbol, $ ∈ FOLLOW(A).

Q: What is a parse tree? 1M

A parse tree (concrete syntax tree) is an ordered tree where interior nodes are grammar variables, leaves are terminals, and each interior node's children correspond to the RHS of a production applied at that node.

Q: What is left recursion? Why is it a problem for top-down parsers? 1M

Left recursion: A production like A → Aα | β. For top-down parsers it causes infinite recursion because the parser keeps expanding A without consuming input. Eliminate by rewriting: A → βA', A' → αA' | ε.

Q: What is backtracking in top-down parsing? 1M

Backtracking means when one production fails, the parser resets input and tries another alternative. It is inefficient; LL(1) parsers avoid backtracking by using 1-symbol lookahead and parsing tables.

Q: What is the handle of a right-sentential form? 1M

A handle is a production A → β whose right-hand side β appears as a substring in a right-sentential form, and replacing β by A is one step in the right-most derivation. Bottom-up parsers reduce handles.

Q: What is an LR(0) item? 1M

An LR(0) item is a production with a dot at some position: A → α·β. Items represent how much of a production has been recognized so far. Sets of items form the states of an LR parser.

Q: Explain the construction of an LL(1) parsing table. 5M

To construct an LL(1) parsing table for grammar G:

  1. Eliminate left recursion and left-factor the grammar.
  2. Compute FIRST(α) for every RHS α of productions.
  3. Compute FOLLOW(A) for every non-terminal A.
  4. For each production A → α:
    For each terminal a ∈ FIRST(α), set Table[A, a] = A → α.
    If ε ∈ FIRST(α), for each b ∈ FOLLOW(A), set Table[A, b] = A → α.
    If ε ∈ FIRST(α) and $ ∈ FOLLOW(A), set Table[A, $] = A → α.

The grammar is LL(1) if no table entry has more than one production. The parser then uses the table to predict which production to apply based on the top-of-stack non-terminal and the next input token.

Key condition: FIRST(αi) ∩ FIRST(αj) = ∅ for all i≠j, and if ε∈FIRST(αi) then FIRST(αj) ∩ FOLLOW(A) = ∅.

Q: Explain the construction of LR(0) and SLR(1) parsing tables with a complete worked example. 15M

A. LR(0) Items and Augmented Grammar

Given grammar G, augment it with S' → S. An LR(0) item is A → α·β (dot marks how much is recognized). A set of items forms a parser state. The closure of an item set adds all productions for non-terminals after the dot.

B. Construction Steps for LR(0)

  1. Augment G: add S' → S.
  2. Construct canonical collection of LR(0) items using goto(I, X).
  3. Create ACTION and GOTO tables from the collection.
For item set I and symbol X: closure(I) = I ∪ { B → ·γ | A → α·Bβ ∈ I } goto(I, X) = closure( { A → αX·β | A → α·Xβ ∈ I } )

C. Worked Example

Grammar: E → E+T | T, T → T*F | F, F → (E) | id

After augmentation: E' → E

Key item sets:

I0: E'→·E, E→·E+T, E→·T, T→·T*F, T→·F, F→·(E), F→·id I1: E'→E· → accepting (reduce) I2: E→E·+T → shift on '+' I3: E→T· → reduce E→T I4: T→T·*F → shift on '*' I5: T→F· → reduce T→F I6: F→(·E) → goto on '(' I7: F→id· → reduce F→id I8: E→E+T· → reduce E→E+T I9: T→T*·F → goto on 'F' I10: F→(E·) → shift on ')' I11: F→(E)· → reduce F→(E)

LR(0) ACTION table: States on rows, terminals on columns. For each item A → α·aβ, set ACTION[s, a] = shift t where t = goto(s, a). For A → α·, set reduce A → α. For E' → E· in final state, set accept.

D. SLR(1) Improvement

SLR(1) uses FOLLOW sets: for item A → α·, instead of reducing on every terminal, reduce only on terminals in FOLLOW(A). This eliminates some spurious conflicts present in LR(0).

E. Conflict Detection

A shift-reduce conflict: same state has both a shift on terminal a and a reduce by A → α on a. A reduce-reduce conflict: two different reductions in the same state for the same lookahead. SLR(1) still reports conflicts for grammars that CLR(1) handles (e.g., the dangling-else grammar without modification).

Draw the DFA of LR(0) item sets. Show I0 through I11. Then show the ACTION/GOTO tables. Explain where SLR(1) differs from LR(0) in reduce actions.
Q: Explain top-down parsing. Construct the LL(1) parsing table for a given grammar and trace the parsing of an input string. 15M

A. Top-Down Parsing

Top-down parsing attempts to derive the input string from the start symbol S by expanding non-terminals left-to-right. It constructs the parse tree from root to leaves. A recursive descent parser uses a separate procedure per non-terminal. Predictive (LL(1)) parsing uses a parsing table with 1-token lookahead to choose productions without backtracking.

B. Elimination of Left Recursion and Left Factoring

For LL(1), the grammar must have no left recursion and must be left-factored. Immediate left recursion elimination:

A → Aα₁ | Aα₂ | … | Aβ | γ becomes: A → γA' A' → α₁A' | α₂A' | … | αₖA' | ε

Left factoring: When two productions share a common prefix α:

A → αβ₁ | αβ₂ | … | αβₖ | γ becomes: A → αA' | γ A' → β₁ | β₂ | … | βₖ

C. LL(1) Parsing Table Construction

Given grammar G (after preprocessing):

  1. Compute FIRST(α) for each RHS α.
  2. Compute FOLLOW(A) for each non-terminal A.
  3. For each production A → α: for each a ∈ FIRST(α), set M[A, a] = A → α. If ε ∈ FIRST(α), for each b ∈ FOLLOW(A), set M[A, b] = A → α.

D. Worked Example

Grammar: E → T E', E' → + T E' | ε, T → id

FIRST(E) = {id}, FIRST(E') = {+, ε}, FIRST(T) = {id}

FOLLOW(E) = {$}, FOLLOW(E') = {$}, FOLLOW(T) = {+, $}

Parsing Table: id + $ E → T E' - - E' → - → + T E' → ε T → id - -

Unit 4: Syntax Directed Translation

4 Lectures · 10 Questions
Q: What is a syntax-directed definition (SDD)? 1M

An SDD is a CFG with semantic rules (attributes) attached to grammar symbols. It specifies how to compute attribute values at each node of the parse tree.

Q: What is a synthesized attribute? 1M

A synthesized attribute is computed from the attribute values of children in the parse tree. Value flows bottom-up (children → parent). E.g., the value of an expression.

Q: What is an inherited attribute? 1M

An inherited attribute is computed from parent and/or siblings (not children). Value flows top-down or left-to-right. E.g., type of a variable propagated to its usage.

Q: What is an S-attributed definition? 1M

An S-attributed SDD uses only synthesized attributes. It can be evaluated during a bottom-up (LR) parse using a post-order traversal of the parse tree.

Q: What is an L-attributed definition? 1M

An L-attributed SDD allows inherited attributes but restricts them: inherited attributes of a symbol in a production can only depend on attributes to the left. L-attributed SDDs can be evaluated during a top-down (LL) parse.

Q: Explain S-attributed and L-attributed definitions with examples. 5M

S-attributed Definitions: Use only synthesized attributes. Evaluated in a bottom-up traversal (post-order). All semantic actions are placed at the right end of the production.

Example (expression value): E → E₁ + T { E.val = E₁.val + T.val } E → T { E.val = T.val } T → num { T.val = num.lexval }

L-attributed Definitions: Allow inherited attributes with the restriction that inherited attributes of symbol Xᵢ can only depend on: (1) attributes of symbols to the left (X₁…Xᵢ₋₁), (2) the inherited attributes of the parent. Can be evaluated during a top-down parse.

Example (type checking in declarations): D → T id { id.inhtype = T.type } T → int { T.type = integer } T → real { T.type = real }

The inherited attribute inhtype flows from the parent non-terminal T to the child id. This is valid L-attributed because id's inherited attribute depends only on T, which is to its left.

Q: What is a syntax directed translation scheme (SDTS)? Give an example. 5M

A Syntax Directed Translation Scheme (SDTS) is an SDD where semantic actions are embedded within the productions of the grammar. The actions are fragments of code to be executed when the production is used during parsing.

The order of semantic actions must respect attribute dependencies:

  • In a bottom-up parse, actions are placed at the right end (S-attributed).
  • In a top-down parse, actions are placed to compute inherited attributes before their use (L-attributed).
Example — generating 3AC from expressions: E → E₁ + T { E.place = newtemp(); emit(E.place, '=', E₁.place, '+', T.place) } E → T { E.place = T.place } T → T₁ * F { T.place = newtemp(); emit(T.place, '=', T₁.place, '*', F.place) } T → F { T.place = F.place } F → ( E ) { F.place = E.place } F → num { F.place = num.place }

Each production's semantic action generates a Three-Address Code instruction. The function newtemp() allocates a new temporary variable.

Q: Explain bottom-up evaluation of S-attributed definitions and top-down evaluation of L-attributed definitions. 15M

A. Bottom-Up Evaluation of S-Attributed SDD

S-attributed definitions have only synthesized attributes. During a bottom-up (LR) parse, a parse tree is implicitly built. When a reduction A → α is performed, the semantic action fires, computing A's synthesized attributes from the attribute values already stored in the stack records for symbols in α.

Implementation via the parser stack: Each stack entry holds a record with the grammar symbol and its synthesized attributes. On reduction A → α, pop |α| records, evaluate the semantic action using those values, and push a new record for A with its computed attributes.

Stack entry format: (symbol, {attr₁: val₁, attr₂: val₂, …}) On reduction by A → B C: pop B_rec, pop C_rec A_rec.synth_attr = f(B_rec.synth_attr, C_rec.synth_attr) push A_rec

B. Top-Down Evaluation of L-Attributed SDD

L-attributed definitions allow inherited attributes. During a top-down (LL) parse, inherited attributes are passed down before expanding a non-terminal. For a production A → X₁ X₂ … Xₙ:

  • Before expanding X₁: compute inherited attributes of X₁ from A's inherited attributes.
  • Before expanding Xᵢ (i > 1): compute inherited attributes of Xᵢ from A's inherited attributes and the synthesized attributes of X₁…Xᵢ₋₁.
  • Synthesized attributes of A are computed after all children are expanded.
Example: D → T id { id.inh = T.type } ← inherited attr passed left-to-right During D → T id: Step 1: Expand T, compute T.type (synthesized) Step 2: Before expanding id, set id.inh = T.type

C. Key Differences

Unit 5: Type Checking

3 Lectures · 8 Questions
Q: What is type checking in a compiler? 1M

Type checking verifies that the operands of an operator are of compatible types. It is performed during the semantic analysis phase, typically by traversing the syntax tree and applying type rules.

Q: What is a type expression? 1M

A type expression is a formula that denotes a type. Basic types (int, real, char) are atomic. Composite types are formed using type constructors: array, record, function, pointer.

Q: What is type coercion? 1M

Type coercion is the implicit conversion of one type to another by the compiler when types in an expression don't match but are compatible (e.g., int → float in mixed-mode arithmetic).

Q: What is a type environment? 1M

A type environment (or type map) is a function mapping identifiers to their types. It is extended during declaration processing and queried during expression type checking.

Q: Explain type equivalence — name equivalence vs structural equivalence. 5M

Type Equivalence determines whether two type expressions denote the same type:

  • Name equivalence: Two types are equivalent if they have the same name (from the same declaration). Simple and safe. Used by languages like Pascal.
  • Structural equivalence: Two types are equivalent if they have the same structure (same base type, same number of fields with equivalent types). Used by languages like C (with typedef, it gets complicated).

Example: In C, typedef int Age; — int and Age may or may not be equivalent depending on the language's rules. Ada uses name equivalence strictly.

Structural equivalence can be expensive (recursive comparison). Name equivalence is O(1) but less flexible for typedefs.
Q: Explain type conversion rules and their implementation in a compiler. 5M

Type Conversion occurs when operands in an expression have different but compatible types. There are two forms:

  • Widening (promotion): Converting a narrower type to a wider one (e.g., short → int, int → float). No information loss.
  • Narrowing: Converting a wider type to a narrower one (e.g., float → int). May lose information.

Implementation: The type checker applies conversion rules during traversal of the AST. For example, in C, integer promotion happens before arithmetic: char + int promotes char to int. In mixed-mode int + float, int is widened to float.

Type rules (inference rules): E → E₁ + E₂ type(E) = type(E₁) + type(E₂) If type(E₁) ≠ type(E₂): apply coercion If compatible: widen narrower type Else: type error

The semantic action inserts an explicit conversion node (e.g., float(i)) in the IR when widening is needed.

Q: Explain the type checking process in detail, including type expressions, type environments, and polymorphic functions. 15M

A. Type Expressions

A type expression describes a type. Basic types are atomic. Composite types use constructors:

  • Array: array(type, index-range), e.g., array(int, 1..10)
  • Record/Struct: record(f₁:t₁, f₂:t₂, …)
  • Function: function(param-types) → return-type
  • Pointer: pointer to type
  • Union/Enum: sum of alternatives

B. Type Environments

A type environment T maps identifiers to type expressions. Initially empty. During declaration processing, T is extended: T(x) = type(x). During expression checking, T is consulted for identifier types.

C. Type Checking Rules (Inference Rules)

For each expression form, a typing rule specifies how to check and what type to assign:

E → E₁ + E₂: if type(E₁) = int and type(E₂) = int → type(E) = int if type(E₁) = real and type(E₂) = real → type(E) = real if compatible (one int, one real) → type(E) = real, insert conversion else → TYPE ERROR

D. Polymorphic Functions

Polymorphism allows a function to operate on arguments of multiple types:

  • Parametric polymorphism (generics): a function has a type parameter. E.g., length(list<T>) works for any T.
  • Overloading: multiple functions with same name but different parameter types. Resolved at compile time.
  • Coercion polymorphism: implicit type conversions make a function appear polymorphic.

Implementation: The type checker generates a type-scheme for each polymorphic function. When the function is called, the compiler instantiates the type-scheme with actual types (Hindley-Milner type inference in ML/Haskell).

E. Overloading Resolution

When multiple versions of a function exist, the compiler selects the most specific matching type. Ambiguity (no unique best match) is a compile-time error.

Key exam points: type environment as a function, inference rules format, three kinds of polymorphism, and how type checking is integrated into the semantic analysis phase via tree traversal.

Unit 6: Run Time Environments

4 Lectures · 9 Questions
Q: What is an activation record (AR)? 1M

An activation record (AR) (or stack frame) is a block of memory allocated on the call stack for each function invocation. It contains: parameters, return address, return value, control link, access link, and local variables.

Q: What is a control link in an activation record? 1M

A control link (dynamic link) points to the activation record of the caller. It allows the runtime to restore the caller's AR when the callee returns.

Q: What is an access link in an activation record? 1M

An access link (static link) points to the AR of the lexically enclosing scope. Used for accessing non-local variables in nested/non-local scopes (block-structured languages).

Q: What is the display data structure? 1M

A display is an array of pointers to activation records, one per nesting depth. display[d] points to the AR of the innermost active procedure at depth d. Allows O(1) access to non-local variables.

Q: What is variable-length data in an AR? How is it handled? 1M

Variable-length data (sized arrays, dynamic locals) is placed above the fixed part of the AR. A pointer to the top (SP) is kept. The compiler generates code to access them via offsets from this pointer.

Q: Explain the organization of an activation record with a diagram. 5M

An activation record is organized as follows (on the runtime stack, growing downward):

High Addresses ┌──────────────────────┐ │ Actual Parameters │ │ Return Value │ │ Return Address │ │ Saved Registers │ │ Control Link (dyn) │ │ Access Link (static) │ │ Local Variables │ │ Temporaries │ │ Variable-Length Data │ ← SP └──────────────────────┘ Low Addresses

Fields explained:

  • Actual Parameters: Arguments passed by caller (above the AR boundary).
  • Return Value: Space for the function's return value.
  • Return Address: Where to resume execution in the caller.
  • Saved Registers: Callee-saved registers pushed before use.
  • Control Link: Pointer to caller's AR (for stack unwinding).
  • Access Link: Pointer to the lexically enclosing AR (for nested scopes).
  • Local Variables: Fixed-size locals, addressed by offset from FP.
  • Temporaries: Intermediate results from expression evaluation.
  • Variable-Length Data: Dynamically sized arrays.

Access: A frame pointer (FP) points to the middle of the AR. Offsets to local variables are computed from FP. The stack pointer (SP) points to the top.

Q: Explain static vs dynamic scoping. Describe how access links and displays are used for non-local variable access. 15M

A. Static vs Dynamic Scoping

Static (lexical) scoping: The scope of a variable is determined at compile time by the program's textual structure. A non-local variable reference is resolved to the lexically enclosing declaration.

Dynamic scoping: The scope of a variable is determined at runtime by the call chain. A non-local variable reference is resolved to the most recent activation of a procedure that declared the variable.

Example: int x = 10; void f() { print(x); } void g() { int x = 20; f(); } Static: f() prints 10 (f's enclosing scope declares x=10) Dynamic: f() prints 20 (g's activation has x=20, and g called f)

B. Access Links (Static Links)

In a block-structured language with static scoping, each AR contains an access link pointing to the AR of the lexically enclosing procedure. To access a non-local variable at nesting depth d, the compiler knows the nesting depth of the reference and follows d access links.

Cost: Accessing a variable at depth difference k requires following k access links — O(k) time.

C. Display Data Structure

A display is an array D[0..max_depth] where D[i] always points to the AR of the innermost active procedure at nesting depth i. When a procedure at depth d is called, D[d] is saved and replaced by the new AR pointer. On return, D[d] is restored.

Cost: O(1) access to any non-local variable regardless of nesting depth. The trade-off is O(1) overhead per call/return for saving/restoring the display entry.

Unit 7: Intermediate Code Generation

4 Lectures · 10 Questions
Q: What is Three-Address Code (TAC)? 1M

Three-Address Code (TAC) is an intermediate representation where each instruction performs at most one operation and has at most three addresses (operands). E.g., x = y + z. It resembles assembly but is machine-independent.

Q: What is a quadruple (quad)? 1M

A quadruple is a 4-tuple (op, arg₁, arg₂, result) representing a 3AC instruction. For unary/branching ops, unused fields are empty. Quads are easy to generate and optimize.

Q: What is a triple? 1M

A triple is a 3-tuple (op, arg₁, arg₂) where arguments refer to instruction positions (pointers) instead of temporary names. Useful when instruction ordering changes during optimization.

Q: What is an indirect triple? 1M

An indirect triple uses a separate list of pointers to triples. It avoids updating pointers when triples are reordered — only the pointer list needs updating.

Q: What is the purpose of backpatching? 1M

Backpatching is a technique to handle forward jumps in boolean code generation. When the target address of a jump is unknown, a placeholder is left. A list of pending jumps is maintained and filled in when the target label is generated.

Q: Generate Three-Address Code for the expression: a = (b + c) * (d - e) + f * g. Show quads and triples. 5M

Source: a = (b + c) * (d - e) + f * g

Step 1 — Decompose into TAC:

t1 = b + c t2 = d - e t3 = t1 * t2 t4 = f * g t5 = t3 + t4 a = t5

Step 2 — Quadruples:

(+, b, c, t1) (-, d, e, t2) (*, t1, t2, t3) (*, f, g, t4) (+, t3, t4, t5) (=, t5, -, a)

Step 3 — Triples (instruction positions as references):

(0): (+, b, c) (1): (-, d, e) (2): (*, 0, 1) (3): (*, f, g) (4): (+, 2, 3) (5): (a, =, 4)

In triples, t3 and t5 are replaced by instruction indices (2 and 4 respectively).

Q: Explain backpatching with an example of boolean code generation for if and if-else statements. 5M

Backpatching is used when generating code for boolean expressions and control-flow statements where jump targets are not yet known.

Mechanism: Maintain a list of quadruple indices for each pending jump. When the target address becomes known, backpatch all pending jumps to that address.

makelist(i) = [i] merge(p1,p2) = p1 ∪ p2 backpatch(p, m) = fill quad[p].result = m for each p ∈ pending list

Example — if (B) S:

gen('if B.goto -') → quad index i, pending list B.truelist = [i] backpatch(B.truelist, nextquad) gen S.code → nextquad points here

Example — if (B) S₁ else S₂:

gen('if B.goto -') → i, B.truelist backpatch(B.truelist, nextquad) → jump to S₁ gen S₁.code gen('goto -') → j, S₁.nextlist backpatch(S₁.nextlist, nextquad) → after S₁ gen S₂.code backpatch(B.falselist, S₂.address)

The truelist of B is patched to the start of S₁; the falselist to the start of S₂. After S₁, a goto skips S₂.

Always use makelist, merge, and backpatch in your answer. Draw the quad indices showing where each patch occurs.
Q: Explain in detail: (i) Three-address code and its representations (quads, triples, indirect triples), and (ii) Translation of boolean expressions and control flow statements using backpatching. 15M

A. Three-Address Code (TAC)

Three-Address Code is the most common IR. Each instruction has at most three operands and performs one operation. It is the natural output of syntax-directed translation.

Types of TAC instructions:

  • Assignment: x = y op z
  • Copy: x = y
  • Unary: x = op y
  • Conditional jump: if x relop y goto z
  • Unconditional jump: goto L
  • Procedure call: param x; call p, n
  • Indexed access: x = y[i]
  • Address/pointer: x = &y; x = *y; *x = y

B. Quadruples (Quads)

A quadruple has four fields: (operator, arg1, arg2, result). Each instruction is identified by its position (index). Temporary names are explicit.

op arg1 arg2 result 0: + b c t1 1: * t1 t2 t3 2: = t3 - a

Pros: Easy to generate, clear naming. Cons: Names are not updated when instructions are reordered during optimization.

C. Triples

A triple has (op, arg1, arg2) where arg1 and arg2 refer to instruction positions (or symbol table indices). No temporary names needed.

op arg1 arg2 0: + b c 1: - d e 2: * 0 1 3: + 2 t4 ← t4 from elsewhere

Pros: Names automatically update when order changes. Cons: Harder to read, pointer arithmetic needed.

D. Indirect Triples

An indirect triple stores pointers to triples in a separate list. Reordering is done by changing the pointer list, not the triples themselves.

Triples: 0: (+, b, c) 1: (*, 0, 2) 2: (a, =, 1) Pointer list: → 0 → 1 → 2

E. Boolean Expressions and Backpatching

Boolean expressions in an if-statement generate code with conditional and unconditional jumps. Because the target addresses of jumps may not be known when the conditional is generated, backpatching is used.

For "if B goto L": generate quad "if B.goto -", record its index in a pending list. When L is known: backpatch(pending_list, L).

Translation of S → if B then S₁:

S.nextlist = merge(B.falselist, S₁.nextlist) gen('goto -') → pending

Translation of S → if B then S₁ else S₂:

backpatch(B.truelist, S₁.instr) S₁.nextlist → merge with goto backpatch(B.falselist, S₂.instr) S.nextlist = merge(S₁.nextlist, S₂.nextlist)

While loop translation (S → while B do S₁):

marker = nextquad ← loop start gen B.code backpatch(B.truelist, S₁.instr) gen S₁.code gen('goto marker') ← loop back backpatch(B.falselist, nextquad) ← exit
Always draw the quad list with indices. Show how truelist/falselist/nextlist flow through productions. Backpatching is a very common 15-mark question.

Unit 8: Code Optimization

5 Lectures · 12 Questions
Q: What is code optimization? 1M

Code optimization transforms the intermediate representation to produce more efficient target code — faster execution, smaller size, or lower power consumption — while preserving the original program's semantics.

Q: What is a basic block? 1M

A basic block is a sequence of statements where control enters at the first statement and leaves at the last without any jumps in between (except at the end). All statements in a block are executed sequentially.

Q: What is a leader in basic block construction? 1M

A leader is the first statement of a basic block. Leaders are: (1) the first statement, (2) any target of a goto/branch, (3) any statement immediately following a goto/branch.

Q: What is a Directed Acyclic Graph (DAG) in optimization? 1M

A DAG for a basic block is a graph where interior nodes are operators, leaves are operands, and each node stores the value of the subexpression it represents. Common subexpressions are merged into a single node.

Q: What is peephole optimization? 1M

Peephole optimization examines a small sliding window ("peephole") of target instructions and applies local transformations: dead code elimination, constant folding, algebraic simplification, etc.

Q: What is constant folding? 1M

Constant folding evaluates constant expressions at compile time. E.g., 3 + 5 → 8. Done during code optimization on the IR.

Q: What is loop optimization? Name two loop optimizations. 1M

Loop optimization improves code inside loops (which dominate runtime). Two techniques: Code motion (invariant code moved out of loop) and Induction variable elimination (replace array-index arithmetic with simpler increments).

Q: Explain the construction of basic blocks and the flow graph. 5M

Step 1 — Identify Leaders: A statement is a leader if: (1) it is the first statement, (2) it is the target of a conditional/unconditional goto, or (3) it immediately follows a goto.

Step 2 — Form Basic Blocks: Each block starts at a leader and ends just before the next leader.

Step 3 — Build Flow Graph: Nodes are basic blocks. Add edge B₁ → B₂ if B₂ can immediately follow B₁. Designate an Entry node and an Exit node.

Example: 1: a = b + c ← Leader 1 2: goto 6 3: x = y * z ← Leader 2 4: if x > 0 goto 3 ← Leader 3 5: a = d - e 6: ...

Blocks: B₁={1,2}, B₂={3}, B₃={4}, B₄={5,6}. Edges: B₁→B₂, B₁→B₄, B₂→B₃, B₃→B₂, B₃→B₄.

Dominators: Node d dominates n if every path from entry to n passes through d. Loops are identified via back edges (edges to dominating nodes).

Q: Construct the DAG for the following basic block and explain optimizations.
a = b + c; b = a - d; c = b + c; d = a - d; 5M

Step 1 — Draw the DAG:

(+) / \ b c → t1 (= b+c) (t1 stored at 'a') (-) / \ t1 d → t2 (= t1-d) (t2 stored at 'b') (+) / \ t2 c → t3 (= t2+c) (t3 stored at 'c') (-) / \ t1 d → t4 (= t1-d) ← same as t2! (t4 stored at 'd')

Step 2 — Apply optimizations:

  • Common subexpression elimination: The second a-d (statement 4) is the same as b = a - d (statement 2). The DAG merges both into one (-) node. So d = t2 — no new computation.
  • Dead code elimination: If a is never used after this block, the first computation a = b+c is dead.
  • Optimized code:
    t1 = b + c
    b = t1 - d
    c = b + c
    d = t1 - d     (only 3 operations instead of 4)
Q: Explain code optimization techniques: local optimization (constant folding, CSE, DAG), loop optimization, and peephole optimization. 15M

A. Local Optimization (Within a Basic Block)

Local optimizations apply to a single basic block without considering control flow across blocks.

1. Constant Folding: Evaluate constant expressions at compile time.

Before: x = 3 + 5 * 2 After: x = 13

2. Algebraic Simplification: Apply algebraic identities.

x + 0 → x x * 1 → x x * 0 → 0 x - x → 0

3. Common Subexpression Elimination (CSE): If a+b is computed twice with unchanged operands, compute once and reuse.

4. Dead Code Elimination: Remove assignments to variables that are never used later.

5. DAG Representation: The DAG for a basic block merges common subexpression nodes, enabling efficient CSE and copy propagation.

B. Loop Optimization

Loops are the most frequently executed parts of a program. Loop optimizations include:

  • Code Motion (Loop Invariant Code Motion): Move computations whose values don't change across iterations outside the loop.
    for i=1 to n: x = a[i]; y = a[i] + c; → for i=1 to n: x = a[i]; y = x + c;
  • Induction Variable Elimination: Replace array index calculations with simple increments.
    j = 4*i inside a loop where i increments by 1 → j = j + 4
  • Loop Unrolling: Repeat loop body multiple times to reduce branch overhead.
  • Loop Fusion: Combine two loops with the same iteration range into one.

C. Peephole Optimization

Peephole optimization examines a small window of consecutive instructions and applies replacement rules. Applied after code generation or on the IR.

  • Unreachable code elimination: goto L; ...; L: ... — remove code between goto and its target if not jumped to.
  • Redundant load/store elimination: x = y; ... = x → ... = y
  • Algebraic simplifications: x = x + 0 → delete; x = x * 1 → delete.
  • Single use / single assignment: Merge if a variable is assigned once and used once.
Draw a DAG for a basic block with common subexpressions. Show the optimized sequence of quads. Loop optimization questions often ask for induction variable elimination — show the before/after code.

Unit 9: Code Generation

4 Lectures · 10 Questions
Q: What is code generation in a compiler? 1M

Code generation is the final compiler phase that translates the intermediate representation (optimized IR) into the target machine language (object code). It involves instruction selection, register allocation, and instruction scheduling.

Q: What is register allocation? 1M

Register allocation assigns program variables to CPU registers (fast) or memory (spill) to minimize execution time. The graph coloring algorithm maps variables to a limited set of registers.

Q: What is a call graph? 1M

A call graph is a directed graph where nodes are procedures and edges represent procedure calls. Used for interprocedural analysis and register allocation across function boundaries.

Q: What is a usage count of a register? 1M

Usage count = (uses × cost-of-not-in-register) / (defs × cost-of-spill). It estimates how much benefit keeping a variable in a register provides, guiding register allocation decisions.

Q: What is a next-use information? 1M

Next-use information records for each variable definition the next statement where that variable is used. If a variable is not used again, its register can be freed immediately (dead variable).

Q: Explain the issues in code generation: (i) instruction selection, (ii) register allocation, and (iii) evaluation order. 5M

1. Instruction Selection: Choose target machine instructions to implement each IR operation. Simple approach: one-to-one mapping (TAC → assembly). Better approaches use templates or tree rewriting to match instruction patterns and cover multiple IR operations in one instruction (e.g., MOVE R1, M[R0] addressing modes).

2. Register Allocation: Assign frequently used variables to CPU registers. Since the number of registers is limited (typically 16–32), some variables must be spilled to memory. The standard method is graph coloring: build an interference graph where nodes are variables and edges connect simultaneously live variables. Color the graph with k colors (k = number of registers). If more than k colors are needed, spill the variable with the lowest usage count.

3. Evaluation Order: The order in which operands are evaluated affects register pressure. Strategies include: evaluate left-to-right, evaluate right-to-left (to free registers sooner), or use a heuristic based on usage counts. The goal is to minimize live ranges of temporaries.

Q: Explain the simple code generation algorithm using next-use information. 5M

The simple code generation algorithm processes a basic block left-to-right and decides for each variable whether to keep it in a register or spill to memory based on next-use information:

  1. Compute next-use: For each definition, find the next statement where the variable is used. Variables with no future use are "dead."
  2. Maintain a set of live variables and available registers.
  3. For each statement x = y op z:
    If y is not in a register and is live → load y into a register.
    If z is not in a register and is live → load z into a register.
    Generate the operation.
    If x was previously in a register and is dead → free that register.
    Assign x to a register (prefer the register holding y if y is dead).

Register selection strategy: Prefer the register that holds a variable that will not be used again (dead). If all registers hold live variables, spill the one with the farthest next-use (or lowest usage count).

For statement: t = a + b 1. Ensure a is in register Ra (load if needed) 2. Ensure b is in register Rb (load if needed) 3. ADD Ra, Rb, Rt 4. Record that t is in Rt
Q: Explain code generation in detail, covering instruction selection strategies, register allocation by graph coloring, and a simple code generation algorithm with a worked example. 15M

A. Instruction Selection

Instruction selection maps IR operations to target machine instructions. Two main approaches:

  • Direct translation: Each IR instruction → one machine instruction. Simple but not optimal.
  • Pattern matching (tree covering): The IR is represented as a tree. Instruction templates match subtrees. A dynamic programming algorithm finds the minimum-cost covering. This can match multiple IR operations into one complex machine instruction.

Example: For a = b + c * d, a direct translation gives t1 = c * d; a = b + t1 (2 instructions). With pattern matching, MUL R1, c, d; ADD a, b, R1 — even better on architectures with complex addressing modes like MOVE a, b(c,d).

B. Register Allocation by Graph Coloring

When the number of simultaneously live variables exceeds the number of CPU registers, we must spill some variables to memory.

Algorithm (iterative approach):

  1. Build the interference graph: nodes = variables; edge (u,v) exists if u and v are simultaneously live.
  2. If a node has degree < k (fewer than k neighbors), remove it (it can always be colored).
  3. If all remaining nodes have degree ≥ k, pick a variable with the lowest usage count as the spill candidate.
  4. After coloring, if a spill was needed, insert load/store instructions and repeat.
Usage count formula: usage(v) = Σ(uses(v) × cost_not_in_reg + defs(v) × cost_spill) Spill the variable with the smallest usage(v).

C. Simple Code Generation Algorithm with Next-Use

Next-use information: for each definition of a variable x, record the next statement where x is used. Computed by a backward scan of the block.

Algorithm:

  1. Initialize all registers as free.
  2. For each statement x = y op z in order:
    a. If y is not in a register and y is live → load y into a free register.
    b. If z is not in a register and z is live → load z into a free register.
    c. If no free register → spill the register whose variable has the farthest next-use.
    d. Generate the machine instruction.
    e. If the register previously holding x has x dead → free it.
    f. Mark x as in the result register.

D. Worked Example

Basic block (assuming R0 holds a, R1 holds b, R2 holds c):

S1: a = b + c S2: b = a - d S3: c = b + c S4: d = a - d

Next-use table:

Variable Defined in Next used in a S1 S2, S4 b S2 S3 c S3 (none) d S4 (none)

Code generation (k=3 registers):

S1: ADD R0, R1, R2 // a = b+c; a in R0 S2: SUB R0, R3, R0 // b = a-d; load d into R3 first MOV R0, R1 // b now in R1 S3: ADD R1, R2, R1 // c = b+c; c now in R1 (was b, now dead) S4: SUB R0, R3, R0 // d = a-d; d in R3 (was R1 holding c, now dead)
Show the interference graph: a, b, c, d all interfere pairwise (simultaneously live at some points). With 3 registers and 4 variables, one must be spilled. Show which one and why.
