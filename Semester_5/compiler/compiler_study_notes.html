Introduction

Compiler phases, interpreter, symbol table, pass structure

Compiler vs Interpreter

A compiler translates the entire source program into an equivalent target program (machine code) before execution. An interpreter translates and executes the source program statement-by-statement, one at a time.

Key differences:

  • Execution speed: Compiled programs run faster; interpreted programs are slower since translation happens at runtime.
  • Translation time: Compilers take longer upfront but produce standalone executables; interpreters start executing immediately.
  • Error detection: Compilers report all errors after full scan; interpreters stop at the first error.
  • Output: Compilers produce a separate target program; interpreters produce no separate output.

Phases of a Compiler

A compiler operates in well-defined phases that transform source code into target code:

  • Lexical Analysis: Reads the source character stream and groups characters into lexemes, producing tokens.
  • Syntax Analysis: Checks the token stream against grammar rules, producing a parse tree.
  • Semantic Analysis: Verifies type rules, scope, and meaning. Performs type checking.
  • Intermediate Code Generation: Produces an intermediate representation (e.g., three-address code).
  • Code Optimization: Improves intermediate code for speed, memory, or power efficiency.
  • Code Generation: Translates optimized IR into target machine code with register allocation.

The Symbol Table is a data structure used by all phases to store information about identifiers (names, types, scopes, memory locations).

Symbol Table

The symbol table is a critical data structure maintained throughout compilation. It stores entries for every identifier (variable, function, class, etc.) with attributes such as:

  • Name: The identifier string
  • Type: Integer, float, array, function, etc.
  • Scope: Where the identifier is visible
  • Memory location: Where the value will be stored
  • Size: Memory footprint
  • Parameters: For functions, parameter list

Operations: insert (add new identifier), lookup (find identifier), delete (remove when scope ends). Implemented using hash tables or search trees for efficiency.

Cross-Compiler and Bootstrap

A cross-compiler is a compiler that runs on one platform (host) but produces executable code for a different platform (target). Used when the target machine doesn't have its own compiler, or for embedded systems.

Bootstrapping is the process of writing a compiler for a new language using the language itself. Steps:

  • Write a minimal compiler for a subset of language L in an existing language (say C). This compiler can compile itself.
  • Use this compiler to compile an extended compiler that supports more features.
  • Iterate until the full compiler for L is built. This is how compilers like GCC were developed.

Lexical and Syntax Analyzers

The lexical analyzer (lexer/scanner) is the first phase. It reads input characters, groups them into lexemes, and produces tokens. Each token has a token name and an optional attribute value. It removes whitespace and comments.

The syntax analyzer (parser) takes the token stream from the lexer and constructs a parse tree (or AST) based on grammar rules. It checks syntactic structure and reports syntax errors.

Pass Structure

A pass refers to one complete scan of the source program (or its intermediate representation). A compiler may be:

  • Single-pass: Compiles in one go. Faster but limited optimization.
  • Multi-pass: Performs multiple scans. Allows better optimization but slower compilation.
Key Concept: The Analysis-Synthesis model divides compilation into front-end (lexical, syntax, semantic analysis → IR generation) and back-end (optimization → target code). The middle represents the IR. This separation allows retargeting the compiler to new architectures by only modifying the back-end.

Explain the phases of a compiler in detail with a block diagram. Discuss the role of each phase and the symbol table.

A compiler processes source code through six logical phases, supported by two auxiliary components — the Symbol Table and the Error Handler.

Source → [Lexical Analyzer] → Tokens Tokens → [Syntax Analyzer] → Parse Tree Tree → [Semantic Analyzer] → Annotated Tree Tree → [Intermediate Code Gen] → Three-Address Code TAC → [Code Optimizer] → Optimized IR IR → [Code Generator] → Target Code (Symbol Table & Error Handler interact with ALL phases)

1. Lexical Analyzer (Scanner): Reads source characters, removes whitespace/comments, and groups characters into lexemes. Outputs a stream of tokens <token-name, attribute-value>. Example: int x = 10; becomes <INT, ->, <ID, "x">, <ASSIGN, ->, <NUM, 10>, <SEMI, ->.

2. Syntax Analyzer (Parser): Uses grammar rules (context-free grammar) to verify syntactic structure. Builds a parse tree where internal nodes are non-terminals and leaves are tokens. Reports syntax errors.

3. Semantic Analyzer: Performs type checking, verifies operator-operand compatibility, checks scope rules, and adds semantic information to the parse tree. Reports type-mismatch errors.

4. Intermediate Code Generator: Produces a machine-independent intermediate representation, typically three-address code (TAC) with at most one operator per instruction. Example: x = a + b * c becomes t1 = b * c; t2 = a + t1; x = t2.

5. Code Optimizer: Applies transformations to improve the IR — constant folding, dead code elimination, common subexpression elimination, loop optimizations. Output is semantically equivalent but more efficient IR.

6. Code Generator: Translates optimized IR into target machine code. Performs instruction selection, register allocation, and memory addressing. Final output is assembly or machine code.

Symbol Table Role: Stores identifier attributes (name, type, scope, memory address). Inserted during lexical analysis, updated during semantic analysis, and consulted during code generation for memory allocation.

Error Handler: Detects, reports, and recovers from errors in any phase. Aims to continue compilation to find as many errors as possible in one pass.

Lexical Analysis

Tokens, regular expressions, finite automata, NFA, DFA, Lex

Tokens, Lexemes, and Patterns

The lexical analyzer works with three core concepts:

  • Token: A pair consisting of a token name and an optional attribute value. Example: <identifier, "x">. Token names: id, num, +, *, etc.
  • Lexeme: The actual character sequence matched by a token. For example, the lexeme "counter" is matched by the token id.
  • Pattern: A rule that describes the set of lexemes that match a token. Usually expressed as a regular expression. Example: pattern for identifier = letter (letter | digit)*

Lexical Errors

Lexical errors occur when the input cannot be matched by any token pattern. Common examples:

  • Invalid characters (e.g., @ in C)
  • Unterminated string literals
  • Malformed numeric constants
  • Identifier too long

Recovery strategies: skip the offending character, insert a missing character, replace with a valid one, or delete a character.

Regular Expressions

A regular expression (RE) defines a set of strings over an alphabet. Rules:

  • ε (epsilon) is a regular expression denoting {ε}
  • a for any symbol a in the alphabet denotes {a}
  • (r)|(s) — union: either r or s
  • (r)(s) — concatenation: r followed by s
  • (r)* — Kleene closure: zero or more occurrences of r
  • (r)+ — one or more r

Example: identifier = letter (letter | digit)*

Finite Automata — NFA and DFA

A finite automaton (FA) is a recognizer for regular expressions. It has 5 components: states (Q), input alphabet (Σ), transition function (δ), start state (q0), and accept states (F).

  • NFA (Nondeterministic FA): Can have multiple transitions for the same input symbol, including ε-transitions. A string is accepted if ANY computation accepts it.
  • DFA (Deterministic FA): Exactly one transition per input symbol from each state. No ε-transitions. Faster to simulate than NFA.

Every NFA can be converted to an equivalent DFA; both recognize the same language. NFA is easier to construct from RE; DFA is easier to implement.

RE to NFA — Thompson's Construction

Thompson's construction builds an NFA from a regular expression by combining smaller NFAs. Rules:

  • For symbol a: create a 2-state NFA with a-transition.
  • For r|s (union): add new start state with ε-transitions to sub-NFAs; merge accept states with ε to new accept.
  • For rs (concatenation): connect accept of r to start of s with ε.
  • For r* (closure): add new start with ε to r's start and accept; loop back from r's accept to its start.

NFA to DFA — Subset Construction

The subset construction algorithm converts an NFA to an equivalent DFA:

  • Each DFA state represents a set of NFA states (subset).
  • Start state of DFA = ε-closure of NFA's start state.
  • For each DFA state and input symbol a, the next DFA state = ε-closure of all NFA states reachable by a from any NFA state in the current subset.
  • A DFA state is accepting if its subset contains any NFA accepting state.

Lex Tool

Lex is a tool that automatically generates a lexical analyzer from a specification of tokens described using regular expressions. The Lex program consists of three sections:

  • Declarations: Variable declarations, regex definitions
  • Translation rules: Pattern {Action} pairs
  • Auxiliary functions: User-defined helper code in C

Lex converts the specification into a C program that uses the generated DFA. Flex is the GNU version.

Key Concept: RE → NFA (Thompson's) → DFA (Subset Construction) → Minimized DFA (Hopcroft's). This pipeline is the heart of every modern lexer. The minimized DFA has the minimum number of states and is used for token recognition.

What is DFA?
A DFA (Deterministic Finite Automaton) is a finite state machine where, for each state and input symbol, there is exactly one transition. DFAs have no ε-transitions. They are efficient to simulate and are equivalent in power to NFAs.
5 Marks
Explain NFA to DFA conversion with example.

Convert NFA to DFA using subset construction:

  • Step 1: Start state of DFA = ε-closure of NFA start.
  • Step 2: For each unmarked DFA state S and input symbol a, compute move(S, a) and take its ε-closure. This is a new DFA state.
  • Step 3: Repeat until no new states.
  • Step 4: DFA accepting states = those whose subset contains any NFA accepting state.

Example: Convert RE (a|b)* via NFA → DFA.

The resulting DFA has two states: S0 = ε-closure({start}) = {start, s1, s2, s3} and S1 (after reading 'a' or 'b') = same as S0. So the DFA is essentially a single accepting state with self-loops on 'a' and 'b'.

What are regular expressions in compiler?

Regular expressions are used to formally specify token patterns in the lexical analysis phase. They define a finite language over an alphabet Σ.

Rules:

  • ε is an RE denoting {ε}
  • For each a ∈ Σ, a is an RE denoting {a}
  • If r and s are REs, then r|s, rs, r*, (r) are REs

Examples:

  • Identifier: letter (letter | digit)*
  • Number: digit+ (. digit+)? (E (+|-)? digit+)?
  • Keywords: if | while | return

REs are equivalent in power to finite automata.

Syntax Analysis

Context-free grammar, parsing techniques, LL(1), LR parsers, YACC

Context-Free Grammar (CFG)

A context-free grammar is a 4-tuple G = (V, T, P, S):

  • V: Set of non-terminals (variables)
  • T: Set of terminals (tokens)
  • P: Set of productions (rules) of form A → γ where A ∈ V
  • S: Start symbol (S ∈ V)

CFGs describe the syntactic structure of programming languages. Example: E → E + T | T; T → T * F | F; F → ( E ) | id

Parse Tree and Ambiguity

A parse tree (derivation tree) is a graphical representation of a derivation. The root is the start symbol; internal nodes are non-terminals; leaves are terminals. The yield of the tree (concatenation of leaves) gives the derived string.

A grammar is ambiguous if there exists a string with two or more distinct parse trees (or two distinct leftmost derivations). Example: E → E + E | E * E | id is ambiguous because id + id * id has two parse trees (different evaluation orders).

Ambiguity is resolved by:

  • Rewriting grammar to enforce precedence and associativity
  • Adding parenthesization rules
  • Using unambiguous grammars

Left Recursion and Left Factoring

A grammar is left-recursive if it has a production of the form A → Aα. Top-down parsers cannot handle left recursion. It is eliminated as:

A → Aα | β becomes: A → βA'; A' → αA' | ε

Left factoring removes common prefixes from productions to enable predictive parsing:

If A → αβ1 | αβ2, rewrite as: A → αA'; A' → β1 | β2

Top-Down Parsing

Top-down parsers build the parse tree from the root downward. Types:

  • Recursive Descent Parsing: Each non-terminal has a procedure that tries each production. Backtracking may occur. Simple but inefficient.
  • Predictive Parsing (LL(1)): Non-backtracking top-down parser. Uses a parsing table indexed by (non-terminal, lookahead token). Requires LL(1) grammar.

LL(1): First 'L' = Left-to-right scan; second 'L' = Leftmost derivation; '1' = one lookahead symbol.

Bottom-Up Parsing (LR Parsers)

Bottom-up parsers build the parse tree from leaves upward using reduction. Types:

  • LR(0): No lookahead. Simple but may have reduce/reduce conflicts.
  • SLR (Simple LR): Uses FOLLOW sets to resolve conflicts. Slightly more powerful than LR(0).
  • CLR (Canonical LR): Uses LR(1) items. Most powerful but large tables.
  • LALR (Lookahead LR): Merges CLR states with same core. Smaller tables, used in YACC.

LR(k): Left-to-right scan, Rightmost derivation in reverse, k lookahead tokens.

Shift-Reduce Parsing

LR parsing uses a stack with state symbols and grammar symbols. Two actions:

  • Shift: Push current input symbol and next state onto stack.
  • Reduce: Pop the right-hand side of a production and push the left-hand side (with goto state).

The parser uses a parsing table with ACTION (shift/reduce/accept/error) and GOTO (state transitions) entries. Conflicts (shift-reduce or reduce-reduce) make a grammar non-LR.

YACC Tool

YACC (Yet Another Compiler Compiler) is a tool that generates a LALR parser from a grammar specification. A YACC program has three sections:

  • Declarations: C declarations, token definitions (%token, %type)
  • Translation rules: Grammar productions with semantic actions
  • Auxiliary functions: User code in C

YACC resolves shift-reduce conflicts by preferring shift. Output is a C program that calls yylex() to get tokens.

First and Follow Sets

FIRST(α): Set of terminals that begin strings derivable from α. Rules:

  • If X is terminal, FIRST(X) = {X}
  • If X → ε is a production, add ε to FIRST(X)
  • If X → Y1Y2...Yn, add FIRST(Y1) - {ε} to FIRST(X); if ε ∈ FIRST(Y1), add FIRST(Y2), etc.

FOLLOW(A): Set of terminals that can appear immediately after A in some sentential form. Includes $ (end marker). Rules:

  • $ ∈ FOLLOW(S) where S is start symbol
  • If A → αBβ, then FIRST(β) - {ε} ⊆ FOLLOW(B)
  • If A → αB or A → αBβ where ε ∈ FIRST(β), then FOLLOW(A) ⊆ FOLLOW(B)

FIRST and FOLLOW sets are used to build LL(1) and SLR parsing tables.

Key Concept: LL parsers (top-down) build the parse tree from root to leaves and use leftmost derivations. LR parsers (bottom-up) build from leaves to root and trace rightmost derivations in reverse. LR parsers are more powerful — they can handle a larger class of grammars.
Exam Tip: For parsing questions, always compute FIRST and FOLLOW sets first, then construct the parsing table, then trace a string to show acceptance or rejection.

What is parse tree?
A parse tree is a hierarchical graphical representation of a derivation in a context-free grammar. The root is the start symbol; each internal node is a non-terminal and its children represent the right-hand side of a production; leaves are terminals. The yield of leaves gives the derived string.
1 Mark
What is left recursion?
A grammar has left recursion if a non-terminal A has a derivation that begins with A itself. Direct left recursion: A → Aα | β. Indirect left recursion: A → Bα, B → Aβ. Top-down parsers cannot handle left-recursive grammars; it must be eliminated first.
5 Marks
Explain top-down parsing.

Top-down parsing starts from the start symbol and tries to derive the input string by applying productions. The parser builds the parse tree from root to leaves.

  • Recursive Descent: Each non-terminal has a procedure. On a non-terminal A, try each production A → α; if input doesn't match, backtrack and try next production.
  • Predictive Parsing: Non-backtracking. Uses LL(1) parsing table. At each step, based on current non-terminal and lookahead token, the table specifies which production to apply.

Requirements: Grammar must have no left recursion (eliminate first) and no common prefixes (left factor).

5 Marks
What is LL(1) grammar?

A grammar is LL(1) if its parsing table has no multiple entries (no ambiguity). LL(1) means the parser:

  • Scans input Left-to-right
  • Constructs Leftmost derivation
  • Uses 1 lookahead symbol

Condition for LL(1): For any non-terminal A with productions A → α | β, we need FIRST(α) ∩ FIRST(β) = ∅, and if ε ∈ FIRST(α), then FIRST(β) ∩ FOLLOW(A) = ∅.

LL(1) grammars enable efficient predictive parsing using a parsing table indexed by (A, a).

Semantic Analysis & IR

Type checking, syntax-directed translation, three-address code, representations

Type Checking

Type checking is the main activity of semantic analysis. It verifies that the type of each construct matches its expected use. The compiler uses the symbol table to look up declared types and applies type rules.

Examples of checks:

  • Operands of arithmetic operators must be numeric
  • Subscript of an array must be an integer
  • Function arguments must match parameter types
  • Return type must match function declaration

Type conversions (coercion) may be applied automatically: integer → float, int → long.

Type Systems

A type system is a set of rules that assigns types to program constructs. Types classify values (integer, real, character, boolean, pointer, etc.).

Properties:

  • Static typing: Types checked at compile time (C, Java, C++)
  • Dynamic typing: Types checked at runtime (Python, JavaScript)
  • Strong typing: Strict type rules, fewer implicit coercions
  • Weak typing: More implicit conversions

Symbol Table Operations

The symbol table supports these operations during semantic analysis:

  • insert(name, attributes): Add a new identifier entry
  • lookup(name): Find the entry for an identifier
  • delete(name): Remove entry when scope ends

Symbol tables can be linear list (slow, O(n)), binary search tree (O(log n)), or hash table (O(1) average). Each scope has its own table; nested scopes are managed with a stack of tables.

Three-Address Code (TAC)

Three-address code (TAC) is an intermediate representation where each instruction has at most three operands: x = y op z. The instruction format limits operations to one binary operator.

Common TAC forms:

  • Assignment: x = y op z (e.g., t1 = a + b)
  • Unary: x = op y (e.g., t2 = -t1)
  • Copy: x = y
  • Jump: goto L
  • Conditional: if x goto L; ifFalse x goto L
  • Procedure call: param x; call p, n
  • Index: x = y[i]; x[i] = y
  • Address: x = &y; x = *y; *x = y

Example: x = a + b * c becomes t1 = b * c; t2 = a + t1; x = t2

Representations of TAC

TAC can be implemented in three ways:

  • Quadruples: Each instruction has 4 fields: (op, arg1, arg2, result). Easy to optimize. Result is a temporary variable.
  • Triples: Each instruction has 3 fields: (op, arg1, arg2). References other instructions by position number. Compact but harder to optimize.
  • Indirect Triples: A list of pointers to triples. Easier to reorder instructions than pure triples.

Example: t1 = a + b; t2 = c + d; x = t1 * t2

Syntax-Directed Translation (SDT)

Syntax-directed translation attaches semantic actions (code fragments) to grammar productions. Actions are executed when the production is used in parsing, generating intermediate code or updating the symbol table.

Example for expression evaluation:

E → E1 + T { E.place = newtemp(); emit(E1.place '+' T.place '→' E.place); } E → T { E.place = T.place; } T → id { T.place = id.place; }

S-Attributed and L-Attributed Definitions

S-attributed definitions: Use only synthesized attributes — attributes computed from children to parent. Can be evaluated during bottom-up parsing.

L-attributed definitions: Allow synthesized plus inherited attributes that flow from left to right (parent to children, or left siblings to right siblings). Can be evaluated during top-down parsing.

Every S-attributed definition is L-attributed, but not vice versa. L-attributed covers a larger class including type checking.

Key Concept: TAC bridges the gap between high-level source and low-level target code. It is machine-independent and easy to optimize. The choice of representation (quadruples/triples) affects how easily optimizations can be applied.
Exam Tip: For TAC questions, always convert arithmetic expressions step-by-step using temporaries. For representation questions, show both quadruples and triples side by side for the same expression.

Explain three-address code representations.

Three-address code is represented in three main ways:

  • Quadruples: 4 fields per instruction: (op, arg1, arg2, result). Most common. Result field allows simple register allocation.
  • Triples: 3 fields per instruction: (op, arg1, arg2). Replaces explicit temporaries with positions in the instruction list. Compact but instructions are referenced by index.
  • Indirect Triples: List of pointers to triples. Separation allows easier reordering during optimization.

Example: a = b + c * d - e

Triples:

(0): *, c, d (1): +, b, (0) (2): -, (1), e (3): =, (2), a

Quadruples:

(0): *, c, d, t1 (1): +, b, t1, t2 (2): -, t2, e, t3 (3): =, t3, _, a

Quadruples are easier for optimization since each temporary has a name.

What is syntax-directed translation?

Syntax-directed translation (SDT) is a technique where semantic actions are attached to grammar productions. The actions are executed in a specific order during parsing to compute attributes, update the symbol table, generate intermediate code, or report errors.

An SDT consists of:

  • A context-free grammar
  • A set of attributes associated with grammar symbols
  • Semantic rules attached to productions

Two main attribute types: synthesized (computed from children) and inherited (computed from parent/siblings). S-attributed grammars use only synthesized attributes; L-attributed grammars allow inherited attributes flowing left-to-right.

Semantic Analysis is performed after syntax analysis. It checks type compatibility, scope rules, and semantic correctness. It uses the symbol table to look up declared types and verifies that operations are applied to appropriate types.

Key activities:

  • Type checking: Verify operand types match operator requirements
  • Type conversion: Insert implicit conversions where allowed
  • Overload resolution: Choose correct function based on argument types
  • Constant folding: Evaluate constant expressions at compile time

Intermediate Code Generation produces a machine-independent representation (typically TAC) using syntax-directed translation.

Indirect Triples: An additional list of pointers [0, 1, 2, 3] references the triples in the order of execution. The triples themselves can be stored in any order; the pointer list controls execution. This makes reordering (for optimization) easy without rewriting the triples.

  • Triples: compact, references by position, harder to optimize
  • Indirect triples: flexibility of pointers + compactness

Code Optimization & Generation

Basic blocks, DAG, peephole optimization, code generation, register allocation

Basic Blocks

A basic block is a maximal sequence of consecutive three-address instructions where:

  • Control can only enter at the first instruction (leader)
  • Control leaves only at the last instruction (without halting or branching except at the end)

Algorithm to identify leaders:

  1. The first instruction of the IR is a leader.
  2. The target of a conditional or unconditional jump is a leader.
  3. The instruction immediately following a conditional or unconditional jump is a leader.

A basic block extends from a leader to the next leader (or end of program).

Flow Graphs

A flow graph is a directed graph where each node represents a basic block and edges represent control flow. An edge from block B1 to B2 means control may flow from B1 to B2 (either fall-through or jump).

The entry block has no predecessors; the exit block represents all exit statements (return, halt).

Flow graphs enable analysis of loops, dominators, and optimization opportunities across blocks.

Directed Acyclic Graph (DAG)

A DAG for a basic block represents the computation structure. Each node represents a computation or value:

  • Leaf nodes: operands (variable names or constants) with labels
  • Interior nodes: operators with two children (operands)
  • A node may have multiple labels (if multiple variables hold same value)

DAG Construction:

  1. If node exists for the operand, reuse it.
  2. If the operation already exists, attach new labels to it.
  3. Otherwise, create a new node.

DAGs identify common subexpressions automatically — same node means same value.

Local vs Global Optimization

Local optimization applies to a single basic block. Examples:

  • Common subexpression elimination
  • Dead code elimination
  • Constant folding
  • Strength reduction (x*2 → x+x)

Global optimization applies across basic blocks using flow graph analysis. Examples:

  • Loop-invariant code motion (hoist computations out of loops)
  • Global common subexpression elimination
  • Induction variable elimination
  • Data flow analysis

Local optimizations are simpler; global ones require control flow and data flow analysis.

Peephole Optimization

Peephole optimization examines a small sliding window (peephole) of instructions and replaces them with more efficient sequences. Applied to target/assembly code.

Common transformations:

  • Redundant loads/stores: Remove STORE a; LOAD a if a is unchanged
  • Unreachable code: Remove code after unconditional jumps
  • Strength reduction: Replace expensive ops with cheaper ones (x*2 → x+x)
  • Constant folding: Evaluate constant expressions at compile time
  • Algebraic simplification: x+0 → x; x*1 → x; x*0 → 0
  • Use of machine idioms: Generate special instruction sequences

Peephole optimization is simple, fast, and effective at the assembly level.

Code Generation

Code generation is the final phase that translates optimized IR into target machine code. The main tasks are:

  • Instruction selection: Choose appropriate machine instructions for each IR operation
  • Register allocation: Decide which variables reside in registers at each point
  • Instruction scheduling: Reorder instructions to avoid pipeline stalls

The code generator must respect the calling convention, register usage, and instruction set of the target architecture.

Register Allocation

Register allocation assigns a (typically small) number of physical registers to a (possibly large) number of temporaries. The goal is to keep frequently used values in registers to minimize memory accesses.

Two approaches:

  • Local register allocation: Within a single basic block using graph coloring or next-use analysis
  • Global register allocation: Across the entire procedure using data flow analysis

The graph coloring algorithm models register allocation as coloring an interference graph (edges between variables that cannot share a register) with K colors (where K = number of registers).

Instruction Selection and Target Machine

Instruction selection maps IR operations to target machine instructions. The naive approach uses a fixed mapping; a better approach uses tree pattern matching with tiling or dynamic programming (BURS, BURG).

Target machine considerations:

  • Instruction set architecture (CISC vs RISC)
  • Number and types of registers
  • Addressing modes supported
  • Cost of each instruction (cycles)
  • Calling conventions

The code generator produces either assembly code (further assembled/linked) or relocatable machine code directly.

Key Concept: A good code generator produces correct, efficient target code. The main bottlenecks are: instruction selection (how to compile each IR op), register allocation (which variables go in limited registers), and instruction scheduling (avoid pipeline stalls). Modern compilers like GCC use multiple optimization passes.

Explain code optimization techniques.

Code optimization techniques improve intermediate or target code without changing its semantics:

  • Constant folding: Evaluate constant expressions at compile time (2 + 3 → 5)
  • Common subexpression elimination: Compute once, reuse (a = b*c; d = b*c → t = b*c; a = t; d = t)
  • Dead code elimination: Remove code whose results are never used
  • Strength reduction: Replace expensive ops with cheaper ones (x*2 → x+x)
  • Loop-invariant code motion: Hoist loop-invariant computations outside loops
  • Copy propagation: Replace copies with original variables
  • Peephole optimization: Improve small instruction sequences
  • Induction variable elimination: Replace induction variables with simpler forms

What is basic block?

A basic block is a sequence of consecutive instructions in which:

  • Control flow enters only at the first instruction
  • Control flow exits only at the last instruction
  • No internal jumps or branch targets within the block

Identifying leaders (first instructions of basic blocks):

  1. First instruction of the entire program
  2. Target of any jump instruction (conditional or unconditional)
  3. Instruction immediately following a jump

Each basic block extends from a leader to just before the next leader (or program end). Basic blocks are the unit of local optimization.

Explain code optimization and code generation. Discuss basic blocks, flow graphs, DAG, peephole optimization, and code generation algorithm with register allocation.

Code Optimization transforms IR to produce equivalent but more efficient code. Key concepts:

Basic Blocks: Identify leaders using the algorithm above; group consecutive instructions from one leader to the next.

Flow Graph: Construct a graph G = (N, E) where N = basic blocks and E = control flow edges. Useful for global analysis and dominator computation.

DAG Example for basic block:

t1 = a + b t2 = c + d t3 = t1 * t2 t4 = a + b x = t3 - t4

The DAG identifies that t1 and t4 compute the same value (a+b), so it can be reused:

Optimized: t1 = a + b t2 = c + d t3 = t1 * t2 x = t3 - t1

Peephole Optimization Examples:

  • STORE R1, a; LOAD R1, a → (remove both if a is dead)
  • MOV R1, R2; MOV R2, R1 → MOV R1, R2 (one instruction enough)
  • MUL R, 2 → SHL R, 1 (strength reduction)
  • goto L1; ... L1: ... → (remove unreachable code)

Code Generation Algorithm: For each IR instruction, the generator selects target code and performs register allocation.

Register Allocation Algorithm (Next-Use):

  1. For each instruction, determine next use of each operand by scanning forward.
  2. For a three-address op x = y + z:
  3. If y is not in register, load it. If z is in register (and y will not be needed after), use it.
  4. Choose a register R for result: prefer a register holding x; else a register with the farthest next use; else spill to memory.
  5. Issue target instructions, using register R.

Example Code Generation for t = a - b:

MOV R1, a ; load a SUB R1, b ; R1 = a - b MOV t, R1 ; store result

Register Allocation by Graph Coloring:

  1. Build interference graph (nodes = temporaries; edge if both live simultaneously)
  2. Try to color with K colors (K = number of registers)
  3. If a node cannot be colored, spill it to memory and retry

Target Machine Considerations:

  • Instruction set and addressing modes
  • Register count and special-purpose registers
  • Calling conventions (ABI)
  • Pipeline hazards (avoid stalls by reordering)

Modern compilers like GCC use multiple passes, profile-guided optimization, and link-time optimization for highest performance.
