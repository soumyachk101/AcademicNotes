Translate the arithmetic expression x + (b + c / d) into a syntax tree. Explain interpreted vs syntax-directed translation with suitable examples. What are the two types of attributes associated with a grammar symbol (inherited vs synthesized)?

Syntax tree of x + (b + c / d) (internal nodes = operators, leaves = operands, respecting precedence and parentheses):


            +
           / \
          x   +
             / \
            b   /
               / \
              c   d

An interpretation of a grammar is a rule that assigns a meaning (value, action) to each production. Two forms: (i) Interpreted translation — the parse tree itself is evaluated by an interpreter; the grammar productions are annotated with semantic functions that compute the value of the node from its children. Example: evaluating a + b * c by walking the tree and applying the function at each operator node. (ii) Syntax-directed translation — each production carries translation rules (attribute equations or semantic actions) that synthesize the output (postfix, 3-address code, object code) during parsing; a single parse of the input drives the generation. Example: production E → E + T emits E' T' + for postfix.

Attributes are values (of any data type) associated with grammar symbols (non-terminals and terminals). The two kinds:

  • Synthesized attributes: value of a parent is computed from its children (bottom-up); needs no context. Example: value of an expr node from its operand nodes.
  • Inherited attributes: value of a child is computed from its parent and/or siblings (top-down flow); gives a node context. Example: a type-checker passing the expected result type down from a statement node to its expression child.

Synthesized attributes yield S-attributed definitions; inherited ones (where needed) yield L-attributed definitions.

2

What is an attribute? What is a syntax-directed definition (SDD)? Illustrate with an example (postfix-evaluation SDD). What is an attributed grammar? What is ambiguity in a grammar? What is the necessity to generate a parse tree? Any technique to remove ambiguity (left factoring / grammar rewriting)?

Attribute: a value associated with a grammar symbol — it can be a number, string, AST node, error code, or any program object (e.g. the value of an expression node, the type of a declaration, the generated code for a statement).

Syntax-directed definition (SDD): a grammar augmented with an action attached to each production. The action is either (i) an equation over attributes or (ii) executable code. It is written as production ::= action, with actions of a non-terminal separated by |, e.g. expr ::= term | expr "+" term.

Postfix-evaluation SDD example:

expr >= expr1 '+' expr2      expr >> print ( expr1.postfix
                                       . expr2.postfix . "+" )
term >= id                     term >> print ( id.value )
     | '(' expr ')'            term >> print ( expr.postfix . ")" )

With input ((2*(3+x))*((2+y))) the tree bottom-up evaluation yields postfix 2 3 x + * 2 y + * * *.

Attributed grammar: a grammar whose productions carry attribute rules (synthesized or inherited). The parse tree plus attribute rules forms the attributed parse tree; evaluating the rules is the translation.

Ambiguity: a grammar is ambiguous if some string has more than one leftmost (equivalently, rightmost) derivation, i.e. more than one parse tree — e.g. E → E + E | E * E for a + b * c. Ambiguity must be resolved because an unambiguous tree is needed for deterministic semantic action.

Necessity of a parse tree: the tree fixes the order of operations (precedence/association), localises each node's context (needed for inherited-attribute flow), supports optimization (DAG sharing), and drives code generation.

Removing ambiguity: (i) Grammar rewriting — restructure into precedence levels: E → T | E + T; T → F | T * F; F → id | '(' E ')' — now one tree per string. (ii) Left factoring — extract a common prefix (A → cAb | cAc → c A (b|c)); this makes the grammar suitable for top-down (LL) parsing by removing the common-prefix choice; it does not by itself remove ambiguity, so combine both techniques.

3

Draw a DAG for the expression statement: if x ≠ 0 then x := 3*(y + 1) else z := y + 1. Show the DAG with node sharing where applicable.

A DAG is obtained from the expression tree by sharing every common subexpression: identical children are identified into one node. Here y + 1 occurs in both branches — it is shared. The boolean test x ≠ 0 produces true/false leaves driving the two conditional edges. Labelled edges T/F (true branch / false branch) and assignments are terminal actions.


                 +-----------+
                 | x  neq  0 |   boolean test: T if x != 0
                 +-----+-----+
             T/   |           \F
                  v            v
            +-----------+  +-----------+
            | 3 * (y+1) |  |   y + 1   |
            +-----+-----+  +-----------+
                  |            |
                  v            v
          (assign x := )   (assign z := )

Reading the DAG: root is the conditional; on T we compute 3 * (y+1) and assign to x; on F we compute y + 1 and assign to z. Because y+1 appears under both branches, a single node is shared between the two paths. The shared y + 1 lets the compiler lift that subexpression out of the conditional once (common subexpression hoisting):


   t := y + 1            // hoisted, evaluated ONCE
   if x != 0 then x := 3 * t
   else z := t

Optimization payoff: one subtraction/addition, one store to t, one conditional store. The ≠ test node also collapses a constant-fold when x is a compile-time constant (e.g. if 5 ≠ 0 always T; if 0 ≠ 0 always F — dead-code elimination).

Translate the arithmetic expression x * (b + c) into a syntax tree and postfix notation. Design a DAG for a + a*0 + 0*0 + 0 + d + 0 + 0, showing constant-folding simplification.

Syntax tree of x * (b + c):


            *
           / \
          x   +
             / \
            b   c

Postfix (operands, then operator in postorder): x b c + *.

DAG of a + a*0 + 0*0 + 0 + d + 0 + 0: The sheet prints the constant as 0 (the original source uses O typographically). We assume 0 is the numeric constant zero (identity for multiplication, identity for addition in the usual ring), not an indeterminate variable or an operator letter. With this assumption every term involving 0 folds:


   Assumption: the "O" printed in the source is the numeric constant 0,
   so that:  x * 0 = 0   and   0 * 0 = 0   and   x + 0 = x.

   a + a*0 + 0*0 + 0 + d + 0 + 0
   = a + 0   + 0   + 0 + d + 0 + 0      (constant folding: a*0 → 0, 0*0 → 0)
   = a + d                                 (adding 0 is identity)

The resulting DAG is a single add node with leaves a and d:


   +
  / \
 a   d

Assumption explicitly stated (for marking): the source uses the letter O where the constant zero 0 is meant; we treat it as the integer constant 0 with the standard ring axioms so that multiplication by 0 and addition of 0 are identities. The DAG has two leaves and one internal + node. No subexpression sharing is needed beyond that because each leaf is distinct. (If the original symbol were instead the variable O, the expression would not fold to a + d; the simplification therefore depends on this reading.)

How do we mean by Syntax-Directed Translation? Compare S-attributed and L-attributed SDDs in a table. What are the main contributions of SDT?

Syntax-Directed Translation (SDT): a grammar G = (V, Σ, P, S) augmented with attribute equations (or semantic actions) attached to productions, such that every parse of an input sentence has a meaning — the generated target (postfix, intermediate code, object code). A parse of a sentence w with root R evaluates the equation tree rooted at R to yield G(w) in the output language.

AspectS-attributed SDDsL-attributed SDDs
Flow of valuesbottom-up: children → parenttop-down and left-to-right into children; only synthesized from above
Typical usetree evaluation, static analysis, most semantic checkscode generation, register allocation, type-checking
Evaluation orderpostorder of the parse treeinorder (left-to-right) of leaves
Number of passesone bottom-up pass over the tree sufficesrequires a single left-to-right traversal; no second pass — each child can be evaluated as soon as all its left siblings and its parent's attributes are known
Feasibilitytree evaluation onlycan be evaluated online by any top-down parser (LL, even some LR with care)
Example equationexpr.val = expr1.val + expr2.valstmt.type = stmt1.type — the L attribute flows down to child stmt1 from parent stmt
When usedwhen the result of a node depends only on its own descendantswhen the result must flow into children (e.g. target machine code depends on which register a variable lives in)

Contributions of SDT to automatic code generation: (1) it converts parsing into generation: a single bottom-up or left-to-right pass simultaneously computes the meaning and emits output, e.g. an interpreter (postfix code evaluation) or an assembler (assembling object code while parsing the source). (2) It unifies syntax and semantics: the semantic action is declared with the production, making it provably well-formed and machine-checkable. (3) It supports two-stage compilers: an attributed parse tree yields a target program that can later be re-optimized. (4) It supports the separation of concerns: parsing is the syntactic role, translation is the semantic role — a clean decomposition that is the backbone of every production compiler.

What is an input-buffering implementation? What problems can arise when implementing the input buffer (lookahead beyond a single character, token boundaries spanning buffer boundaries, end-of-file)? What is a sentinel and its use?

Input buffering: the compiler reads the source into a large buffer (input buffer) rather than character-by-character; the parser pulls tokens from the buffer via a next_token() routine. Each token is cached, with a pointer to the next character. The buffer must hold enough input for the parser's lookahead window.

Problems:

  • Lookahead > 1 character. If the buffer holds only one character, a token like == (2 chars) or an identifier abc (3 chars) cannot be emitted. The buffer must hold enough characters to see the complete next token. For a grammar with max k-lookahead, hold k characters.
  • Token boundary spans the buffer edge. A token may straddle the boundary between two read() chunks — e.g. a 512-byte buffer holds foo in the first chunk but bar in the second; the tokenization engine must not split identifiers, string literals or comments at the buffer edge. One must either (i) read the whole file at once, or (ii) implement a sliding buffer that holds the tail of the previous chunk plus the head of the new chunk so tokenization never straddles the join.
  • End of file. When the buffer runs out of characters the matcher must detect it without dereferencing *buffer_ptr = 0. The usual technique: append a special marker (sentinel) so the parser can recognise that no more input follows.

Sentinel: a special character — commonly $ or an internal EOF token — that the lexer consumes (recognises as "no more input") but that the parser never attempts to match against a grammar production. The sentinel terminates the input: a matching loop checks if (*buf == SENTINEL) return; before emitting a token; the parser's productions do not have $ on their right-hand side, so the parser only sees the sentinel to know the input has ended, not to parse it.

Why a sentinel matters: it separates the lexing concern (how far to read) from the matching concern (which production does this token match). Without it, every matcher must special-case the "is this the last character" check, and an unterminated identifier/string would otherwise be silently split at EOF. With it, the buffer can be refilled or exhausted; the sentinel is the fixed point the matcher converges on.

Mention different loop-optimization techniques. What is a dependency graph? What is an LR(1) parser (brief recap in the code-generation context)?

Loop-optimization techniques:

  • Loop unrolling: duplicate the loop body 2, 4 or k times so that the branch-per-iteration is amortised over k iterations. The loop bound n must be a compile-time multiple of k (or a residual tail loop handles the remainder). Speedup: 1/k fewer branch checks; code size: k× larger. Example: for(i=0;i<n;i+=4){b[i]=a[i]*2; b[i+1]=a[i+1]*2; b[i+2]=a[i+2]*2; b[i+3]=a[i+3]*2;}
  • Loop jamming: combine two (or more) consecutive loops over the same range into one loop over one array traversal, reducing memory traffic and instruction fetch. for(i) t[i]=a[i]+b[i]; jammed with for(i) c[i]=t[i]*2; becomes one loop.
  • Induction variable elimination (strength reduction): replace a costly induction variable (like i*k, the address calculation) with an add-by-constant chain. If i = i + 1 each iteration, addr = base + i*k becomes a addr = addr + k update, one integer add per iteration instead of a multiply.
  • Strength reduction: replace a hard operation with a cheaper equivalent on the path: x*8 → x << 3; pow(n,2) → n*n when n is small.
  • Peephole optimization: a local scan of a window of w instructions (usually a register or stack) that applies local rewrites: x = x + 0 delete; x = 1; x = x*2; → x = 2; LOAD t; LOAD s; → LOAD s.
  • Loop invariant code motion (LICM): hoist statements whose value does not change within the loop body out of the loop (e.g. addr = &mat[i][j] outside a for(k) { ... } loop that does not write i or j).

Dependency graph: a directed graph whose nodes are the statements of a loop; an edge Si → Sj means Sj reads a value that Si writes (a data dependency, i.e. flow). Two subcases: a loop-carried edge (Sj is in the next iteration of Si's value) is a true dependency that prevents parallel execution; a anti-dependency (write-after-read) can be removed by renaming registers/arrays. The graph exposes which iterations can be run simultaneously — the basis of loop parallelisation.

LR(1) parser (recap): a bottom-up (shift-reduce) parser that keeps a stack of states and reads exactly one lookaheads (hence "LR(1)"). It is constructed from the grammar by the item sets method: LR(0) items are a production with a dot in some position; the closure and goto functions close sets on non-terminals after the dot. The parser has a finite automaton of states; each state has LR(1) sets of (item, lookaheads) pairs that determine whether to shift or reduce. LR(1) can handle every language that is unambiguous in the sense of leftmost-derivation + 1 lookaheads — a strict superset of LL(1). In code generation it is the workhorse of bottom-up semantic evaluation: reductions give the bottom-up order needed for S-attributed SDDs; inherited attributes can be handled by passing values through the stack. LR(k) (k > 1) adds more lookahead but blows up the state table; k = 1 is the sweet spot — enough lookahead for most imperative-language grammars.

What is type checking? Differentiate dynamic and static type checking.

Type checking: a verification step that confirms every value in a program is used in a way consistent with its declared type, and that every expression / declaration / statement has a type that can be assigned. The goal is to catch errors early that would otherwise surface as runtime crashes, garbage data, or silent mis-computation. Type systems are the language's specification of which values are interchangeable.

AspectStatic type checkingDynamic type checking
When errors are detectedat compile time (before execution)at runtime, as the values flow through the program
Mechanismtype inference / type checker walks the AST and checks each nodeeach operation inspects the actual values' tags before execution; incompatible → raise an exception
Example languageJava: int x = "abc"; — rejected at compile time; also long y = 3.14; needs explicit castPython: x = "abc" + 1 raises TypeError only when the line executes (a variable can be reassigned to any type)
Cost at runtimelow — checks done once; generated code can assume types are correcthigh — every operation has an attached tag check; the interpreter must inspect values
Effect on program structuretypes propagate; a type error forces restructuring before runningtypes evolve; no compile-time contract; errors localize at the site of execution
Strength of guaranteeif the type system is sound, every run obeys it (all type errors detected before running)if a check fails the program aborts; a partial guarantee — some errors are caught, others silently propagate
Typical error classmissing return types, wrong argument types, uninitialised variables, unhandled checked exceptionsruntime type errors, e.g. None handling in Python, dynamic-dispatch failures
Trade-offcatches more bugs earlier; the programmer pays in boilerplate; hard to write ad-hoc polymorphismflexible, less code; bugs surface late; slower execution due to tag checks

Note on Java vs Python: Java is statically type-checked and strongly typed — a String literal may not be assigned to an int variable without a compile-time error. Python is dynamically type-checked: variables have no declared type; the type is that of the value, and x + 1 only works when the current value of x is int. Python also does not do static checking — it uses duck typing (check the method, not the type) at each call site, so its dynamic check is a method dispatch failure, not a tag-check failure.

What are the types of type systems? What are the specifications of a simple type checker (type inference rules, unification, subsumption, environment)?

Types of type systems (classified on several axes):

  • Typed vs untyped: untyped (machine code, raw C with void*) — every expression has the same type; typed — every expression has a distinct type.
  • Strongly vs weakly typed: strongly — operations only between values of compatible types ("a" + 1 is an error); weakly — implicit conversions are allowed ("a" + 1 becomes "a1" in JavaScript); strong + strict = sound type system.
  • Explicit (nominal) vs implicit (structural): nominal — two types are identical only if the programmer named them identically (Java class Dog1 vs class Dog2); structural — two types are interchangeable if their shape (fields, methods) match (interface-style, in Go and in many functional languages).
  • Sound vs unsound: sound — if the type checker accepts a program, no run-time type error can occur; unsound — the checker lets through a program that will break at runtime (e.g. implicit any in TypeScript, unchecked generics in some languages).

Specifications of a simple type checker: A simple type checker assigns a type to every expression and verifies that every application matches its expected signature.

(1) Type inference rules. A set of rules of the form (Γ, E) → τ, where Γ is the environment (map from variable → type), E is an expression, and τ is the inferred type. Examples:

  • Literals: Γ ⊢ 42 : int; Γ ⊢ "hi" : string
  • Variables: if x : t ∈ Γ, then Γ ⊢ x : t
  • Application: Γ ⊢ e1 : t1 → t2 and Γ ⊢ e2 : t1 implies Γ ⊢ e1(e2) : t2
  • Let: Γ, x : t ⊢ e2 : t' and Γ ⊢ e1 : t implies Γ ⊢ let x = e1 in e2 : t' (with let-generalisation for polymorphic types)

(2) Unification. When two type expressions must be equal (e.g. function argument type = parameter type), the checker solves equations between type variables to make them compatible. E.g. unifying a → int with string → b binds a := string and b := int, giving the most general type string → int. The unifier is the engine of inference: it either succeeds with a binding, or fails with a type clash.

(3) Subsumption. A subsumption rule says that τ₁ ⊑ τ₂ (τ₁ is a subtype of τ₂) — a value of type τ₁ may be used where τ₂ is expected. A subsumption rule in a checker: if Γ ⊢ e : τ₁ and τ₁ ⊑ τ₂, then Γ ⊢ e : τ₂. Inheritance: a Dog value can fill a slot expecting Animal (Dog ⊑ Animal).

(4) Environment. The type environment Γ is a mapping from each free variable in scope to its declared type. It grows as new variables come into scope (Γ, x : t) and shrinks when they leave (Γ \ {x}). The checker keeps a stack of environments (one per scope); the most-inner binding shadows outer ones. The environment plus the rules defines the typing context; the checker's verdict is Γ ⊢ E : τ for some well-formed τ — or a type error if no τ exists.

Putting it together (the four pillars of a simple checker): the environment supplies the declared types; the inference rules walk the AST and assign types; unification solves the type-variable equations that arise; subsumption allows subtypes to fill supertype slots. A program type-checks iff it type-checks under all four rules simultaneously.
