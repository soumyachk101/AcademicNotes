What is an activation record (stack frame)? Explain its components in detail (control info: return address, return register, home base; temporary/locals; access link; parameters). What are the various data structures used for symbol-table construction? When and how are active activation records used? What is a symbol table, and how is it implemented?

Activation record (stack frame): the memory area created on the run-time stack when a procedure is called and discarded when it returns. It holds everything needed to complete the procedure's execution and resume the caller: parameters, local variables, temporaries, control information and links to other frames.

Components:

+----------------------------------------------+
|            caller's frame (top of stack)     |
+----------------------------------------------+
|  actual parameters: p1 p2 ... pn            |  passed by caller
|  access link    --> caller's frame           |  for free vars / dynamic chain
|  temporaries: t1 t2 ...                     |  intermediates of expressions
|  local vars: x y z ...                      |  named variables of the proc
|  control information:                       |
|     return address  (PC of instruction       |
|                     after the CALL)          |
|     return register (value a function returns|
|                     in, on return)           |
|     home base (offset of the procedure's     |
|                 locals from the static base) |
+----------------------------------------------+
                     (SP grows down; FP points
                      to the control-info area)
  • Return address: so the caller can continue after the callee finishes.
  • Return register: the value a function expression evaluates to, held on return.
  • Home base: used only when local names are accessed statically — enables fast access to globals and statically-allocated locals.
  • Access link: pointer to the activation record of the textually enclosing procedure — it forms the static (lexical) chain used to reach nonlocal variables; the dynamic chain is the chain of frames currently on the run-time stack (the caller frames), used for dynamic scoping, where a name resolves to the most recent activation of the same procedure.

Data structures for the symbol table:

StructureSearchWhen used
Linear listO(n) scanDynamic scoping / blocks — entries created and destroyed as blocks are entered; supports lifetimes
Hash tableO(1) averageThe standard choice; fixed-size array, hash of name; needs collision handling (open addressing / chaining)
Binary search treeO(log n)Names in sorted order; supports range queries over names
Direct addressO(1) exactArray indexed directly by the name; fastest but impractical for large name-spaces

What a symbol table is and how it is implemented: a structure recording semantic information about every identifier. An entry carries at least: name, type, scope, address (the target location), plus kind (variable / procedure / constant), level, and a next pointer. Two strategies: (1) per-scope tables — each block has its own table linked to the outer block's (the static chain); on exit the table is destroyed and names die with it; or (2) a single global table where every entry is marked with its scope/level and deleted when its scope ends. Per-scope tables give clean lifetime management; a global table is simpler but must scope-check on every lookup.

Explain syntax errors vs semantic errors with a table of examples. What are the dynamic storage-allocation techniques? What are the storage-allocation strategies — stack vs heap, with garbage collection?

Syntax vs semantic errors: a syntax error is a violation of the grammar of the language — detected by the parser; a semantic error is a meaning violation (type, scope, use-before-declaration) in a structurally correct program — detected by the semantic analyzer. Structural form is checked first; semantics only when the program is syntactically correct.

Syntaxif (x < 3) y = 4 — missing ;Parser (LL/LR, shift-reduce conflict)
Syntaxsum = (a + b — unmatched parenthesisParser

Semanticcalling foo(2) when foo takes 3 argsSemantic analyzer

Dynamic storage-allocation techniques (allocating data at run time, as opposed to static/compile-time allocation) — three main forms:

  1. Stack allocation — for variables whose lifetime follows the control structure of the program (automatic locals of a procedure, loop bodies). Allocated by moving a pointer, O(1), and released in exactly LIFO order when the block/procedure exits.
  2. Heap allocation — for data with a lifetime that is not controlled by the control structure: dynamic arrays sized at run time, nodes of linked structures that outlive the allocating scope (malloc/free, new/delete). Requires explicit or collected deallocation.
  3. Garbage collection — the runtime itself determines when heap objects are dead and reclaims them, so the programmer never deallocates.

Storage-allocation strategies compared:

StrategyBehaviourStrengthLimitation
StackLIFO, single top pointer, bounds checked on pushVery fast, O(1); automatic release; natural for recursionOnly works when lifetimes nest with the control structure; no dynamic scoping; fixed upper bound per procedure
HeapPool of free blocks; first/next-fit allocation at run timeSupports arbitrary lifetimes (dynamic arrays, graphs, strings built at run time)Slow (search for a block + bookkeeping); fragmentation; free must be called exactly once or leaked

Garbage collection fixes the "who frees it?" problem: reference counting keeps a count per object and frees it when it hits 0 (simple, but cyclic leaks and cost per access); mark-and-sweep periodically starts from the roots, marks reachable objects, then sweeps the rest (handles cycles, stops the world or runs in two passes). Heap + GC is the usual strategy for languages like Java; stack stays the default for ordinary automatic local variables.

3

Discuss the parameter-passing mechanisms with suitable examples: (a) call by value, (b) call by reference, (c) call by name, with a worked example where by-name changes the program result. Then the storage-allocation strategies: (a) stack allocation, (b) heap allocation, with snippets.

a) Call by value (copy semantics): the value of the actual argument is evaluated once at the call and copied into the formal parameter. The callee's modifications to the parameter are invisible to the caller — no side effects, no aliasing, safest and most common.

void inc(int x) { x = x + 1; }   // x is a copy
int main() { int a = 5; inc(a); printf("%d", a);  // prints 5 — a unchanged
}

b) Call by reference (pass by location): the callee receives the address of the actual variable; the formal and actual are aliases. The callee can modify the caller's variable — this is the mechanism for output parameters, but it also creates the aliasing danger:

void swap(int &p, int &q) { int t = p; p = q; q = t; }
swap(x, x);            // aliasing: p and q are the SAME place
                        // t = x; x = x; x = t  ->  no effect, not a swap
swap(x, x + 1);        // overlapping evaluation order -> undefined behaviour
Passing x and an expression of x mixes aliased lvalues; the same-variable call silently fails.

c) Call by name (lazy evaluation): the actual argument expression is substituted textually for the formal and re-evaluated every time the formal is used. It enables passing functions/expressions unevaluated, but re-evaluation can change the result:

// by-name: y and z are the EXPRESSION x, not its value
proc A(x)
  B(x, x)
A(4)
proc B(y, z)          // y, z formal-by-name
  y := 3
  z := y
end B
// global variable z is written

by value:  B copies x=4 for both y and z.
           y:=3  (writes the local copy);  z := y  ->  z = 4
by name:   y and z are both the expression "x".
           y := 3  substitutes x := 3  (x is now 3)
           z := y  substitutes z := x = 3  ->  z = 3
Different final value of z (4 vs 3) from one semantic choice.

Storage-allocation strategies:

// a) Stack allocation: LIFO, O(1) pointer move, lives with the control structure
int* p = stack_alloc(8 * 100);      // 800 bytes on the run-time stack
free(p);                             // released on scope exit — automatic

// b) Heap allocation: arbitrary lifetime, GC or explicit free needed
int* q = malloc(100 * sizeof(int));  // heap block, survives the caller's scope
free(q);                             // programmer's responsibility (or GC reclaims)

The stack is fast and automatic but supports only lifetimes that nest with the control structure; the heap is slower (free-list search + bookkeeping) but supports data that outlive the allocating procedure.

1

Translate the arithmetic expression 5 * a * (b + c) / d into (a) three-address code (temporaries t1…t4 shown) and (b) postfix notation.

a) Three-address code (TAC): each statement has at most three operands; every intermediate value is a temporary so that no address is reused before it is consumed. Operator precedence is honoured explicitly:

5 * a * ( b + c ) / d
--------------------------
t1 = b + c
t2 = 5 * a
t3 = t2 * t1
t4 = t3 / d
result = t4

Equivalent x86-style listing (target ISA: x86-64, EAX/EBX/ECX/EDX registers):

mov  ECX, 5
imul ECX, [a]          ; ECX = 5*a        (t2)
mov  EDX, [b]
add  EDX, [c]          ; EDX = b+c        (t1)
imul ECX, EDX          ; ECX = 5*a*(b+c)  (t3)
mov  EAX, ECX
idiv [d]               ; EAX = t3/d       (t4)  ; quotient in EAX, remainder EDX
mov [result], EAX

b) Postfix (reverse-Polish) notation: operands are listed left-to-right with each operator immediately following its operands; precedence is encoded by the ordering, so no parentheses are needed:

5 * a * (b + c) / d   -->    5 a * b c + * d /

Stack evaluation confirms it: 5 a * → t2; b c + → t1; * → t2*t1 = t3; d / → t3/d = t4. The postfix form is exactly what an interpreter or a stack machine executes — each operator pops its operands and pushes the result, which is why postfix code needs no precedence table and no parentheses.

Explain quadruples, triples and indirect triples; give a comparison table; represent x := (a + b) * c - d in all three forms; generate machine code for x := a + (b * c) - d; and state the properties of intermediate representations suitable for (a) indexed assignments, (b) pointer assignments, (c) conditional statements.

Quadruples: one tuple (op, arg1, arg2, result) per statement; the result is an explicit 4th field (a named temporary), so values go to a temporary first and move only at the end — easy to reorder and to CSE.

Triples: 3-tuples (op, arg1, arg2) — no result field; a triple's "value" is its position number, so later triples refer to it by index.

Indirect triples: a separate list of triple numbers gives the execution order; reordering during optimization edits only the list, and final code is produced by patching that list.

For x := (a + b) * c - d:

Properties of IRs suitable for:

  • (a) Indexed assignments x[i] := e — the IR must express address computation (base + scale × index) as a first-class node; a DAG with an addr(x, i) node supports reusing it, and 3-AC needs an explicit temporary t = x + i*W before t := e.
  • (b) Pointer assignments p := q — the IR must carry type on every variable; a pointer lvalue means writing through the address, so aliasing must stay explicit; type-erasing arithmetic IRs are unsuitable.
  • (c) Conditional statements — use two-way branches (jump-if, else label) rather than unrestricted gotos, so control flow is structured; use a copy statement for non-scalar assignment.
  • DAG / IR advantages: CSE, strength reduction and redundancy checking all fall out of node sharing. Cost: per-block DAGs are O(n) with pointer overhead; whole-program DAGs are rarely used — cross-block dataflow makes them expensive.

What is backpatching? Give a worked mini-example (L1/L2 list patches for the code of if x < 10 goto L, showing next/prev fields). What are the issues in the design of a code generator?

Backpatching: when the code generator emits a jump whose target is not yet known (a forward branch), it writes the instruction with a placeholder target and records the instruction's address in a backpatch list. When the target is finally reached, the recorded addresses are patched — the placeholder is filled in with the true address. Each list entry stores the address of the instruction to patch plus next and prev links (a doubly-linked list) so old and new addresses can be appended at either end in O(1).

Worked example — statement if (x < 10) goto L plus an else fall-through body:

Code generated so far (jump targets are still "?"):
addr  instruction                    L1 list            L2 list
----  -----------------------------  --------           --------
  0   jump-if-true   x  10   ?      [0]                []
  1   jump           _  _    L      [0]                [1]   (patch #1 when L known)
  2   [ body of "if x < 10" ]
  3   [ else body ]
  4   [ code after the if-then-else ]

Patching step by step:
 backpatch(L1, 4):  the true branch targets addr 4
                    list entry #0:  next = NULL,  prev = NULL,  patch_addr = 4
                    code line 0 becomes:  jump-if-true x 10 4
 backpatch(L2, 3):  the else (fall-through) targets addr 3
                    list entry #1:  next = NULL,  prev = #0,  patch_addr = 3
                    code line 1 becomes:  jump _ _ 3
After both patches every jump has a real target; the
L1/L2 lists are empty and released.

Issues in code-generator design:

  1. Quality of generated code — the generator must be correct: the machine code's input-output behaviour must exactly match the source, even after aggressive transformations.
  2. Register allocation — deciding which values live in which registers, what spills to memory, and where spills occur; naive one-value-one-register is far from optimal; dynamic allocation with liveness is much better.
  3. Addressing-mode selection — choosing base-pointer, scaled-index, immediate or memory operands to minimize instruction count and memory references.
  4. Memory ordering and access patterns — respecting side effects (an lvalue must be evaluated where it may have effects) and minimizing loads/stores through the memory hierarchy.
  5. Code size vs speed — small code (shorter instruction count, fewer branches) vs fast code (more registers, more instructions); targets differ: embedded vs desktop.
  6. Machine-specific knowledge — the generator encodes the calling convention, data-type support, branch targets, and alignment requirements of the target ISA.
  7. Preserving semantics under optimization — every optimization must be provably meaning-preserving; the correctness criteria are the same as for optimization (same I/O on all inputs).

What are the properties of an efficient code generator? Discuss the optimization levels (local vs global vs interprocedural) briefly.

Properties of an efficient code generator:

  1. Correctness — the generated program must have exactly the same observable behaviour as the source for every input; no transformation may change lvalue evaluation order, side effects, or I/O order.
  2. Fast machine code — exploit the machine's addressing modes, use registers for frequently referenced values, minimize memory references, and choose branch targets that are usually taken (profile feedback when available).
  3. Short code — minimize instruction count where it does not hurt speed; important on cache-limited or embedded targets.
  4. Effective register allocation — keep hot values in registers; spill only what must live; a good allocator can beat a bad one by a wide margin.
  5. Minimum memory references — keep loop-carried values in registers across iterations; avoid reloading invariants inside loops.

Optimization levels:

LevelScopeTypical transformations
Localone basic block / statementconstant folding, common subexpression elimination, strength reduction, peephole patterns, copy propagation
Global (intra-procedural)whole procedure / flow graphloop-invariant code motion, dead-code elimination, induction-variable substitution, loop unrolling / jamming
Interproceduralacross call sites / whole programfunction inlining (removes call overhead, exposes more dataflow), argument duplication, partial evaluation of known calls

Local transformations are cheapest and run in the same pass as code generation; global transformations require data-flow analysis over the control-flow graph (liveness, reaching definitions, available expressions) and yield the biggest gains on loops; interprocedural analysis is the most powerful but the most expensive (the call graph can be large, inlining can blow up code size, and correctness across program boundaries must be preserved by respecting calling conventions and side effects).

Basic block: a maximal straight-line sequence of code with a single entry at the top and a single exit at the bottom — no branches, jumps, labels, or stops inside. Blocks are found by identifying leaders: (1) the first statement of the procedure; (2) any statement that is the target of a jump; (3) any statement immediately after a jump or conditional. Each leader starts a new block and runs to the next leader (or the end).

Code optimization = transforming a correct program into a faster / smaller / more memory-efficient one. Correctness criteria: (1) for every input the optimized program produces the same output; (2) the relative order of I/O is preserved; (3) no side-effecting lvalue is evaluated at a different point. Levels: local (block/peephole), global (whole procedure, loop-level dataflow), interprocedural (across call sites, inlining).

What is peephole optimization (with a rules table)? What are dead code elimination, variable elimination, code motion, and reduction in strength?

Peephole optimization: look at a short "window" of adjacent instructions (the peephole) and apply a set of pattern-substitution rules that simplify the local code. It is the cheapest form of optimization — no data-flow analysis, just local algebra on the instruction stream.

PatternReplacementRationale
x + 0xidentity
x * 1xidentity
x * 00annihilation
x - 0xidentity
x - x0difference of identical operands
-( -x )xdouble negation cancels
x + x2 * xstrength reduction: add to multiply
LOAD x; LOAD xdelete oneredundant load
STORE x, v; LOAD x with no intervening write to xv (a register/temp)redundant store-load pair

Dead code elimination: remove code that cannot affect the observable output. Two forms: (1) dead assignments — v := e where v is never read again before being redefined (v is "dead" at that point); (2) unreachable code — statements after an unconditional jump, or inside a condition that can never be true. Both require liveness / reachability information.

Variable elimination: replace every use of a variable with the expression that defined it (generalised copy propagation), provided no side effect is lost: the defining expression must be side-effect-free, and v must not be an lvalue anywhere (no &v, no array-of-pointers where v is an element). It collapses a variable into its value and exposes further optimizations like CSE.

Code motion: move code to a point where it is executed less often without changing semantics. The principal case is loop-invariant code motion: an expression whose value does not change inside the loop is moved before the loop. Legality conditions — all must hold: (1) the value of every operand is invariant over the loop body; (2) no operand's address is modified inside the loop (aliasing); (3) the operand is not the loop's induction variable; (4) evaluation order of side-effecting lvalues is preserved.

for (i = 0; i < n; i++)          for (i = 0; i < n; i++)
  a = a[i] + b + 1;                 a = a[i] + t;
                                   t = b + 1;              // moved out (invariant)

Reduction in strength: replace an expensive operator with a cheaper one computing the same value: multiplication → addition (x*x → 2*x when x is a power of 2), division by a power of 2 → right shift (x/8 → x >> 3 for unsigned), repeated addition → induction variable, pow(2,k) → 1 << k.

What is meant by redundant load/store statements? Explain with examples: (a) constant folding, (b) common sub-expression elimination, (c) loop unrolling, (d) loop jamming, (e) copy propagation — each with a short before/after.

Redundant load/store: a LOAD instruction that fetches a memory value which is already known (because the last store to that location is visible in the same window and the location has not been written since) is redundant; similarly a STORE followed by a LOAD of the same value with no intervening write is a redundant pair. The optimizer substitutes the known value for the load and deletes the store if the value is not otherwise needed:

before:  v = x + 1;  x = v;  y = x;       after:  v = x + 1;  y = v;  x = v;
(2 loads and 1 store collapsed; x's load deleted because v is live)

(a) Constant folding: evaluate an arithmetic expression whose operands are all compile-time constants, and replace it with the result:

before:  x = 2 + 3;          after:  x = 5;
        a = b * 4;          after:  a = b << 2;   (strength reduction folds too)

(b) Common subexpression elimination: if an expression e is computed, its value stored in a temporary t, and t has not been redefined, then every subsequent occurrence of e is replaced by t:

before:  t1 = a + b;  c = t1;  d = a + b;     after:  t1 = a + b;  c = t1;  d = t1;
(uses reaching-definitions analysis to know t1 still holds a+b)

(c) Loop unrolling: replicate the loop body k times and adjust the induction variable, to reduce branch and loop-control overhead:

before:  for (i = 0; i < 4; i++)  s = s + a[i];
after:   s = s + a[0]; s = s + a[1]; s = s + a[2]; s = s + a[3];
        (4 iterations, 3 fewer branch checks)

(d) Loop jamming: two (or more) loops that iterate over the same array at the same index are merged into one — the array element is loaded once instead of twice, halving memory traffic:

before:                              after:
for i:  a[i] = b[i] + c[i];        for i:  t  = b[i] + c[i];
for i:  d[i] = a[i] * 2;                 a[i] = t;
                                      d[i] = t * 2;
                                  (a[i] stored then re-loaded: eliminated;
                                   one pass, half the I/O)

(e) Copy propagation: replace uses of a variable with the value that was assigned to it, provided the variable is not an lvalue and the assigned expression has no side effect. It makes CSE and dead-code elimination possible:

before:  y = a;  x = y;  z = y + 1;      after:  x = a;  z = a + 1;
                                          (y's definition is now dead -> deleted)

y = a becomes a dead assignment — y is never used after propagation — so the compiler deletes it and both x and z read a directly: the classic pipeline copy propagation → CSE → dead-code elimination.
